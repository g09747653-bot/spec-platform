## Overview

Автономный контур доставки — это локальная программная экосистема, предназначенная для автоматического перевода коротких текстовых или голосовых задумок пользователя в полностью протестированный и готовый к развертыванию программный продукт. Вся работа по реализации выполняется полностью автономно, силами группы специализированных ИИ-агентов, функционирующих непосредственно на локальной рабочей станции пользователя под управлением ОС Windows.

### Цели и фазы развития проекта

Разработка и запуск системы осуществляются в четыре последовательных этапа:
1. **Локальный однопользовательский режим Spec Platform**: развертывание и функционирование всего стека на машине владельца. Исключаются облачные провайдеры авторизации (без OAuth), используется локальная СУБД SQLite, локальная цепочка моделей (через Ollama или аналогичные решения) либо облачные API-ключи по выбору пользователя, настраиваемые локально.
2. **Кодификация handoff-протокола**: реализация исполняемого конвейера взаимодействия между агентами. Жестко фиксируются роли, гейты приемки, уровни принятия решений и протокол блокировок (`blocked_protocol`).
3. **Параллельная разработка и масштабирование**: поддержка одновременной работы до 10 агентов-исполнителей под управлением одного агента-архитектора. Внедряются специализированные роли контроллеров и исследователей для реализации сложных проектов (например, игровых продуктов на современных движках).
4. **Телеграм-интерфейс**: подключение Telegram-бота в качестве внешнего канала для отправки коротких текстовых или голосовых задумок. Данный этап реализуется в последнюю очередь, когда стабильность и автономность внутреннего контура полностью доказаны.

### Логика остановки конвейера при сбое тестов

В системе действует бескомпромиссный принцип **"Красный CI — полная остановка конвейера"**:
* При падении любого интеграционного или модульного теста в рамках любой из активных задач (красный статус CI для конкретной задачи) происходит **немедленная полная остановка всей оркестрации конвейера доставки** (hard stop).
* Все параллельно запущенные задачи других исполнителей мгновенно приостанавливаются (переводятся оркестратором в статус `PAUSED` с записью обновленного состояния в файлы задач на диске), а агенты прекращают генерацию кода и выполнение операций.
* Это предотвращает засорение общего репозитория некорректным кодом, исключает появление каскадных ошибок сборки и защищает владельца от неконтролируемого расхода токенов API. Работа возобновляется только после ручного вмешательства пользователя.

### Ключевые принципы

* **Локальность и приватность**: Все данные и кодовая база проекта хранятся и обрабатываются локально.
* **Файловый handoff-протокол**: Взаимодействие агентов осуществляется через неизменяемые JSON-файлы в структурированной директории, что гарантирует устойчивость к сбоям и легкое восстановление состояния сессии.
* **Полная наблюдаемость**: Каждое действие, промпт, ответ модели и запуск тестов логируются и отображаются пользователю в реальном времени через веб-интерфейс (live web feed).
* **Контроль со стороны человека**: Пользователь сохраняет полный контроль, имеет возможность остановить процесс в любой момент времени и вручную скорректировать файлы для снятия блокировок.

## User Roles

Система спроектирована в соответствии с однопользовательской моделью доступа (`single_user`). Внутри системы определены следующие роли:

### Владелец / Оператор (Человек)
* **Наблюдатель**: Отслеживает ход выполнения задач через интерактивную ленту активности в локальном веб-интерфейсе.
* **Контроллер**: Может в любой момент остановить работу конвейера, забрать управление, отредактировать исходный код или конфигурационные файлы.
* **Арбитр блокировок**: Анализирует причины остановок, зафиксированные в файлах `BLOCKED_<taskId>.md`, вносит необходимые правки в код или требования и удаляет файл блокировки для возобновления работы агентов.
* **Администратор системы**: Настраивает локальное окружение, API-ключи и параметры моделей в файле `.env`.

### Агент-Архитектор (ИИ-агент)
* Читает входной спецификационный бандл из Spec Platform.
* Разбивает проект на логические вехи (milestones) и задачи.
* Формирует и записывает структурированные handoff-задания для исполнителей в папку `/handoff/tasks/`.
* Проверяет отчеты исполнителей, анализирует результаты тестирования.
* Проводит автоматический аудит покрытия кода тестами.
* Выполняет процедуру верификации артефактов ("Artifact Walks").
* Принимает работу или возвращает ее на доработку с указанием причин.

### Агенты-Исполнители (ИИ-агенты на базе Claude Code)
* До 10 параллельно запущенных инстансов.
* Считывают персональные handoff-задания из файлов `task_<taskId>.json`.
* Вносят изменения в кодовую базу в изолированном Docker-контейнере (`docker_execution`).
* Пишут модульные (unit) и сквозные (e2e) тесты.
* **Самопроверка**: Самостоятельно запускают тесты в процессе разработки внутри своего контейнера для проверки корректности внесенных изменений перед отправкой отчета.
* Формируют и записывают отчеты в файлы `report_<taskId>.json`.
* При обнаружении непреодолимых препятствий инициируют протокол блокировки (`blocked_protocol`).
* **Технический протокол запуска Claude Code**: Агенты-Исполнители запускаются управляющим оркестратором программно внутри изолированных Docker-контейнеров. Оркестратор вызывает утилиту Claude Code исключительно в неинтерактивном режиме (headless mode).
  * *Целевой (обязательный) подход*: Для автоматического подтверждения изменений и исключения зависания на интерактивных запросах оркестратор обязан использовать встроенные CLI-флаги автоматизации (например, `claude --yes`) и устанавливать переменные окружения автоматического исполнения (например, `CI=true`).
  * *Опциональный подход (на будущее)*: Разработка сложного программного враппера на NodeJS/Python, осуществляющего перехват стандартных потоков ввода-вывода (stdin, stdout, stderr) и динамическую эмуляцию ответов на интерактивные запросы, переносится во внесистемные требования будущих версий и в рамках текущей реализации не выполняется.
* **Технический метод приостановки работы**: Для мгновенной и надежной приостановки выполнения параллельно запущенных задач других исполнителей при возникновении сбоя (переход конвейера в режим паузы) оркестратор производит вызов Docker API `docker pause` (или эквивалентную команду SDK) для заморозки соответствующего изолированного контейнера исполнителя на уровне ядра ОС. Ввиду ограничений целевой ОС Windows на использование POSIX-сигналов (`SIGSTOP`/`SIGCONT`), приостановка работы агентов-исполнителей вне Docker-контейнеров (например, в режиме локальной отладки на хост-системе) не поддерживается; функция приостановки и возобновления работы конвейера доступна исключительно для агентов, запущенных в изолированной среде Docker через вызовы `docker pause` и `docker unpause`.

### Контроллеры и Исследователи (Исполнительные ИИ-агенты)
* **Контроллер**: Выполняет статический анализ кода, проверяет соответствие стандартам кодирования, выявляет синтаксические предупреждения и ошибки форматирования.
* **Исследователь**: Проводит анализ альтернативных архитектурных решений на диске, ищет оптимальные способы реализации задач и предоставляет справочную информацию Архитектору и Исполнителям.

## Functional Requirements

### Локальный однопользовательский режим Spec Platform
* **Локальный запуск**: Запуск всего веб-интерфейса и бэкенда на локальном хосте (`127.0.0.1` или `localhost`) без обращения к внешним SaaS для авторизации и OAuth.
* **Автоматическая сессия**: Автоматический вход локального пользователя с правами Администратора при старте веб-интерфейса.
* **Управление ключами**: Считывание API-ключей (включая Anthropic API Key) напрямую из локального файла `.env`.
* **Локальное хранилище**: Использование SQLite в качестве основной базы данных.

### Кодификация handoff-протокола и управление конвейером
* **Парсинг спецификационного бандла**: Автоматическое считывание файлов из папки `bundle/`: `constitution.md`, `requirements.json`, `architecture.md` и `tasks.json`.
* **Нарезка на вехи (Milestones)**: Агент-Архитектор должен проанализировать зависимости между исходными задачами из бандла и составить последовательный или частично параллельный план выполнения вех.
* **Распределение задач**: Запись файлов заданий по шаблону `task_<taskId>.json` в директорию `/handoff/tasks/`.
* **Мониторинг отчетов**: Периодический опрос (polling) или отслеживание событий файловой системы в папке `/handoff/reports/` для обнаружения файлов `report_<taskId>.json`.

### Распределение ответственности за запуск тестов и валидация гейтов
Процесс верификации разделен на две независимые фазы с четким разграничением зон ответственности:
1. **Фаза разработки (Исполнитель)**: Агент-Исполнитель самостоятельно пишет тесты и запускает их внутри своей изолированной среды в процессе работы над кодом для локального подтверждения работоспособности. По завершении он фиксирует результаты в файле отчета `report_<taskId>.json`.
2. **Фаза приемки результатов (Оркестратор)**: Оркестратор полностью берет на себя выполнение финальных приемочных проверок на гейтах. При обнаружении нового файла отчета `report_<taskId>.json` со статусом `SUCCESS`, оркестратор выполняет следующие действия:
   * Создает абсолютно чистый, изолированный Docker-контейнер.
   * Клонирует/копирует туда актуальное состояние кодовой базы со всеми изменениями Исполнителя.
   * Производит независимый запуск тестов и проверок артефактов ("Artifact Walks").
   * Только результаты проверок оркестратора в этой чистой среде определяют прохождение гейта приемки. Результаты из отчета Исполнителя используются исключительно для информационных целей в веб-интерфейсе.
* **Определение тестовых команд и алгоритм автоматического определения стека (`techStack`)**:
  * Если в файле задачи `task_<taskId>.json` заполнено необязательное поле `unitTestCmd`, оркестратор запускает именно эту команду для прогона модульных тестов. Аналогично для `e2eTestCmd`.
  * Если указанные поля отсутствуют, оркестратор определяет технологический стек задачи. Поиск осуществляется по полю `techStack` в файле задачи.
  * Если поле `techStack` не задано в JSON-файле задачи, оркестратор выполняет **алгоритм автоматического определения стека** путем сканирования файлов в рабочей директории проекта (`workspace`):
    * Наличие файла `package.json` -> устанавливает стек `nodejs`. Дефолтные команды: модульные тесты — `npm test`, сквозные тесты — `npm run test:e2e`.
    * Наличие файлов `requirements.txt` или `pyproject.toml` -> устанавливает стек `python`. Дефолтные команды: модульные тесты — `pytest`, сквозные тесты — `pytest tests/e2e`.
    * Наличие файла `go.mod` -> устанавливает стек `go`. Дефолтные команды: модульные тесты — `go test ./...`, сквозные тесты отсутствуют по умолчанию.
    * Наличие файла `Cargo.toml` -> устанавливает стек `rust`. Дефолтные команды: модульные тесты — `cargo test`, сквозные тесты отсутствуют по умолчанию.
    * Если ни один маркерный файл не обнаружен, стек переводится в статус `generic`. При отсутствии в файле задачи явных команд `unitTestCmd` или `e2eTestCmd` для стека `generic`, оркестратор немедленно завершает верификацию гейта с ошибкой, фиксируя сбой приемки.

* **Проверка артефактов (Artifact Walks)**: Архитектор считывает массив `expectedArtifacts` из файла задачи. Для каждого ожидаемого артефакта оркестратор выполняет запуск команды `validationCmd` с аргументами `validationArgs` внутри Docker-контейнера. Запуск команды `validationCmd` всегда выполняется строго из корня рабочей директории проекта (workspace) внутри Docker-контейнера, после чего вывод процесса валидируется по регулярному выражению `successRegex` для подтверждения успешной работы.

### Параллельная разработка и оркестрация
* **Масштабирование исполнителей**: Поддержка одновременного запуска до 10 независимых агентов Claude Code.
* **Предотвращение конфликтов**: 
  * Агент-Архитектор должен распределять задачи так, чтобы параллельные исполнители не редактировали одни и те же файлы одновременно (определяется по полю `filesToEdit` в задании).
  * Использование транзакционного режима SQLite WAL для предотвращения взаимных блокировок базы данных.

### Обработка блокировок и интермедиация сбоев
* **Активация BLOCKED-протокола (`blocked_protocol`)**:
  * Если исполнитель не может продолжить работу (ошибки в требованиях, неразрешимые конфликты библиотек), он переводит статус задачи в `BLOCKED` (фиксируя это на диске в файле задачи `task_<taskId>.json`) и создает в корне рабочей директории файл `BLOCKED_<taskId>.md` строго по установленному шаблону с подробным описанием проблемы на русском языке.
  * Работа над данной конкретной задачей приостанавливается.
* **Разблокировка пользователем**:
  * Система отслеживает удаление файла `BLOCKED_<taskId>.md` с помощью файлового вотчера (file watcher) или периодического опроса.
  * Как только файл удален пользователем, система считает блокировку снятой, и соответствующий исполнитель автоматически возобновляет работу.
* **Принудительная остановка при сбое тестов (`stop_at_tests`)**:
  * При падении любого теста или ошибке сборки на этапе интеграции в ходе проверки оркестратора на чистом Docker-контейнере, автоматическая работа всего конвейера полностью прекращается (hard stop всей оркестрации).
  * Оркестратор незамедлительно переводит все остальные активные задачи в статус `PAUSED`, фиксирует изменения в файлах задач на диске и замораживает соответствующие им контейнеры Docker через API-вызов `docker pause`.
  * Система переходит в глобальный режим ожидания ручного вмешательства (`manual_file_edit`). Автоматический мерж или коммит сломанного кода строго запрещен.

### Наблюдаемость (Observability) и логирование
* **Лента активности (Live Web Feed)**: Отображение логов всех агентов в реальном времени в локальном веб-интерфейсе.
* **Трассировка решений**: Запись обоснования (Rationale) для каждого изменения архитектуры, добавления библиотек или разбиения задач в базу данных и лог-файлы сессии.

### Телеграм-интерфейс
* **Прием идей**: Интеграция с Telegram Bot API для приема текстовых описаний и голосовых сообщений.
* **Локальная транскрибация**: Преобразование голосовых заметок в текст с использованием локальной модели Whisper или внешнего API (настраивается в `.env`).
* **Инициация контура**: Автоматический вызов API-метода Spec Platform для генерации первичного бандла спецификаций на основе распознанного текста идеи и последующий запуск автономного контура.
* **Уведомления**: Отправка оповещений в Telegram о ключевых событиях (успешное завершение вехи, активация блокировки, критический сбой CI, приведший к полной остановке конвейера).

## Non-Functional Requirements

### Производительность и ресурсы (Performance Targets)
* **Аппаратные ограничения и оптимизация VRAM**: Работа всей системы оптимизирована под одну видеокарту с **16 ГБ VRAM** на Windows.
  * **Рекомендации по моделям**: Для минимизации потребления видеопамяти при локальном исполнении рекомендуется использовать модель `Whisper-base` для транскрибирования аудио и локальные LLM-модели (например, через Ollama) строго в формате **GGUF с квантованием Q4_K_M**.
  * **Исключение автоматического контроля**: Прикладной код ядра системы не выполняет программную проверку и принудительное ограничение выделения VRAM внешними процессами (такими как Ollama, Whisper или Docker). Автоматизированное тестирование этого лимита исключено из приемочных тестов кода; соблюдение лимита VRAM гарантируется соблюдением операционных инструкций по выбору моделей.
* **Время запуска**: Холодный старт локального веб-интерфейса и загрузка состояния из SQLite базы данных должны занимать не более **3 секунд**.
* **Тайм-ауты агентов**: На любую итерацию работы агента-исполнителя (анализ, написание кода, генерация тестов) накладывается жесткий лимит времени — **5 минут**. По истечении тайм-аута сессия агента принудительно прерывается, а задача помечается как `FAILED`.

### Безопасность и изоляция (Security Constraints)
* **Docker-изоляция (`agent_isolation: docker_execution`)**:
  * Весь сгенерированный агентами код, включая установку зависимостей и прогон тестов, должен запускаться исключительно внутри Docker-контейнеров. Прямой запуск на хост-системе Windows запрещен.
* **Интеграция с Docker Desktop на Windows**:
  * Взаимодействие с Docker API должно осуществляться через стандартный именованный канал (named pipe) Windows: `\\.\pipe\docker_engine` (или в формате URI `npipe://./pipe/docker_engine`). Использование сетевых TCP-портов без авторизации запрещено.
  * **Трансляция путей**: При монтировании локальных папок хоста в качестве томов (Volumes) в контейнеры, система должна преобразовывать абсолютные Windows-пути в Unix-формат Docker Desktop: `/<буква_диска>/...`. При этом буква диска обязательно приводится к нижнему регистру, а обратные косые черты `\` заменяются на прямые `/` (например, `C:\Users\Owner\workspace` преобразуется в `/c/Users/Owner/workspace`).
* **Защита секретов**: Файл `.env` должен быть добавлен в `.gitignore`. Запрещено копировать файл `.env` целиком внутрь Docker-контейнеров исполнителей. Передача необходимых токенов должна осуществляться точечно через переменные окружения контейнера под строгим контролем Архитектора.
* **Локальный сетевой контур**: Локальный веб-сервер системы биндится исключительно на loopback-интерфейс `127.0.0.1`. Доступ к панели управления из внешних сетей по умолчанию закрыт.

### Надежность и отказоустойчивость (Reliability & State Recovery)
* **Файловая избыточность и источник правды**: Файлы JSON в директориях `/handoff/tasks/` и `/handoff/reports/` являются первичным и единственным источником правды (Single Source of Truth) для состояния задач и отчетов. Локальная база данных SQLite используется как вспомогательное хранилище для логов, трассировки и обеспечения работы веб-интерфейса. При возникновении расхождений между данными на диске и в базе данных, приоритет всегда отдается файлам на диске. При старте или перезапуске системы база данных SQLite должна принудительно синхронизировать свое состояние с актуальными JSON-файлами на диске. Это гарантирует надежное восстановление конвейера при аварийном завершении работы любого агента или перезапуске системы.
* **Управление транзакциями в БД**: Для предотвращения ошибок блокировки СУБД SQLite при параллельной работе до 10 агентов и веб-интерфейса, база данных должна быть настроена в режиме WAL со временем ожидания не менее 5 секунд.

### Стандарты кодирования (Coding Standards)
* **Форматирование и линтинг**: Любой код, созданный агентами, перед отправкой Архитектору должен быть проверен локальным линтером/форматтером. Наличие синтаксических ошибок или критических предупреждений линтера приравнивается к падению тестов и блокирует приемку задачи.
* **Документирование**: Сложные участки кода должны снабжаться краткими комментариями на русском языке.

## Integration Requirements

### Интеграция со Spec Platform Bundle
Автономный контур считывает и парсит входной бандл спецификаций из папки `bundle/` в корне проекта (`constitution.md`, `requirements.json`, `architecture.md`, `tasks.json`). Структура и схемы валидации файлов зафиксированы в разделе *Data Requirements*.

### Спецификация API Spec Platform для генерации бандла

Интеграция с локальной Spec Platform (запущенной по умолчанию на `http://127.0.0.1:8000`) осуществляется по протоколу HTTP REST. При получении текстовой или голосовой идеи (после транскрибирования), система отправляет POST-запрос на генерацию бандла.

#### Эндпоинт отправки идеи на генерацию
* **Метод:** `POST`
* **Путь:** `/api/spec-platform/generate-bundle`
* **Формат запроса:** `application/json`
* **Тело запроса:**
```json
{
  "projectId": "game-engine-proj-01",
  "ideaText": "Создать текстовый квест на движке с выводом результатов в консоль и ведением логов в JSON",
  "inputType": "TEXT"
}
```
*В случае голосового ввода, предварительно транскрибированный текст передается в поле `ideaText` со значением `inputType` равным `"VOICE"`.*

#### Формат ответа при успешной генерации
* **Код ответа:** `200 OK`
* **Тело ответа:**
```json
{
  "status": "SUCCESS",
  "bundleId": "bundle_98765",
  "bundlePath": "C:\\Users\\Owner\\workspace\\game-engine-proj-01\\bundle",
  "filesGenerated": [
    "constitution.md",
    "requirements.json",
    "architecture.md",
    "tasks.json"
  ]
}
```

#### Альтернативный CLI-интерфейс генерации
В качестве резервного или отладочного метода интеграции поддерживается вызов локальной CLI-утилиты Spec Platform:
```bash
spec-platform-cli generate --project-id "game-engine-proj-01" --idea "Текст идеи" --output-dir "C:\Users\Owner\workspace\game-engine-proj-01\bundle"
```

### Интеграция с Anthropic API и локальными моделями
* **Anthropic API**: Запросы выполняются по протоколу HTTPS к официальному эндпоинту Anthropic. API-ключ извлекается из переменной `ANTHROPIC_API_KEY` в `.env`. Обязательна обработка HTTP-ошибок 429 (Rate Limits) с применением экспоненциальной задержки.
* **Локальные модели**: Запросы отправляются на эндпоинт, указанный в `LOCAL_LLM_API_BASE`. Система эмулирует стандартный протокол чат-завершений OpenAI.

### Интеграция с Docker Engine API
* Управление контейнерами Docker Desktop на Windows осуществляется через named pipe `DOCKER_ENGINE_PIPE` (по умолчанию `\\.\pipe\docker_engine` или в формате URI `npipe://./pipe/docker_engine`).
* При маппинге томов выполняется строгое преобразование путей:
  * Символ диска переводится в нижний регистр.
  * Все обратные слэши `\` заменяются на прямые `/`.
  * Пример: `C:\Users\Owner\workspace` -> `/c/Users/Owner/workspace`.

### Интеграция с Telegram Bot API
* Подключение выполняется по схеме Long Polling с использованием токена из переменной `TELEGRAM_BOT_TOKEN`.
* Бот принимает входящие голосовые сообщения в формате `.ogg` (Opus), скачивает их и передает на локальный сервис транскрибации Whisper по адресу, указанному в переменной `WHISPER_API_BASE`, перед отправкой текста в Spec Platform API.
