## Overview

Автономный контур доставки — это локальная программная экосистема, которая предназначена для автоматического превращения короткой задумки (переданной в виде текста или голоса) в полностью протестированный и готовый к развертыванию программный продукт без обязательного участия человека. 

Входной точкой контура является спецификационный бандл (Bundle), генерируемый Spec Platform, который включает в себя конституцию, требования, архитектуру и задачи. Дальнейший процесс полностью делегируется локальной сети специализированных ИИ-агентов, работающих непосредственно на рабочей станции владельца под управлением ОС Windows с объемом видеопамяти 16 ГБ VRAM.

Для упрощения межпроцессного взаимодействия, обеспечения реактивности интерфейса и надежного совместного использования состояния, вся серверная часть системы (включая API-сервер NextJS и движок оркестратора Orchestrator Engine) запускается в рамках **единого Node.js-процесса (монолитная архитектура)**.

Взаимодействие между агентами, передача задач и отчетность строятся на базе неизменяемых, человекочитаемых файлов на диске (файловый handoff-протокол). Это гарантирует, что состояние системы легко восстанавливается после аварийного завершения работы или перезапуска процессов. Безопасность и предсказуемость кода имеют наивысший приоритет: при падении любого из тестов или возникновении непредвиденной ошибки в процессе выполнения задачи конвейер немедленно останавливается (принцип "Красный CI — полная остановка"), предотвращая каскадную генерацию некорректного кода.

Настоящий документ содержит детальный план реализации, декомпозицию задач и руководство по сборке системы, разбитые на четыре последовательных этапа (Milestones).

## Detailed Tasks

### Milestone 1: Spec Platform Local Core & Web UI

**Цель**: Развернуть локальную монолитную инфраструктуру приложения, настроить безопасную работу с базой данных SQLite в режиме WAL, организовать валидацию конфигурации `.env` и реализовать веб-интерфейс на NextJS для отслеживания состояния контура в реальном времени.

#### Task 1.1: Инициализация БД SQLite в режиме WAL
* **Описание**: Настройка локальной реляционной СУБД SQLite для хранения метаданных проектов, задач, вех, отчетов, трассировки решений и логов.
* **Технические требования**:
  * Инициализировать файл базы данных `local.db` в корневой директории приложения.
  * При создании каждого соединения с базой данных выполнять следующие PRAGMA-инструкции для предотвращения ошибок взаимной блокировки (`database is locked`):
    ```sql
    PRAGMA journal_mode=WAL;
    PRAGMA busy_timeout=5000;
    ```
  * Создать механизм миграций для развертывания схемы таблиц: `projects`, `milestones`, `tasks`, `reports`, `agent_logs`, `agent_decisions` в соответствии со спецификацией `solution.md`.
* **Критерий приемки**: Файл базы данных успешно создается при первом запуске. Тест на конкурентную запись (10 параллельных потоков одновременно пишут логи) проходит без ошибок блокировки базы данных.

#### Task 1.2: Модуль парсинга конфигурации `.env` и секретов
* **Описание**: Реализация безопасного считывания и строгой валидации параметров окружения хоста Windows.
* **Технические требования**:
  * Разработать модуль конфигурации, проверяющий файл `.env` в корне проекта.
  * **Строгая валидация обязательных переменных**: Модуль должен проверять наличие и корректность следующих переменных, необходимых для запуска:
    1. `ANTHROPIC_API_KEY` — строковый ключ доступа к моделям Claude (должен начинаться на `sk-ant-`).
    2. `PORT` — числовое значение порта для запуска локального сервера NextJS.
    3. `WORKSPACE_ROOT_PATH` — валидный абсолютный локальный путь на Windows-хосте, где будут располагаться рабочие каталоги проектов.
  * Все остальные переменные (такие как `LOCAL_LLM_API_BASE`, `TELEGRAM_BOT_TOKEN`, `WHISPER_API_BASE` и др.) валидируются на соответствие форматам только в случае их фактического присутствия в файле.
  * Файл `.env` должен быть в обязательном порядке добавлен в `.gitignore`.
* **Критерий приемки**: При отсутствии или невалидности любой из трех обязательных переменных (`ANTHROPIC_API_KEY`, `PORT`, `WORKSPACE_ROOT_PATH`) монолитный процесс немедленно завершает работу с выводом подробного описания ошибки в stderr.

#### Task 1.3: Однопользовательский веб-интерфейс (NextJS) и монолитная архитектура
* **Описание**: Создание единой кодовой базы (монолита), где API-сервер NextJS и движок оркестратора выполняются в рамках одного процесса Node.js.
* **Технические требования**:
  * Сконфигурировать запуск NextJS на loopback-интерфейсе `127.0.0.1` на порту, указанном в переменной `PORT` файла `.env`.
  * Исключить внешние облачные сервисы авторизации и OAuth: при обращении к страницам интерфейса автоматически авторизовать пользователя как Администратора (авто-сессия владельца).
  * Реализовать дашборд с отображением текущего проекта, статусов вех/задач и интерактивной лентой логов.
  * Интегрировать движок оркестратора непосредственно в жизненный цикл сервера NextJS (например, инициализация синглтона оркестратора при старте кастомного сервера NextJS). Это позволяет напрямую вызывать методы оркестратора и использовать общую шину событий Node.js (Event Emitter).
* **Критерий приемки**: При старте приложения страницы открываются в браузере по адресу `http://127.0.0.1:<PORT>`, вход выполняется автоматически без запроса логина/пароля. Оркестратор запускается внутри того же процесса.

#### Task 1.4: Инфраструктура SSE-стриминга логов (Live Web Feed)
* **Описание**: Реализация механизма передачи логов от оркестратора в веб-интерфейс в реальном времени.
* **Технические требования**:
  * Создать бэкенд-эндпоинт `/api/observability/stream-logs` на базе Server-Sent Events (SSE).
  * Подключить эндпоинт к общей внутренней шине событий (Event Emitter) оркестратора, запущенного в том же Node.js-процессе.
  * Настроить трансляцию поступающих логов из базы данных и потоков stdout/stderr контейнеров агентов подключенным по SSE клиентам.
* **Критерий приемки**: Каждая новая строка лога, сгенерированная оркестратором, мгновенно появляется в окне логов веб-интерфейса без задержек и без выполнения повторных запросов (polling) к базе данных.

### Milestone 2: Файловый handoff-протокол и Оркестратор одиночного цикла

**Цель**: Разработать трансляцию путей, взаимодействие с Docker Desktop на Windows через именованный канал, парсинг спецификационного бандла, автоматическое определение тестового окружения и приемочный гейт с проверкой артефактов.

#### Task 2.1: Модуль трансляции путей Windows-to-Docker
* **Описание**: Реализация алгоритма детерминированного преобразования Windows-путей в Unix-пути для Docker Desktop на Windows.
* **Технические требования**:
  * Создать функцию преобразования абсолютных Windows-путей.
  * Алгоритм преобразования:
    1. Заменить все обратные косые черты `\` на прямые `/`.
    2. Выделить букву диска в начале пути, привести её к нижнему регистру.
    3. Преобразовать путь в формат `/<буква_диска>/...` (например, `C:\Users\Owner\workspace` преобразуется строго в `/c/Users/Owner/workspace`).
* **Критерий приемки**: Функция покрыта юнит-тестами, проверяющими преобразование путей для различных дисков, вложенных папок и путей, содержащих пробелы.

#### Task 2.2: Интеграция с Docker Engine API через Named Pipe
* **Описание**: Организация взаимодействия управляющего процесса оркестратора с Docker Desktop на хост-машине Windows.
* **Технические требования**:
  * Настроить Docker SDK на использование локального именованного канала (Windows named pipe) `\\.\pipe\docker_engine` (или в формате URI `npipe://./pipe/docker_engine`).
  * Реализовать методы создания, запуска, остановки и удаления контейнеров через вызовы Docker API.
* **Критерий приемки**: Тестовый скрипт оркестратора успешно подключается к Docker Desktop, запрашивает список запущенных контейнеров и возвращает результат без сетевых TCP-вызовов.

#### Task 2.3: Headless-запуск Claude Code Wrapper
* **Описание**: Реализация неинтерактивного запуска агента-исполнителя (Claude Code) внутри изолированного контейнера.
* **Технические требования**:
  * Разработать логику запуска контейнера исполнителя в изолированном Docker-окружении (`agent_isolation: docker_execution`).
  * Передавать в контейнер переменную окружения `CI=true` и запускать утилиту Claude Code с флагами автоматизации (например, `claude --yes`), исключающими интерактивные запросы подтверждения изменений.
  * Выполнять монтирование рабочей папки проекта с хоста в контейнер, применяя трансляцию путей из Task 2.1.
* **Критерий приемки**: Оркестратор запускает контейнер, Claude Code успешно вносит изменения в файлы в смонтированной директории и завершает работу без зависания в ожидании ввода пользователя.

#### Task 2.5: Алгоритм автоматического определения тест-стека (`techStack`)
* **Описание**: Разработка модуля автодетекции технологического стека проекта при отсутствии явных параметров в задаче.
* **Технические требования**:
  * Если поле `techStack` не задано в JSON-файле задачи, оркестратор выполняет сканирование рабочей директории проекта `{WORKSPACE_ROOT_PATH}`:
    * Наличие файла `package.json` -> устанавливает стек `nodejs` (команды по умолчанию: модульные тесты — `npm test`, сквозные тесты — `npm run test:e2e`).
    * Наличие `requirements.txt` или `pyproject.toml` -> устанавливает стек `python` (команды по умолчанию: модульные тесты — `pytest`, сквозные тесты — `pytest tests/e2e`).
    * Наличие `go.mod` -> устанавливает стек `go` (команда по умолчанию: `go test ./...`, сквозные отсутствуют).
    * Наличие `Cargo.toml` -> устанавливает стек `rust` (команда по умолчанию: `cargo test`, сквозные отсутствуют).
  * Если ни один маркерный файл не найден, стек устанавливается в `generic`. Если в задаче при этом отсутствуют явные команды тестирования, верификация гейта сразу завершается ошибкой.
  * **Запись на диск**: При автодетекции `techStack` оркестратор **обязан немедленно перезаписать** соответствующий файл `task_<taskId>.json` на диске, добавив туда определенное строковое значение стека. Это гарантирует, что файлы на диске остаются единственным источником правды.
* **Критерий приемки**: Функция автодетекции корректно определяет стек для тестовых папок проектов и перезаписывает JSON-файлы задач на диске, встраивая туда определенные значения `techStack`.

#### Task 2.6: Двухфазная верификация гейтов приемочным оркестратором
* **Описание**: Реализация независимой проверки результатов работы Исполнителя силами оркестратора на хосте.
* **Технические требования**:
  * Оркестратор отслеживает появление отчетов по шаблону `{WORKSPACE_ROOT_PATH}/handoff/reports/report_<taskId>.json`.
  * При обнаружении отчета со статусом `SUCCESS` оркестратор запускает приемочный гейт: разворачивает чистый, изолированный контейнер Docker, копирует туда актуальный код проекта и запускает модульные/сквозные тесты.
  * **Проверка артефактов (Artifact Walks)**: Параметры проверок считываются оркестратором из полей `expectedArtifacts` файла задачи `{WORKSPACE_ROOT_PATH}/handoff/tasks/task_<taskId>.json`. Для каждого артефакта запускается команда `validationCmd` с аргументами `validationArgs` строго из корня рабочей директории внутри Docker-контейнера, после чего вывод процесса (stdout/stderr) валидируется по регулярному выражению `successRegex`.
  * При успешном прохождении проверок оркестратор считывает обоснование архитектурного решения из полей `decisionId`, `decisionTitle` и `rationale` отчета.
  * **Генерация и кодирование MD5**: Если поле `decisionId` не передано явно во входящем файле отчета, оркестратор обязан вычислить его детерминированно как MD5-хеш от конкатенации строк `taskId` и `decisionTitle`. Полученный MD5-хеш должен быть представлен в виде **шестнадцатеричной строки в нижнем регистре (hex-encoded string in lower case)**. Полученные данные записываются в таблицу `agent_decisions` СУБД SQLite.
* **Критерий приемки**: Задача помечается как `COMPLETED` только после прохождения тестов оркестратора в чистом контейнере и успешной валидации артефактов по параметрам из файла задачи. Обоснование решения (Rationale) успешно сохраняется в локальной БД. MD5-хеш генерируется строго в формате hex в нижнем регистре.

#### Task 2.7: Обработка блокировок по протоколу `blocked_protocol`
* **Описание**: Реализация механизма остановки задачи и ожидания действий человека при возникновении тупиковых ситуаций.
* **Технические требования**:
  * Если исполнитель не может выполнить задачу, он переводит статус в `BLOCKED` в файле задачи `{WORKSPACE_ROOT_PATH}/handoff/tasks/task_<taskId>.json` и записывает файл `{WORKSPACE_ROOT_PATH}/BLOCKED_<taskId>.md` в корень рабочей директории по установленному Markdown-шаблону из `requirements.md`.
  * Использовать File Watcher на базе библиотеки `chokidar` для высокопроизводительного мониторинга создания и удаления файлов блокировок в директории `{WORKSPACE_ROOT_PATH}`.
  * Блокировка считается снятой, когда файл `{WORKSPACE_ROOT_PATH}/BLOCKED_<taskId>.md` удаляется пользователем вручную. После этого оркестратор автоматически переводит задачу в статус `PENDING` и возобновляет работу исполнителя.
* **Критерий приемки**: При создании файла `BLOCKED_<taskId>.md` задача переводится в статус `BLOCKED` в UI и оркестратор приостанавливает планирование. При ручном удалении этого файла система фиксирует изменение в течение 1 секунды и автоматически перезапускает исполнителя.

### Milestone 3: Параллелизм, координация и "Красный CI"

**Цель**: Реализовать параллельную работу до 10 агентов без взаимных блокировок и конфликтов файлов, механизм аварийной остановки "Красный CI" с заморозкой контейнеров, вспомогательные роли агентов, автоматическое восстановление состояния из файлов при старте и скрипт контроля VRAM.

#### Task 3.1: Параллельный планировщик задач
* **Описание**: Разработка планировщика оркестратора для распределения задач между параллельными контейнерами исполнителей.
* **Технические требования**:
  * Планировщик должен поддерживать одновременную работу до 10 контейнеров исполнителей.
  * **Предотвращение файловых коллизий**: Перед запуском задачи планировщик считывает обязательный массив `filesToEdit` напрямую из файла задачи `{WORKSPACE_ROOT_PATH}/handoff/tasks/task_<taskId>.json`. Если файлы из этого массива пересекаются с файлами уже запущенных задач, планировщик откладывает старт текущей задачи.
* **Критерий приемки**: Неконфликтующие задачи выполняются параллельно в независимых контейнерах. Задачи с пересекающимися файлами в массиве `filesToEdit` ожидают своей очереди.

#### Task 3.2: Механизм приостановки и выхода из режима "Красный CI"
* **Описание**: Реализация экстренной остановки всей оркестрации при сбое любого интеграционного или модульного теста на этапе приемочной верификации, с возможностью ручного возобновления работы.
* **Технические требования**:
  * При падении теста оркестратор немедленно останавливает конвейер: все остальные активные задачи переводятся в статус `PAUSED` в файлах `{WORKSPACE_ROOT_PATH}/handoff/tasks/task_<taskId>.json` на диске.
  * Для мгновенной приостановки запущенных контейнеров исполнителей оркестратор выполняет вызов Docker API `docker pause` для контейнеров с именами вида `delivery-executor-${taskId}`.
  * **Управляющий эндпоинт**: Создать на сервере оркестратора (в рамках того же монолитного Node.js-процесса) выделенный API-эндпоинт управления `POST /api/orchestrator/retry` для обработки запроса повторного запуска.
  * При вызове эндпоинта оркестратор выполняет операцию `docker unpause` для замороженных контейнеров, сбрасывает статусы приостановленных задач на диске и в СУБД на `IN_PROGRESS` или `PENDING`, возобновляя проверки.
* **Критерий приемки**: При падении теста все контейнеры замораживаются в течение 1 секунды. Вызов эндпоинта `POST /api/orchestrator/retry` из веб-интерфейса успешно возобновляет работу конвейера и повторно запускает тесты.

#### Task 3.3: Интеграция вспомогательных агентов (Контроллеры и Исследователи)
* **Описание**: Внедрение системных ролей для статического анализа и поиска решений без создания тяжелых дополнительных контейнеров Docker (для экономии VRAM).
* **Технические требования**:
  * Контроллеры и Исследователи выполняются как точечные неинтерактивные LLM-запросы непосредственно из процесса оркестратора на хосте.
  * Агент-контроллер запускает линтеры и форматтеры внутри контейнера исполнителя:
    * `nodejs` -> `eslint --fix` и `prettier --check`
    * `python` -> `flake8` и `black --check`
    * `go` -> `go fmt` и `go vet`
    * `rust` -> `cargo fmt --check` и `cargo clippy`
  * Если обнаружены синтаксические предупреждения или ошибки форматирования, Контроллер бракует задачу до этапа тестов и возвращает ее исполнителю.
  * Агент-исследователь осуществляет навигацию по репозиторию, формирует структурированный контекстный JSON-отчет по структуре файлов проекта и передает его оркестратору для последующей отправки Архитектору.
* **Критерий приемки**: Ошибки форматирования или синтаксиса в измененных файлах приводят к автоматическому возврату задачи исполнителю на доработку без запуска тестов.

#### Task 3.4: Восстановление состояния из файлов на диске при старте (Шаг 0)
* **Описание**: Реализация отказоустойчивости системы и автоматической синхронизации базы данных SQLite с диском при перезапуске.
* **Технические требования**:
  * При старте оркестратор сканирует директорию `{WORKSPACE_ROOT_PATH}/handoff/tasks/`.
  * **Шаг 0: Предотвращение сбоев внешнего ключа**. Прежде чем импортировать вехи и задачи, оркестратор считывает `projectId` из файла `milestones.json` на диске. Если запись проекта в таблице `projects` СУБД SQLite отсутствует, оркестратор обязан автоматически выполнить вставку записи проекта по умолчанию:
    ```sql
    INSERT OR REPLACE INTO projects (project_id, title, description, status) 
    VALUES (:projectId, 'Восстановленный проект ' || :projectId, 'Автоматически восстановленный проект на основе резервной копии на диске', 'ACTIVE');
    ```
  * **Шаг 1: Восстановление вех**. Считывание файла `/handoff/tasks/milestones.json` и восстановление записей в таблице `milestones`.
  * **Шаг 2: Восстановление задач**. Считывание файлов задач `task_*.json` из папки `/handoff/tasks/` и импорт в таблицу `tasks`.
  * **Коррекция и автодетект отсутствующего поля `techStack`**: Если в восстанавливаемом с диска файле `task_*.json` отсутствует поле `techStack` (например, файл был отредактирован пользователем вручную и поле было утеряно), оркестратор **обязан повторно запустить алгоритм автоматического определения стека (Task 2.5)** для данного проекта непосредственно перед сохранением записи в таблицу `tasks` SQLite, чтобы избежать ошибок целостности базы данных (`NOT NULL constraint failed`).
* **Критерий приемки**: Полное удаление файла `local.db` и последующий старт оркестратора приводят к успешному автоматическому пересозданию базы данных, генерации записи проекта, импорту вех и импорту всех задач без ошибок ограничений внешних ключей и без падений на пустых полях `techStack`.

#### Task 3.5: Автоматический аудит использования VRAM в CI
* **Описание**: Реализация автоматизированного контроля за лимитом выделения видеопамяти при локальном прогоне тестов.
* **Технические требования**:
  * Интегрировать скрипт автоматического аудита `vram_monitor.ps1` (из спецификации `solution.md`) в приемочный тестовый цикл.
  * Скрипт должен опрашивать утилиту `nvidia-smi` каждые 500 мс во время выполнения сквозного E2E-теста работы сети агентов.
  * Скрипт осуществляет сбор метрик в фоновом режиме, а по завершении тестов считывает пиковое значение занятой видеопамяти, приводя результат к целочисленному значению `[int]` для надежного арифметического сравнения.
  * Если пиковое значение VRAM превышает установленный лимит в 12 ГБ (12288 МБ), скрипт принудительно завершает работу с кодом `exit 1`.
* **Критерий приемки**: Запуск E2E-тестов в CI-окружении успешно завершается; скрипт мониторинга корректно фиксирует пиковое потребление видеопамяти и подтверждает соблюдение лимита в 12 ГБ VRAM.

### Milestone 4: Телеграм-интерфейс и локальный Whisper

**Цель**: Реализовать интерфейс Telegram-бота для удаленного управления контуром доставки, добавить локальное распознавание голосовых заметок и интегрировать автоматический вызов генератора бандлов Spec Platform.

#### Task 4.1: Телеграм-бот на базе Long Polling
* **Описание**: Создание русскоязычного интерфейса Telegram-бота для приема текстовых и голосовых идей от владельца.
* **Технические требования**:
  * Настроить подключение к Telegram API по схеме Long Polling с использованием токена из переменной `TELEGRAM_BOT_TOKEN`.
  * Бот должен обрабатывать входящие сообщения строго от пользователя с идентификатором `TELEGRAM_OWNER_CHAT_ID`. Запросы от сторонних пользователей должны игнорироваться.
* **Критерий приемки**: Бот успешно запускается, реагирует на текстовые сообщения владельца приветственным сообщением на русском языке и игнорирует сообщения от других аккаунтов.

#### Task 4.2: Конвертация аудио и транскрибация голосовых заметок Whisper
* **Описание**: Локальное распознавание голосовых сообщений, присланных в Telegram.
* **Технические требования**:
  * При получении голосового сообщения (в формате `.ogg` / Opus) бот скачивает его файл с серверов Telegram.
  * Выполнить автоматическую конвертацию аудиофайла `.ogg` в формат `.wav` (PCM 16-bit, 16000Hz, mono) с помощью встроенной библиотеки-обертки `fluent-ffmpeg` (требует установленного ffmpeg в системе).
  * Отправить сконвертированный файл `.wav` POST-запросом на адрес локального Whisper-совместимого API, указанного в переменной `WHISPER_API_BASE` в `.env`.
* **Критерий приемки**: Отправка голосового сообщения в Telegram приводит к его автоматической конвертации на хосте, успешной транскрибации через Whisper-API и выводу распознанного русского текста в ответном сообщении бота.

#### Task 4.3: Интеграция API генерации бандла Spec Platform
* **Описание**: Интеграция шлюза Telegram с эндпоинтом Spec Platform для запуска генерации бандла.
* **Технические требования**:
  * После успешного получения текста идеи (напрямую или из голосового Whisper-сообщения) отправить REST-запрос `POST /api/spec-platform/generate-bundle` на сервер Spec Platform.
  * Тело запроса и ответ должны строго соответствовать схемам, описанным в `requirements.md`.
  * При успешном завершении генерации бандла запустить автоматический цикл оркестратора через вызов `POST /api/orchestrator/start-loop`.
* **Критерий приемки**: Распознанный текст идеи автоматически передается в Spec Platform, которая генерирует файлы бандла спецификаций на диске. Оркестратор фиксирует создание бандла и автоматически инициирует новую веху разработки.

#### Task 4.4: Модуль оповещений в Telegram (Telegram Alerts)
* **Описание**: Реализация русскоязычных уведомлений в чат владельца о ключевых событиях контура.
* **Технические требования**:
  * Настроить отправку структурированных сообщений через Telegram Bot API по следующим триггерам событий оркестратора:
    * Инициализация нового проекта и нарезка вех.
    * Переход задачи в статус `BLOCKED` с отправкой текста проблемы из файла `BLOCKED_<taskId>.md`.
    * Критический сбой CI (Красный CI) с сообщением о полной остановке конвейера и приостановке всех задач.
    * Успешное прохождение всех приемочных гейтов и завершение проекта.
* **Критерий приемки**: При возникновении блокировки или падении теста владелец мгновенно получает детальное русскоязычное уведомление в Telegram с описанием ошибки.

## Risks & Sequencing Notes

### Технические риски и стратегии их минимизации

1. **Конфликты блокировок SQLite (`database is locked`)**:
   При пиковой нагрузке (10 параллельных исполнителей пишут логи, а пользователь обновляет интерфейс) SQLite может временно заблокировать файл.
   * *Решение*: Использование режима WAL (`PRAGMA journal_mode=WAL`) и установка таймаута ожидания блокировки не менее 5000 мс (`PRAGMA busy_timeout=5000`) на уровне пула соединений.

2. **Зависание Claude Code во внутриконтейнерной среде**:
   CLI Claude Code может ожидать интерактивного подтверждения изменений (Y/n) или ввода логина, что приведет к исчерпанию 5-минутного тайм-аута.
   * *Решение*: Принудительная установка переменной окружения `CI=true` и передача флага автоматического согласия `--yes`. Логирование stdout/stderr в реальном времени для аудита зависаний.

3. **Несовместимость форматов аудио в Whisper**:
   Telegram присылает голосовые сообщения в формате `.ogg` (Opus), в то время как локальные реализации Whisper (например, Whisper-совместимые API) часто требуют традиционные контейнеры (`.wav` или `.mp3`).
   * *Решение*: Внедрение обязательной предварительной конвертации аудио на хосте с использованием библиотеки `fluent-ffmpeg` перед отправкой HTTP-запроса на транскрибацию.

4. **Нарушение ограничений внешнего ключа при восстановлении БД с диска**:
   При запуске системы с пустой базой данных SQLite сканирование и импорт задач `task_*.json` завершатся ошибкой `FOREIGN KEY constraint failed`, так как в базе еще нет записи проекта с соответствующим `projectId`.
   * *Решение*: Реализация строгого Шага 0 в процедуре инициализации, создающего запись проекта с дефолтными значениями до импорта вех и задач.

### Очередность и этапы сборки системы (Sequencing Notes)

Разработка строго следует линейной последовательности вех от Milestone 1 до Milestone 4. Любое нарушение порядка приведет к интеграционным тупикам:

1. **Milestone 1** должен выполняться самым первым, поскольку он создает хост-окружение монолитного процесса, запускает локальную базу данных SQLite в режиме WAL, настраивает валидацию секретов в `.env` и разворачивает веб-интерфейс NextJS. Без этой основы невозможно логировать и отслеживать последующую работу оркестратора.
2. **Milestone 2** надстраивается над базой и веб-интерфейсом. Он вводит низкоуровневые механизмы интеграции с Docker Desktop на Windows через Named Pipe, реализует файловый handoff-протокол обмена задачами и отчетами, а также создает приемочный гейт с проверкой тестов и верификацией артефактов (Artifact Walks) для одной изолированной задачи.
3. **Milestone 3** масштабирует оркестратор одиночного цикла до сложного многоагентного планировщика. Здесь внедряется параллельная работа до 10 агентов с предотвращением коллизий по `filesToEdit`, подключаются роли Контроллеров и Исследователей, настраивается механизм экстренной остановки ("Красный CI") с использованием системных вызовов `docker pause` / `docker unpause` для заморозки контейнеров, реализуется отказоустойчивое восстановление состояния с диска (Шаг 0) и интегрируется автоматический аудит лимита VRAM.
4. **Milestone 4** подключается на финальном этапе, когда стабильность, безопасность и автономность внутреннего контура доставки на хост-системе полностью доказаны и верифицированы. Он открывает внешний сетевой канал взаимодействия через Telegram-бота и локальный Whisper для удаленного управления и передачи идей голосом.
