## Overview

**Автономный контур доставки** — это локальная программная экосистема, которая преобразует короткую задумку (переданную текстом или голосом) в полностью протестированный и готовый к развертыванию программный продукт без обязательного участия человека. 

Входной точкой контура является спецификационный бандл (Bundle), генерируемый Spec Platform, который включает в себя конституцию, требования, архитектуру и задачи. Дальнейший процесс полностью делегируется локальной сети специализированных ИИ-агентов, работающих непосредственно на рабочей станции владельца под управлением ОС Windows.

### Фазы развития проекта

Развитие проекта разделено на четыре ключевых этапа:
1. **Локальный однопользовательский режим Spec Platform**: развертывание и функционирование всего веб-интерфейса и бэкенда на локальной машине пользователя без зависимости от внешних облачных провайдеров авторизации (без OAuth), с локальной базой данных SQLite и гибким выбором моделей (локальных через Ollama или облачных через API-ключи в `.env`).
2. **Кодификация handoff-протокола**: реализация исполняемого конвейера взаимодействия на базе файлового обмена, где жестко зафиксированы роли (Архитектор, Исполнитель), гейты приемки, уровни принятия решений и протокол блокировок (`blocked_protocol`). Действует бескомпромиссный принцип: «Красный CI — полная остановка всей оркестрации».
3. **Параллельная разработка и масштабирование**: поддержка одновременной работы до 10 агентов-исполнителей под управлением одного агента-архитектора. Для сложных проектов (уровня игровых продуктов на современных движках) внедряются дополнительные роли — контроллеры и исследователи.
4. **Телеграм-интерфейс**: подключение Telegram-бота в качестве внешнего канала для отправки коротких текстовых или голосовых задумок. Данный этап реализуется в последнюю очередь, когда стабильность и автономность внутреннего контура полностью доказаны на практике.

### Логика остановки конвейера при сбое тестов

В системе действует бескомпромиссный принцип **«Красный CI — полная остановка конвейера»**:
* При падении любого интеграционного или модульного теста в рамках любой из активных задач (красный статус CI для конкретной задачи) происходит **немедленная полная остановка всей оркестрации конвейера доставки** (hard stop).
* Все параллельно запущенные задачи других исполнителей мгновенно приостанавливаются (переводятся оркестратором в статус `PAUSED` с записью обновленного состояния в файлы задач на диске), а агенты прекращают генерацию кода и выполнение операций.
* Это предотвращает засорение общего репозитория некорректным кодом, исключает появление каскадных ошибок сборки и защищает владельца от неконтролируемого расхода токенов API. Работа возобновляется только после ручного вмешательства пользователя.

### Ключевые принципы

* **Локальность и приватность**: Все данные и кодовая база проекта хранятся и обрабатываются локально.
* **Файловый handoff-протокол**: Взаимодействие агентов осуществляется через неизменяемые JSON-файлы в структурированной директории, что гарантирует устойчивость к сбоям и легкое восстановление состояния сессии.
* **Полная наблюдаемость**: Каждое действие, промпт, ответ модели и запуск тестов логируются и отображаются пользователю в реальном времени через веб-интерфейс (live web feed).
* **Контроль со стороны человека**: Пользователь сохраняет полный контроль, имеет возможность остановить процесс в любой момент времени и вручную скорректировать файлы для снятия блокировок.

## High-Level Architecture Design

Архитектура системы спроектирована с учетом жестких аппаратных ограничений локальной рабочей станции Windows, лимитов видеопамяти (16 ГБ VRAM) и требований к надежности (устойчивость к сбоям за счет файловой синхронизации).

### Архитектурные компоненты и их взаимодействие

Вся координация между агентами построена на основе распределенного конвейера с файловой синхронизацией. Локальный веб-интерфейс Spec Platform общается с бэкендом оркестратора через локальный REST API. Оркестратор управляет жизненным циклом агентов, запускаемых в изолированных Docker-контейнерах, посредством Docker Engine API через именованный канал Windows.

```
+---------------------------------------------------------------------------------+
|                                 Windows Host                                    |
|                                                                                 |
|  +--------------------------+                 +------------------------------+  |
|  |     Spec Platform        |                 |      Orchestrator Engine     |  |
|  | (Local Web UI, sqlite-db)| <=============> |  (State Machine, Scheduler,  |  |
|  |   127.0.0.1:3000 / 8000  |  Local REST API |   File Watcher, Log Stream)  |  |
|  +--------------------------+                 +------------------------------+  |
|               ^                                             ||                  |
|               | (Чтение Bundle)                             || (Управление)     |
|               v                                             v                   |
|  +---------------------------------------------------------------------------+  |
|  | Local Workspace (Single Source of Truth)                                  |  |
|  |                                                                           |  |
|  |  /bundle/                  /handoff/tasks/         /handoff/reports/      |  |
|  |  [const., reqs., tasks]    [task_*.json]           [report_*.json]        |  |
|  +---------------------------------------------------------------------------+  |
|               ^                                             ||                  |
|               | (Монтирование томов)                        || Docker API       |
|               v                                             v (Named Pipe)      |
|  +---------------------------------------------------------------------------+  |
|  | Docker Desktop Sandbox Isolation                                          |  |
|  |                                                                           |  |
|  |  +---------------------------+           +------------------------------+ |  |
|  |  | Container: Architect      |           | Containers: Claude Code      | |  |
|  |  | (Planning, Code Review)   |           | (Executors 1..10, Headless)  | |  |
|  |  +---------------------------+           +------------------------------+ |  |
|  +---------------------------------------------------------------------------+  |
|                                                                                 |
+---------------------------------------------------------------------------------+
```

### Принцип «Файловый handoff-протокол как Single Source of Truth»

База данных SQLite используется исключительно как индекс состояний для ускорения работы Web UI, кэширования логов и вывода аналитики. Первичным и единственным источником правды о состоянии задач, вех и отчетов всегда является файловая система рабочей директории `workspace`. 

При старте или перезапуске системы оркестратор сканирует конфигурационный файл вех `/handoff/tasks/milestones.json`, директорию задач `/handoff/tasks/` и директорию отчетов `/handoff/reports/` и принудительно синхронизирует базу данных. Любое падение процесса, отключение питания или сбой LLM-провайдера не приводит к потере состояния. Конвейер возобновляет работу с той точки, на которой был сохранен последний валидный JSON-файл на диске.

### Стратегия работы в условиях 16 ГБ VRAM

Для предотвращения исчерпания видеопамяти на хост-системе Windows:
* Основной объем ресурсоемких рассуждений (генерация кода, планирование Архитектора) делегируется облачным моделям Anthropic Claude через API-ключи.
* Локальные модели запускаются через внешнюю утилиту Ollama. Для локальных нужд анализа используются квантованные модели GGUF (например, `llama3:8b` в формате `Q4_K_M`), потребляющие не более 6–8 ГБ VRAM.
* Выгрузка локальной модели транскрипции Whisper-base из видеопамяти полностью возлагается на настройки самого стороннего сервера (например, параметры `idle timeout` и авторазгрузки в whisper.cpp или faster-whisper, на котором запущен Whisper-совместимый API). Оркестратор взаимодействует с сервером по HTTP REST и не управляет процессом Whisper (start/kill) напрямую. Это сохраняет архитектуру оркестратора простой и защищает от конфликтов управления процессами.
* Оставшиеся ресурсы VRAM резервируются под графическую подсистему Windows и нужды Docker Desktop.

## System Modules

### 1. Spec Platform Local Core (Локальное ядро)
Обеспечивает пользовательский интерфейс и базовое управление спецификациями.
* **Local Web UI**: Однопользовательская веб-панель (React/Node.js), автоматически авторизующая пользователя как Администратора при запуске. Предоставляет доступ к конфигурации проекта, ленте активности в реальном времени и инструментам ручного снятия блокировок.
* **Bundle Generator**: Модуль парсинга требований и генерации исходного бандла. На основе короткой задумки формирует директорию `/bundle/` с файлами `constitution.md`, `requirements.json`, `architecture.md` и `tasks.json`.

### 2. Orchestrator Engine (Оркестратор конвейера)
Ядро управления автономным циклом, написанное на TypeScript/Node.js.
* **State Machine & Scheduler**: Планировщик, распределяющий неконфликтующие задачи между свободными контейнерами исполнителей. На основе поля `filesToEdit` в заданиях планировщик гарантирует, что два параллельных исполнителя не будут одновременно изменять одни и те же файлы.
* **File Watcher**: Высокопроизводительный мониторинг файловой системы в рабочей директории на базе библиотеки `chokidar`. Отслеживает появление отчетов `report_*.json`, файлов блокировок `BLOCKED_*.md` и ручные изменения исходного кода.
* **Docker Container Controller**: Обертка над Docker Engine API, управляющая жизненным циклом контейнеров агентов через именованный канал Windows. Выполняет создание, запуск, приостановку (`docker pause`) и возобновление (`docker unpause`) контейнеров.

### 3. Multi-Agent Network (Сеть агентов)
* **Agent-Architect**: Высокоуровневый агент, работающий с API Anthropic. Отвечает за декомпозицию исходного бандла на вехи, создание файлов `task_*.json` и `milestones.json`, проверку входящих отчетов и проведение финального аудита кода («Artifact Walks»).
* **Agent-Executor (Claude Code Wrapper)**: Обертка вокруг CLI-инструмента Claude Code. Запускается внутри контейнера с переменной окружения `CI=true` и флагом `--yes` для автоматического применения изменений без интерактивного подтверждения (headless mode).
* **Controllers & Researchers**: Специализированные системные агенты. Контроллер осуществляет статический анализ и запускает линтеры на измененных файлах. Исследователь осуществляет навигацию по репозиторию, ищет зависимости и предоставляет контекстные справки Архитектору.

### 4. Integration & Notification Gateway (Шлюз интеграций)
* **Telegram Bot Client**: Клиент, работающий по схеме Long Polling, принимающий идеи пользователя и отправляющий статусы выполнения и экстренные оповещения.
* **Whisper Transcriber**: Коннектор к локальному или облачному API Whisper для преобразования входящего аудио в текст.

## Data Model

Локальная СУБД SQLite спроектирована по реляционной схеме. Для предотвращения взаимных блокировок базы данных при одновременной работе до 10 агентов-исполнителей, архитекторов и веб-интерфейса, СУБД SQLite при инициализации соединения настраивается в режиме WAL.

### Параметры конфигурации SQLite
```sql
PRAGMA journal_mode=WAL;
PRAGMA busy_timeout=5000;
```

### Схема таблиц базы данных

```sql
-- Таблица проектов
CREATE TABLE projects (
    project_id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    description TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status TEXT NOT NULL CHECK (status IN ('ACTIVE', 'PAUSED', 'COMPLETED', 'FAILED'))
);

-- Таблица вех (Milestones)
CREATE TABLE milestones (
    milestone_id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    title TEXT NOT NULL,
    description TEXT,
    depends_on TEXT, -- JSON-массив ID зависимых вех
    status TEXT NOT NULL CHECK (status IN ('PENDING', 'IN_PROGRESS', 'COMPLETED', 'FAILED')),
    FOREIGN KEY(project_id) REFERENCES projects(project_id) ON DELETE CASCADE
);

-- Таблица задач
CREATE TABLE tasks (
    task_id TEXT PRIMARY KEY,
    milestone_id TEXT NOT NULL,
    title TEXT NOT NULL,
    description TEXT NOT NULL,
    tech_stack TEXT NOT NULL CHECK (tech_stack IN ('nodejs', 'python', 'go', 'rust', 'generic')),
    files_to_edit TEXT NOT NULL, -- JSON-массив путей к файлам
    unit_test_cmd TEXT,
    e2e_test_cmd TEXT,
    expected_artifacts TEXT NOT NULL, -- JSON-массив ожидаемых артефактов
    status TEXT NOT NULL CHECK (status IN ('PENDING', 'IN_PROGRESS', 'COMPLETED', 'FAILED', 'BLOCKED', 'PAUSED')),
    FOREIGN KEY(milestone_id) REFERENCES milestones(milestone_id) ON DELETE CASCADE
);

-- Таблица отчетов об исполнении
CREATE TABLE reports (
    report_id TEXT PRIMARY KEY,
    task_id TEXT NOT NULL,
    executor_id TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('SUCCESS', 'FAILED', 'BLOCKED')),
    tests_total INTEGER DEFAULT 0,
    tests_passed INTEGER DEFAULT 0,
    tests_failed INTEGER DEFAULT 0,
    errors TEXT, -- JSON-массив строк ошибок
    block_reason TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(task_id) REFERENCES tasks(task_id) ON DELETE CASCADE
);

-- Таблица логов агентов (для Live Web Feed)
CREATE TABLE agent_logs (
    log_id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id TEXT NOT NULL,
    task_id TEXT,
    agent_role TEXT NOT NULL, -- ARCHITECT, EXECUTOR, CONTROLLER, RESEARCHER
    message TEXT NOT NULL,
    log_level TEXT NOT NULL, -- INFO, WARN, ERROR, DEBUG
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(project_id) REFERENCES projects(project_id) ON DELETE CASCADE,
    FOREIGN KEY(task_id) REFERENCES tasks(task_id) ON DELETE CASCADE
);

-- Таблица трассировки решений (Rationale)
CREATE TABLE agent_decisions (
    decision_id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    task_id TEXT,
    title TEXT NOT NULL,
    rationale TEXT NOT NULL, -- Обоснование принятого решения
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(project_id) REFERENCES projects(project_id) ON DELETE CASCADE,
    FOREIGN KEY(task_id) REFERENCES tasks(task_id) ON DELETE CASCADE
);
```

### Синхронизация вех (Milestones) и предотвращение ошибок внешнего ключа

Для исключения ошибок нарушения целостности базы данных (`FOREIGN KEY constraint failed`) при сбросе или синхронизации СУБД с диска, метаданные вех (название, описание, зависимости) в обязательном порядке кодифицируются на диске.

#### Процедура восстановления таблицы projects при импорте вех

При старте или процедуре восстановления состояния оркестратор выполняет операцию импорта в три шага:

1. **Шаг 0: Восстановление записи проекта**. Прежде чем импортировать вехи из `milestones.json`, оркестратор считывает `projectId` из файла `milestones.json` и проверяет наличие соответствующей записи в таблице `projects`. Если запись отсутствует, оркестратор выполняет предварительный запрос для автоматического создания записи проекта на основе метаданных из бандла или значений по умолчанию:
   ```sql
   INSERT OR REPLACE INTO projects (project_id, title, description, status) 
   VALUES (:projectId, 'Восстановленный проект ' || :projectId, 'Автоматически восстановленный проект на основе резервной копии на диске', 'ACTIVE');
   ```
   Это гарантирует, что при пустой базе данных (например, после удаления файла SQLite) создание родительской записи проекта происходит до импорта зависимых таблиц, что предотвращает ошибку нарушения ограничений внешнего ключа (`FOREIGN KEY constraint failed`).

2. **Шаг 1: Восстановление вех**. Оркестратор считывает файл `/handoff/tasks/milestones.json`, парсит его и полностью восстанавливает записи в таблице `milestones`.
   Шаблон файла `/handoff/tasks/milestones.json`:
   ```json
   {
     "projectId": "isometric-game-01",
     "milestones": [
       {
         "milestoneId": "ms_01",
         "title": "Инициализация проекта и базовый рендеринг",
         "description": "Настройка структуры проекта и вывод базовой сетки canvas",
         "dependsOn": []
       },
       {
         "milestoneId": "ms_02",
         "title": "Игровая логика и управление",
         "description": "Реализация управления персонажем через WASD",
         "dependsOn": ["ms_01"]
       }
     ]
   }
   ```

3. **Шаг 2: Восстановление задач**. Только после успешного завершения Шага 1 оркестратор приступает к сканированию папки `/handoff/tasks/` для импорта файлов задач `task_*.json` в таблицу `tasks`.

#### Предотвращение дублирования решений в `agent_decisions`

Для предотвращения дублирования записей при повторном сканировании или обновлении файлов отчетов `report_*.json`, в структуре файлов отчетов предусмотрено обязательное поле `decisionId`. При импорте отчетов оркестратор использует SQL-команду слияния (`INSERT OR REPLACE`):

```sql
INSERT OR REPLACE INTO agent_decisions (decision_id, project_id, task_id, title, rationale, created_at)
VALUES (:decisionId, :projectId, :taskId, :decisionTitle, :rationale, CURRENT_TIMESTAMP);
```

Если поле `decisionId` отсутствует во входящем файле отчета, оркестратор вычисляет его детерминированно с использованием алгоритма хеширования (например, MD5 от конкатенации `taskId` и `decisionTitle`), что обеспечивает уникальный и воспроизводимый идентификатор для каждой уникальной записи архитектурного решения.

## API / Protocol Design

### Спецификация API локального взаимодействия (REST)

#### 1. POST `/api/spec-platform/generate-bundle`
Принимает текстовую или голосовую идею пользователя и инициирует создание спецификационного бандла.
* **Request Body**:
```json
{
  "projectId": "game-engine-proj-01",
  "ideaText": "Создать текстовый квест на движке с выводом результатов в консоль и ведением логов в JSON",
  "inputType": "TEXT"
}
```
* **Response 200 OK**:
```json
{
  "status": "SUCCESS",
  "bundleId": "bundle_98765",
  "bundlePath": "C:\\Users\\Owner\\workspace\\game-engine-proj-01\\bundle",
  "filesGenerated": [
    "constitution.md",
    "requirements.json",
    "architecture.md",
    "tasks.json"
  ]
}
```

#### 2. POST `/api/orchestrator/start-loop`
Запуск автоматического конвейера доставки по сгенерированному бандлу.
* **Request Body**:
```json
{
  "projectId": "game-engine-proj-01",
  "bundlePath": "C:\\Users\\Owner\\workspace\\game-engine-proj-01\\bundle"
}
```
* **Response 200 OK**:
```json
{
  "status": "IN_PROGRESS",
  "message": "Orchestrator successfully parsed spec bundle and initialized State Machine"
}
```

### Файловый handoff-протокол

Файловый обмен является единственным контрактом синхронизации между агентом-архитектором и исполнителями.

#### Схема задачи (`task_schema.json`)
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "HandoffTask",
  "type": "object",
  "properties": {
    "taskId": { "type": "string" },
    "milestoneId": { "type": "string" },
    "title": { "type": "string" },
    "description": { "type": "string" },
    "techStack": {
      "type": "string",
      "enum": ["nodejs", "python", "go", "rust", "generic"]
    },
    "filesToEdit": {
      "type": "array",
      "items": { "type": "string" }
    },
    "unitTestCmd": { "type": "string" },
    "e2eTestCmd": { "type": "string" },
    "expectedArtifacts": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "path": { "type": "string" },
          "validationCmd": { "type": "string" },
          "validationArgs": {
            "type": "array",
            "items": { "type": "string" }
          },
```

#### Алгоритм Windows-to-Docker трансляции путей

Оркестратор на хосте Windows выполняет строго детерминированное преобразование путей при монтировании локальных папок хоста в тома (Volumes) контейнеров Linux (WSL2):

```typescript
function translateWindowsPathToDocker(windowsPath: string): string {
    // 1. Замена обратных слэшей на прямые
    let resolvedPath = windowsPath.replace(/\\/g, '/');
    
    // 2. Поиск буквы диска в начале пути (например, C:/)
    const driveLetterRegex = /^([a-zA-Z]):/;
    const match = resolvedPath.match(driveLetterRegex);
    
    if (match) {
        const driveLetter = match[1].toLowerCase();
        resolvedPath = resolvedPath.replace(driveLetterRegex, `/${driveLetter}`);
    }
    
    return resolvedPath;
}
// Пример: "C:\Users\Owner\workspace\project1" -> "/c/Users/Owner/workspace/project1"
```

## Security Architecture

Безопасность локальной среды пользователя является абсолютным приоритетом при проектировании контура.

### Изоляция исполнения (`agent_isolation: docker_execution`)

Все действия по сборке кода, установке зависимостей и запуску тестов происходят исключительно внутри изолированных Docker-контейнеров. Прямой запуск недоверенного кода на хост-системе Windows строго запрещен.

### Сопряжение с Docker Desktop на Windows

* Взаимодействие бэкенда с Docker API осуществляется через стандартный именованный канал Windows: `\\.\pipe\docker_engine`. Использование сетевых портов TCP (например, `localhost:2375`) без изменения конфигурации и авторизации запрещено.
* При монтировании локальных директорий в контейнеры применяется обязательный алгоритм трансляции путей в формат `/<буква_диска>/...` с приведением буквы к нижнему регистру и заменой косых черт.

### Изоляция базы данных SQLite от контейнеров исполнителей

И контейнеры исполнителей, и сами агенты-исполнители полностью изолированы от прямого доступа к СУБД SQLite на хост-системе и не имеют сетевого доступа к ней.

* **Реализация трассировки решений (Rationale)**: Когда агенту необходимо зафиксировать обоснование своего архитектурного решения или изменения, он записывает эти данные (поля `rationale` и `decisionTitle`) непосредственно в файл отчета `report_*.json` в рамках отведенных полей. Схема также включает обязательное поле `projectId` для связывания записи с целевым проектом в БД.
* **Импорт в БД**: Оркестратор на хост-системе с помощью File Watcher фиксирует изменение файла отчета, считывает обоснование с диска и самостоятельно выполняет безопасную запись в таблицу `agent_decisions` СУБД SQLite, связывая запись по идентификаторам `task_id` и `project_id`.

### Защита учетных данных

Локальный файл `.env` (`credential_storage: env_file`) никогда не копируется внутрь Docker-контейнеров исполнителей. Передача секретов (например, `ANTHROPIC_API_KEY` для интеграционных тестов) осуществляется точечно и жестко контролируется Архитектором через переменные окружения конкретного контейнера при запуске. Файл `.env` обязательно добавляется в `.gitignore`.

## Testing Strategy

Процесс тестирования является главным гейтом приемки результатов работы агентов.

### 1. Двухфазная верификация кода

* **Фаза разработки (Исполнитель)**: Агент-исполнитель самостоятельно пишет тесты и запускает их внутри своего контейнера в процессе работы над кодом для локального подтверждения работоспособности. Результаты фиксируются в `report_*.json`.
* **Фаза приемки (Оркестратор)**: Оркестратор полностью берет на себя выполнение финальных приемочных проверок на гейтах. При обнаружении нового файла отчета `report_*.json` со статусом `SUCCESS`, оркестратор создает абсолютно чистый, изолированный Docker-контейнер, копирует туда актуальное состояние кодовой базы со всеми изменениями Исполнителя, после чего производит независимый запуск тестов и проверок артефактов («Artifact Walks»). Результаты этой независимой проверки являются окончательным решением для гейта приемки.

### 2. Алгоритм автоматического определения тест-стека

Если в файле задачи `task_<taskId>.json` не заданы явно команды `unitTestCmd` или `e2eTestCmd`, оркестратор применяет алгоритм автоматического сканирования файлов рабочей директории проекта (`workspace`):

```typescript
function detectTechStackAndCommands(workspacePath: string) {
    const hasPackageJson = fs.existsSync(path.join(workspacePath, 'package.json'));
    const hasRequirementsTxt = fs.existsSync(path.join(workspacePath, 'requirements.txt'));
    const hasPyProject = fs.existsSync(path.join(workspacePath, 'pyproject.toml'));
    const hasGoMod = fs.existsSync(path.join(workspacePath, 'go.mod'));
    const hasCargoToml = fs.existsSync(path.join(workspacePath, 'Cargo.toml'));

    if (hasPackageJson) {
        return {
            techStack: 'nodejs',
            unitTestCmd: 'npm test',
            e2eTestCmd: 'npm run test:e2e'
        };
    } else if (hasRequirementsTxt || hasPyProject) {
        return {
            techStack: 'python',
            unitTestCmd: 'pytest',
            e2eTestCmd: 'pytest tests/e2e'
        };
    } else if (hasGoMod) {
        return {
            techStack: 'go',
            unitTestCmd: 'go test ./...',
            e2eTestCmd: ''
        };
    } else if (hasCargoToml) {
        return {
            techStack: 'rust',
            unitTestCmd: 'cargo test',
            e2eTestCmd: ''
        };
    } else {
        return {
            techStack: 'generic',
            unitTestCmd: '', // Ошибка гейта при отсутствии явных команд в задаче
            e2eTestCmd: ''
        };
    }
}
```

### 3. Механизм верификации артефактов (Artifact Walks)

Для каждого ожидаемого артефакта из массива `expectedArtifacts` файла задачи оркестратор выполняет запуск команды `validationCmd` с массивом аргументов `validationArgs` внутри чистого Docker-контейнера. Запуск команды всегда выполняется строго из корня рабочей директории (`workspace`) проекта, после чего вывод процесса (stdout/stderr) валидируется по регулярному выражению `successRegex` для подтверждения успешной работы.

### 4. Реализация полной остановки при сбое («Красный CI»)

При падении любого интеграционного или модульного теста в рамках любой из активных задач (красный статус CI для конкретной задачи) на этапе проверки оркестратора:
* Происходит немедленная полная остановка всей оркестрации конвейера доставки (hard stop).
* Оркестратор незамедлительно переводит все остальные активные задачи в статус `PAUSED`, фиксирует изменения в файлах задач на диске.
* Для мгновенной и надежной приостановки выполнения параллельно запущенных задач других исполнителей при возникновении сбоя (переход конвейера в режим паузы) оркестратор производит вызов Docker API `docker pause` (или эквивалентную команду SDK) для заморозки соответствующего изолированного контейнера исполнителя на уровне ядра ОС.
* **Строгое правило именования контейнеров**: Для связывания ID выполняющейся задачи (`taskId`) с конкретным контейнером в Docker Daemon используется детерминированный формат именования: `delivery-executor-${taskId}`. Оркестратор находит контейнер по этому имени на Windows-хосте и выполняет вызов `docker pause delivery-executor-${taskId}`, обеспечивая быструю и безопасную заморозку.
* Система переходит в глобальный режим ожидания ручного вмешательства (`manual_file_edit`). Автоматический мерж или коммит сломанного кода строго запрещен.

## Success Criteria

Успешность реализации системы оценивается по следующим измеримым показателям:

* **Скорость холодного старта**: Время запуска локального веб-интерфейса и загрузки состояния из SQLite не превышает **3 секунд**.
* **Надежность изоляции**: Сгенерированный код ни при каких обстоятельствах не выполняется на хост-системе Windows напрямую. Любые системные вызовы за пределы Docker-контейнера пресекаются.
* **Масштабируемость без дедлоков**: При одновременной работе до 10 агентов-исполнителей и 1 Архитектора отсутствуют ошибки взаимной блокировки базы данных (`database is locked`) благодаря транзакционному режиму SQLite WAL и busy_timeout.
* **Полное восстановление состояния**: Принудительное завершение процесса оркестратора в любой момент времени не приводит к потере данных или рассинхронизации. После перезапуска система полностью восстанавливает статус конвейера на основе JSON-файлов на диске, включая вехи из `milestones.json` и задачи из `task_*.json`.
* **Реактивность File Watcher**: Точное распознавание создания/удаления файлов `BLOCKED_*.md` в течение 1 секунды с корректным запуском или остановкой планировщика задач.
* **Эффективность VRAM**: Потребление видеопамяти при пиковых нагрузках (работа Ollama + Whisper + графическая оболочка Windows) не должно приводить к зависанию системы и превышать порог в **12 ГБ VRAM**. 

#### Автоматизированный метод верификации лимита VRAM в CI-окружении

Для строгого контроля лимита VRAM во время приемочного тестирования в CI-сценарий интегрируется легковесный PowerShell/Bash скрипт мониторинга, опрашивающий состояние GPU с помощью утилиты `nvidia-smi` на Windows-хосте:

```powershell
# Скрипт автоматического аудита пикового потребления видеопамяти (vram_monitor.ps1)
$MaxAllowedVramMB = 12288 # 12 ГБ в Мегабайтах
$PeakVramMB = 0
$MonitoringActive = $true

# Фоновый сбор метрик каждые 500мс во время выполнения тестовых сценариев
$Job = Start-Job -ScriptBlock {
    param($maxVram)
    $localPeak = 0
    while ($true) {
        # Получаем объем занятой VRAM в мегабайтах
        $vramQuery = & nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits
        if ($vramQuery -match '^\d+$') {
            $currentVram = [int]$vramQuery
            if ($currentVram -gt $localPeak) {
                $localPeak = $currentVram
                # Отправляем новое пиковое значение в стандартный вывод фонового задания
                Write-Output $localPeak
            }
        }
        Start-Sleep -Milliseconds 500
    }
}

# Выполнение тестового прогона агентов в Docker
npm run test:agents-full-loop

# Остановка мониторинга и получение пикового значения с явным приведением к целочисленному типу (int)
Stop-Job $Job
[int]$PeakVramMB = [int](Receive-Job $Job | Select-Object -Last 1)

Write-Host "Пиковое потребление VRAM во время тестов: $PeakVramMB MB"

if ($PeakVramMB -gt $MaxAllowedVramMB) {
    Write-Error "Критическая ошибка: Превышен лимит выделения видеопамяти! Пик: $PeakVramMB MB, Лимит: $MaxAllowedVramMB MB"
    exit 1
} else {
    Write-Host "Тест эффективности VRAM успешно пройден."
    exit 0
}
```

Данный скрипт запускается параллельно с выполнением основного сквозного (E2E) теста конвейера, гарантируя, что ни одна из задействованных локальных моделей не выходит за рамки аппаратного бюджета в 12 ГБ VRAM.

## Key Solution Decisions

| Решение | Обоснование | Альтернативы |
| --- | --- | --- |
| **Использование SQLite в режиме WAL с busy_timeout** | Позволяет реализовать полностью локальную, бесшовную и быстродействующую базу данных, не требующую сложного развертывания (Zero Configuration), при этом обеспечивая параллельный доступ для 10 агентов без риска взаимных блокировок. | PostgreSQL в Docker (усложняет развертывание), хранение только в JSON (низкая производительность аналитики в Web UI). |
| **Файловый handoff-протокол как Single Source of Truth** | Гарантирует абсолютную устойчивость к аварийным завершениям работы. Текстовые JSON-файлы легко поддаются ручному редактированию пользователем, а также без проблем версионируются в Git. | Хранение состояния только в оперативной памяти или базе данных (риск потери данных при сбоях). |
| **Кодификация вех в `milestones.json` на диске** | Исключает ошибки нарушения целостности базы данных (`FOREIGN KEY constraint failed`) при синхронизации СУБД с диска.
