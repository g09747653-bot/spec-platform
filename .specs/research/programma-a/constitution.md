## Project Vision

Автономный контур доставки — это локальная экосистема для автоматической разработки программного обеспечения, которая превращает короткую задумку (переданную текстом или голосом) в полностью протестированный и готовый к развертыванию продукт без обязательного участия человека. 

Входной точкой контура является спецификационный бандл (Bundle), генерируемый Spec Platform, который включает в себя конституцию, требования, архитектуру и задачи. Дальнейший процесс полностью делегируется локальной сети специализированных ИИ-агентов, работающих непосредственно на рабочей станции владельца.

Развитие проекта разделено на четыре ключевых этапа:
1. **Локальный однопользовательский режим Spec Platform**: развертывание и функционирование всего стека на локальной машине пользователя без зависимости от внешних облачных провайдеров авторизации (без OAuth), с локальной базой данных и гибким выбором моделей (локальных или облачных через API-ключи).
2. **Кодификация handoff-протокола**: реализация исполняемого конвейера, где жестко зафиксированы роли (Архитектор, Исполнитель), гейты приемки, уровни принятия решений и протоколы обработки блокировок. При возникновении критических ошибок (красный статус CI) происходит полная остановка процесса.
3. **Параллельная разработка и масштабирование**: поддержка одновременной работы до 10 agents-исполнителей под управлением одного агента-архитектора. В систему внедряются дополнительные роли — контроллеры и исследователи, позволяющие создавать сложные продукты уровня игровых проектов на современных движках.
4. **Телеграм-интерфейс**: подключение внешнего канала ввода (текстовые и голосовые сообщения в Telegram) на завершающем этапе, когда надежность и автономность внутреннего контура полностью доказаны.

Человек сохраняет за собой роль верховного контроллера: он может в реальном времени наблюдать за ходом выполнения задач через интерактивную ленту активности, в любой момент остановить работу контура и забрать управление на себя.

## Core Principles

При проектировании и реализации Автономного контура доставки необходимо руководствоваться следующими фундаментальными принципами:

* **Абсолютная локальная автономность и владение данными**: Все критически важные компоненты системы должны работать локально на машине пользователя. Контур не должен зависеть от сторонних SaaS-платформ авторизации или проприетарных облачных баз данных. Использование внешних LLM-провайдеров допускается только при явном указании API-ключей владельцем.
* **Файловый handoff-протокол как единый источник правды**: Взаимодействие между агентами, передача задач и отчетность строятся на базе неизменяемых, человекочитаемых файлов на диске. Это гарантирует, что состояние системы легко восстанавливается после аварийного завершения работы или перезапуска процессов.
* **Принцип "Красный CI — полная остановка"**: Безопасность и предсказуемость кода имеют наивысший приоритет. При падении любого из тестов или возникновении непредвиденной ошибки в процессе выполнения задачи конвейер немедленно останавливается, предотвращая каскадную генерацию некорректного кода или бесконечные циклы правок.
* **Наблюдаемость и аудит (Observability)**: Каждое действие агента, каждый запущенный скрипт, промпт и ответ модели должны логироваться. Пользователь должен иметь возможность поминутно восстановить ход мыслей агента-архитектора и действия исполнителей.
* **Гибридный контроль**: Баланс между полной автоматизацией и возможностью ручного вмешательства. Если система заходит в тупик, она переходит в режим ожидания помощи человека через прозрачный интерфейс редактирования файлов.

## Technology Constraints

Система должна строго соответствовать следующим технологическим ограничениям:

* **Операционная система и аппаратные ресурсы**: Работа на одной локальной машине под управлением Windows. Ограничение по объему видеопамяти составляет **16 ГБ VRAM**. Это требует оптимального распределения ресурсов между локально развернутыми вспомогательными моделями и интерфейсом.
* **База данных (`local_db`)**: Использование СУБД **sqlite**. База данных должна храниться локально в файле в директории проекта, обеспечивая нулевую конфигурацию при первом запуске. 
  * *Параллельный доступ*: Для предотвращения ошибок блокировки базы данных (`database is locked`) при одновямнной работе до 10 агентов-исполнителей и архитектора, СУБД SQLite должна быть в обязательном порядке сконфигурирована со следующими параметрами:
    * Включение режима WAL (Write-Ahead Logging): `PRAGMA journal_mode=WAL;`
    * Установка таймаута ожидания блокировки: `PRAGMA busy_timeout=5000;` (не менее 5000 мс).
* **Интерфейс запуска (`launch_interface`)**: Локальный веб-интерфейс (**web**), доступный по адресу `127.0.0.1` или `localhost`. Порт должен настраиваться через переменные окружения.
* **Провайдер моделей (`llm_provider`)**: Основным облачным провайдером для работы агентов (включая Claude Code) является **anthropic**. 
  * *Локальные модели*: Допускается использование локальных моделей в пределах лимита 16 ГБ VRAM. Все локальные модели должны запускаться через внешние локальные серверы (например, Ollama) и предоставлять стандартный OpenAI-совместимый эндпоинт, адрес (URL) которого и параметры конфигурации задаются исключительно в файле `.env`.
* **Хранение секретов (`credential_storage`)**: Все ключи доступа (включая Anthropic API Key) и конфигурационные параметры должны храниться исключительно в локальном файле конфигурации окружения **env_file** (файл `.env`). Использование внешних облачных хранилищ секретов запрещено.

## Architecture Constraints

Архитектура системы строится вокруг концепции распределенного конвейера агентов с файловой синхронизацией:

* **Файловый handoff-протокол**: Вся координация между агентом-архитектором и агентами-исполнителями осуществляется посредством записи структурированных файлов в строго определенные директории. В качестве единого формата передачи данных используется исключительно **JSON**. Архитектура должна гарантировать, что обрыв процесса любого из агентов не приводит к потере состояния — при перезапуске агент считывает последний валидный файл handoff-задания.
* **Структура папок handoff-протокола**:
  В корневой рабочей директории проекта (`workspace`) жестко закрепляется следующая иера hierarchy папок:
  * `/handoff/tasks/` — директория для размещения файлов заданий от Архитектора исполнителям. Имя файла формируется по шаблону: `task_<taskId>.json`.
  * `/handoff/reports/` — директория для размещения файлов отчетов от исполнителей Архитектору. Имя файла формируется по шаблону: `report_<taskId>.json`.
* **Схема данных JSON для файлов задач (`task_schema.json`)**:
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "HandoffTask",
  "type": "object",
  "properties": {
    "taskId": { "type": "string" },
    "milestoneId": { "type": "string" },
    "title": { "type": "string" },
    "description": { "type": "string" },
    "filesToEdit": {
      "type": "array",
      "items": { "type": "string" }
    },
    "expectedArtifacts": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "path": { "type": "string" },
          "validationCmd": { "type": "string" },
          "validationArgs": {
            "type": "array",
            "items": { "type": "string" }
          },
          "successRegex": { "type": "string" }
        },
        "required": ["path", "validationCmd", "validationArgs", "successRegex"]
      }
    },
    "status": {
      "type": "string",
      "enum": ["PENDING", "IN_PROGRESS", "COMPLETED", "FAILED", "BLOCKED"]
    }
  },
  "required": ["taskId", "milestoneId", "title", "description", "filesToEdit", "expectedArtifacts", "status"]
}
```
* **Схема данных JSON для файлов отчетов (`report_schema.json`)**:
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "HandoffReport",
  "type": "object",
  "properties": {
    "reportId": { "type": "string" },
    "taskId": { "type": "string" },
    "executorId": { "type": "string" },
    "status": {
      "type": "string",
      "enum": ["SUCCESS", "FAILED", "BLOCKED"]
    },
    "testsRun": {
      "type": "object",
      "properties": {
        "total": { "type": "integer" },
        "passed": { "type": "integer" },
        "failed": { "type": "integer" }
      },
      "required": ["total", "passed", "failed"]
    },
    "errors": {
      "type": "array",
      "items": { "type": "string" }
    },
    "blockReason": { "type": "string" }
  },
  "required": ["reportId", "taskId", "executorId", "status"]
}
```
* **Изоляция исполнения агентов (`agent_isolation`)**: Запуск кода, написанного агентами-исполнителями, а также прогон тестов должны происходить в изолированном контейнере **docker_execution**. Агенты не должны иметь прямого неконтролируемого доступа к хост-системе Windows во избежание случайного повреждения файлов пользователя или неконтролируемой сетевой активности.
* **Многоагентная иерархия**:
  * **Агент-Архитектор**: Читает спецификационный бандл из Spec Platform, разбивает проект на вехи (milestones), формирует детальные handoff-задания для исполнителей, проводит инспекцию кода и результатов тестирования.
  * **Агенты-Исполнители (до 10 параллельных инстансов Claude Code)**: Принимают handoff-задание, вносят изменения в код в рамках Docker-контейнера, пишут модульные и сквозные тесты, запускают проверки и генерируют отчеты о выполнении.
  * **Контроллеры и Исследователи**: Вспомогательные агенты, осуществляющие статический анализ кода, поиск оптимальных архитектурных решений на диске и координацию параллельных потоков разработки.
* **Протокол обработки блокировок (`blocked_protocol`)**: Если агент-исполнитель или архитектор сталкивается с неразрешимым препятствием (логическое противоречие в требованиях, невозможность настроить окружение), система активирует протокол **file_edit**. Чтобы исключить состояние гонки и конфликт файлов при параллельной работе до 10 агентов, блокировка фиксируется для конкретной задачи. Агент записывает описание проблемы в индивидуальный файл `BLOCKED_<taskId>.md` в корне рабочей директории и переводит задачу в статус ожидания. Пользователь может вручную отредактировать файлы исходного кода/требований для снятия блокировки. Блокировка конкретной задачи считается официально снятой, когда файл `BLOCKED_<taskId>.md` удаляется пользователем, что фиксируется файловым вотчером (file watcher) или периодическим опросом (polling) со стороны системы, после чего исполнитель по данной задаче автоматически возобновляет работу.
* **Интермедиация сбоев (`failure_intervention`)**: При возникновении ошибок сборки или тестирования, требующих вмешательства человека, применяется протокол **manual_file_edit**. Пользователь исправляет проблемные места непосредственно в кодовой базе или файлах конфигурации, после чего контур возобновляет автоматическую работу.

## Testing Approaches

Процесс тестирования является ключевым гейтом приемки результатов работы агентов. Автономный контур должен реализовывать жесткий и многоуровневый подход к верификации:

* **Граница автоматизации (`automation_boundary`)**: Система функционирует в полностью автономном режиме до момента прогона тестов (**stop_at_tests**). Если тесты завершаются с ошибкой (красный статус CI), автоматическое внесение изменений прекращается, фиксируется состояние сбоя, и система ожидает действий пользователя. Контур не имеет права коммитить или сливать ветки с падающими тестами.
* **Уровни тестирования**:
  1. **Юнит-тестирование (Unit tests)**: Проверка изолированных модулей, классов и функций. Пишется исполнителем в обязательном порядке для каждого нового или измененного компонента.
  2. **Интеграционное и сквозное тестирование (E2E tests)**: Проверка сценариев взаимодействия компонентов системы в изолированном Docker-окружении.
  3. **"Живые прогулки" с артефактами (Artifact walks)**: Специализированный автоматизированный сценарий, в рамках которого агент-архитектор производит валидацию сгенерированных бинарных файлов, скриптов и других артефактов.
     * *Механизм верификации*: Параметры для проверки работоспособности артефактов должны в обязательном порядке наследоваться и извлекаться из полей `expectedArtifacts` handoff-задания. Агент-архитектор производит запуск, используя переданную команду (`validationCmd`) и массив аргументов (`validationArgs`), после чего проверяет вывод процесса на соответствие регулярному выражению (`successRegex`) для подтверждения успешной работы.
* **Автоматический аудит тестов**: Агент-архитектор проверяет не только работоспособность кода, но и покрытие тестами. Если исполнитель прислал отчет о выполнении задачи, но не покрыл измененный функционал тестами, задача автоматически отправляется на доработку.

## Coding Standards

Код, генерируемый агентами и составляющий ядро системы, должен соответствовать строгим критериям качества:

* **Читаемость для людей и машин**: Исходный код должен быть самодокументируемым. Агенты обязаны снабжать сложные алгоритмы лаконичными комментариями на русском языке. Структура файлов и каталогов должна строго следовать общепринятым стандартам используемого языка программирования.
* **Форматирование**: Перед передачей кода на проверку Архитектору, агент-исполнитель обязан запустить локальный линтер и форматировщик кода (например, Prettier, ESLint, Black или аналогичные инструменты, зафиксированные в конфигурации проекта). Наличие синтаксических предупреждений или ошибок форматирования приравнивается к падению тестов.
* **Логирование и трассировка**: Каждая подсистема должна вести детальные логи. Любое ключевое решение агента (например, изменение структуры БД, добавление зависимости) должно сопровождаться записью в лог-файл сессии с указанием причины (Rationale).
* **Принцип единственной ответственности (Single Responsibility)**: Агенты должны избегать создания гигантских монолитных файлов. Код должен быть разбит на логические модули, удобные для параллельного анализа несколькими агентами.

## Security Constraints

Безопасность локальной среды пользователя является абсолютным приоритетом при проектировании автономного контура:

* **Docker-изоляция**: Все действия по компиляции, сборке, установке зависимостей (например, через `npm install`, `pip install`) и непосредственному запуску разрабатываемого продукта должны осуществляться исключительно внутри Docker-контейнеров (`agent_isolation: docker_execution`). Прямой запуск недоверенного кода на хост-системе Windows строго запрещен.
* **Интеграция с Docker Desktop на Windows**:
  * Для взаимодействия бэкенда с Docker API на Windows-хосте должен использоваться стандартный именованный канал Windows: `//./pipe/docker_engine`. Использование сетевых портов TCP (например, `localhost:2375`) без явной авторизации запрещено.
  * Логика маппинга путей: при монтировании локальных папок хоста в тома контейнеров (Volumes) система должна выполнять строго детерминированное преобразование путей. Обязательным целевым форматом преобразования абсолютных Windows-путей в Unix-подобные пути контейнера является стандартный формат Docker Desktop `/<буква_диска>/...` (например, путь `C:\Users\Owner\workspace\project1` преобразуется строго в `/c/Users/Owner/workspace/project1`). При этом буква диска всегда приводится к нижнему регистру, а все обратные косые черты `\` заменяются на прямые `/`.
* **Защита учетных данных**: Файл `.env` (`credential_storage: env_file`) никогда не должен копироваться внутрь Docker-контейнеров, где работают агенты-исполнители, если только им явно не требуются конкретные API-ключи для тестирования интеграций. Передача секретов должна быть точечной и жестко контролироваться Архитектором. Файл `.env` должен быть обязательно добавлен в `.gitignore`.
* **Локальный сетевой контур**: Локальный веб-интерфейс Spec Platform должен биндиться только на loopback-интерфейс (`127.0.0.1`). Доступ к панели управления из внешней сети по умолчанию должен быть закрыт.
* **Контроль деструктивных действий**: Агенты не должны иметь прав на удаление каталогов вне выделенной рабочей директории проекта (`workspace`). Любые попытки выхода за пределы этой директории должны блокироваться на уровне файловой системы Docker и монитора процессов.

## Performance Targets

Несмотря на запуск на одной локальной машине, система должна обеспечивать высокую отзывчивость и стабильность работы:

* **Эффективное использование VRAM**: При использовании локальных моделей для анализа кода или парсинга речи потребление видеопамяти не должно превышать **12 ГБ VRAM**, оставляя минимум 4 ГБ VRAM для нужд операционной системы и графического интерфейса пользователя.
* **Быстрый запуск конвейера**: Время холодного старта локального веб-интерфейса и загрузки состояния из SQLite базы данных не должно превышать **3 секунд**.
* **Параллельная обработка**: Архитектура системы должна поддерживать эффективное планирование ресурсов при работе до 10 параллельных исполнителей. Запуск контейнеров Docker должен быть оптимизирован по памяти (использование легковесных базовых образов, кэширование слоев сборки) для предотвращения зависания хост-системы Windows.
* **Тайм-ауты агентов**: На любое действие агента-исполнителя должен накладываться жесткий тайм-аут (например, не более 5 минут на одну итерацию генерации/тестирования). Это исключает зацикливание агента и нецелевой расход токенов API.

## Integration Points

Автономный контур доставки взаимодействует со следующими ключевыми внешними и внутренними компонентами:

* **Интеграция со Spec Platform Bundle**:
  Система должна автоматически считывать и парсить входной бандл спецификаций из локальной папки. Бандл представляет собой папку со строго определенной структурой:
  * `bundle/constitution.md` — файл конституции проекта.
  * `bundle/requirements.json` — структурированный файл функциональных и нефункциональных требований проекта.
  * `bundle/architecture.md` — описание архитектуры, технологического стека и ограничений.
  * `bundle/tasks.json` — структурированный список исходных задач для Архитектора.
  
  Файл `bundle/requirements.json` должен строго соответствовать следующей JSON-схеме (`requirements_schema.json`):
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "SpecBundleRequirements",
  "type": "object",
  "properties": {
    "bundleId": { "type": "string" },
    "functionalRequirements": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "id": { "type": "string" },
          "title": { "type": "string" },
          "description": { "type": "string" }
        },
        "required": ["id", "title", "description"]
      }
    },
    "nonFunctionalRequirements": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "id": { "type": "string" },
          "category": { "type": "string" },
          "description": { "type": "string" }
        },
        "required": ["id", "category", "description"]
      }
    }
  },
  "required": ["bundleId", "functionalRequirements", "nonFunctionalRequirements"]
}
```

  Файл `bundle/tasks.json` должен строго соответствовать следующей JSON-схеме:
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "SpecBundleTasks",
  "type": "object",
  "properties": {
    "bundleId": { "type": "string" },
    "projectId": { "type": "string" },
    "tasks": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "taskId": { "type": "string" },
          "title": { "type": "string" },
          "description": { "type": "string" },
          "dependsOn": {
            "type": "array",
            "items": { "type": "string" }
          },
          "metadata": {
            "type": "object",
            "properties": {
              "expectedArtifacts": {
                "type": "array",
                "items": {
                  "type": "object",
                  "properties": {
                    "path": { "type": "string" },
                    "validationCmd": { "type": "string" },
                    "validationArgs": {
                      "type": "array",
                      "items": { "type": "string" }
                    },
                    "successRegex": { "type": "string" }
                  },
                  "required": ["path", "validationCmd", "validationArgs", "successRegex"]
                }
              }
            },
            "required": ["expectedArtifacts"]
          }
        },
        "required": ["taskId", "title", "description", "dependsOn", "metadata"]
      }
    }
  },
  "required": ["bundleId", "projectId", "tasks"]

```
* **Интеграция с Anthropic API**: Надежное соединение с API Claude для обеспечения работы агентов. Должна быть реализована автоматическая обработка ошибок сети, превышения лимитов на запросы (Rate Limits) и механизмы экспоненциальной задержки перед повторной отправкой запроса (Exponential Backoff).
* **Интеграция с Docker Daemon**: Управление контейнерами через Docker Engine API на Windows (Docker Desktop) с использованием локального сокета-канала `//./pipe/docker_engine`. Автоматическое создание, запуск, остановка контейнеров и монтирование локальных рабочих директорий проекта с выполнением трансляции путей.
* **Интеграция с Telegram Bot API**: Подключается на финальном этапе разработки контура. Бот принимает текстовые сообщения и голосовые заметки (с последующей локальной или облачной транскрибацией), преобразует их в первичное описание идеи и инициирует создание бандла в Spec Platform для последующей передачи в автономный контур.
