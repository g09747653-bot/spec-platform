Проверено при перепроверке:

| Трассировка | Каждый FR/NFR/IR замаплен на задачи (таблица Requirement Coverage в tasks.md); выборочная сверка FR-004, FR-011, FR-014, FR-020, NFR-012 — расхождений нет |

| Страхи заказчика | Все три закрыты конструктивно (см. ниже) |

**Как план закрывает три ключевых беспокойства заказчика:**

1. *«ТЗ забывается, агент уходит с маршрута»* — гейты вшиты в код, а не в промпты (P1, P2): агент физически не может перескочить этап, состояние машины хранится в БД. CLAUDE.md направляет каждую сессию к бандлу. Этот документ добавляет второй контур: milestone-гейты заказчика и протокол сессий (§4).
2. *«ТЗ недостаточно подробно»* — 20 FR имеют 100+ проверяемых критериев приёмки; каждая задача несёт собственные Acceptance Criteria и трассировку к требованиям. Уточнений «на ходу» не потребуется: у исполнителя есть ответ на уровне «какие колонки в таблице» и «какой HTTP-код при какой ошибке».
3. *«Тупики посреди пути»* — walking skeleton (M1) вскрывает интеграционные риски в первые часы, а не в конце; самый рискованный кластер (стриминг/резюм, задачи 45–48) явно помечен и строится сначала на стаб-провайдере; для настоящих тупиков — протокол BLOCKED и процедура амендмента (§5), которая меняет ТЗ управляемо, а не «по ситуации».

**Минорные замечания (не блокируют, учтены в этом документе):**

- З-1. Качество генерируемых спек (SC-17 «бандл пригоден агенту без переписывания») — единственный критерий, не проверяемый автоматически. План честно относит его к ручной оценке (задача 102). Следствие для сроков: после технической готовности заложить 1–3 дня итераций над промптами стадий. Учтено в оценках §7.
- З-2. Реальные LLM-провайдеры впервые трогаются только в проде (задача 103), т.к. CI обязан быть детерминированным. Добавляю в гейт M3 ручной смоук на preview-окружении с настоящими ключами (§3, гейт M3) — без изменения tasks.md.
- З-3. Отдельной задачи на публичную landing-страницу нет (анонимному посетителю по требованиям доступны только маркетинг/авторизация). Покрывается задачами 10/14; при желании — косметика после MVP.
- З-4. Внешние предпосылки (OAuth-приложения, аккаунты, ключи) размазаны по задачам 6/9/12. Вынесены отдельным чек-листом заказчика (§6) — их надо закрыть ДО старта, иначе исполнитель будет простаивать.

## 2. Структура принятия решений

### Роли

| Роль | Кто | Что делает |
|---|---|---|
| **Заказчик** | Пользователь | Единственный источник изменений ТЗ. Команды: «начинай M<N>», «проверь M<N>», «принято» / «доработать». Участие ≈ 15–40 мин на гейт |
| **Архитектор** | Отдельная сессия Claude (эта роль) | По команде заказчика проверяет milestone по чек-листу §3, выносит вердикт, ведёт амендменты ТЗ. НЕ пишет код проекта |
| **Исполнитель** | Claude Code (OPUS 5) | Выполняет tasks.md по номерам, отмечает чекбоксы, ведёт `.specs/decisions.md`, останавливается на гейтах |

### Уровни решений — кто что решает

| Уровень | Тип решения | Кто решает | Фиксация |
|---|---|---|---|
| **0 — молча** | Невидимое снаружи модуля: имена переменных, внутренняя структура файла, порядок тестов | Исполнитель | нигде |
| **1 — с записью** | Техническое решение в рамках заданных контрактов: выбор вспомогательной библиотеки (напр., ZIP-пакет), способ реализации AC, не меняющий ни один контракт solution.md | Исполнитель | строка в `.specs/decisions.md` |
| **2 — стоп и вопрос** | Противоречие между документами; AC невыполним как написан; нужно изменить контракт/схему БД/интерфейс модуля сверх заданного; новая зависимость вне стека | Архитектор → при необходимости Заказчик | амендмент (§5) |
| **3 — только Заказчик** | Изменение объёма (scope), перенос MVP cut line, отключение любого обязательного теста, любая правка constitution.md | Заказчик | амендмент (§5) |

Правило-лакмус для исполнителя: **если решение меняет хоть один AC, хоть один интерфейс из solution.md или хоть одну строку constitution.md — это не твой уровень. Остановись и спроси.**

### Жизненный цикл milestone (основной контур управления)

```
Заказчик: «начинай M<N>»
   ↓
Исполнитель: задачи M<N> по номерам; чекбоксы; тесты зелёные; CI зелёный
   ↓  (красный CI = стоп и чинить, дальше не идти)
Исполнитель: «M<N> завершён» + краткий рапорт (что сделано, decisions.md, blocked-лист)
   ↓
Заказчик: «проверь M<N>»  →  Архитектор: чек-лист гейта §3
   ↓
Вердикт:  ПРИНЯТО → git tag m<N>-accepted → Заказчик: «начинай M<N+1>»
          ДОРАБОТАТЬ → нумерованный список дефектов → Исполнитель чинит ТОЛЬКО их → повторная проверка
```

Это и есть запрошенная модель «я даю команду — ты проверяешь результат»: заказчик произносит две короткие команды на milestone, всё остальное делают исполнитель и Архитектор.

### Файловый handoff-протокол (принят 2026-08-12)

Обмен рапортами и заданиями идёт через файлы репозитория — заказчик не копирует ничего, кроме одной константной фразы:

- `.specs/handoff/START_HERE.md` — пишет Архитектор перед каждым раундом: вердикт по предыдущему рапорту, решения, задание, режим сессии. Команда заказчика исполнителю всегда одна: **«Прочитай .specs/handoff/START_HERE.md и исполни»**.
- `.specs/handoff/REPORT-M<N>.md` — пишет исполнитель при каждой остановке по стандартной форме рапорта; новые раунды добавляются секцией сверху, история не затирается; файл коммитится вместе с работой. В чат исполнитель выводит две строки: статус одной фразой и путь к рапорту.
- Заказчик сообщает Архитектору только факт остановки («готово», по желанию — скрин последних строк). Архитектор читает рапорт и файлы проекта напрямую через подключённую папку, проверяет и кладёт следующий START_HERE.md.
- Контрольные суммы и git-bundle не требуются: у Архитектора прямой доступ к папке проекта, целостность обеспечивается git-историей самого репозитория. (Схемы с SHA-256-бандлами нужны, когда стороны изолированы друг от друга; здесь это лишний слой.)
- Отправка фразы заказчиком = утверждение вердикта из START_HERE.md, включая амендменты с пометкой «утверждено заказчиком». На ключевых гейтах (M1, M2, M3, M6, M7) Архитектор дополнительно проговаривает вердикт в чате явно и ждёт реакции заказчика перед выпуском START_HERE.md.

### Порядок работы с PR (принято 2026-08-12, следствие A-1)

Исполнитель мержит свои PR сам, без участия заказчика. Рамки обязательны:

1. Мерж только при **зелёных обоих обязательных чеках**. Красный чек = чинить, а не мержить.
2. **Обход защиты запрещён абсолютно:** никакого `--admin`, никакого временного снятия branch protection, никакого прямого push в `main`. Отказ сервера в мерже — это сигнал, а не препятствие: остановиться и рапортовать.
3. Squash-merge, ветка удаляется после мержа. `main` обязан оставаться зелёным всегда.
4. Гранулярность: один PR на задачу или на группу тесно связанных задач. PR, который невозможно осмысленно прочитать целиком, — слишком большой.
5. Мерж ≠ приёмка. Приёмку milestone выносит Архитектор на гейте; смерженный PR может быть отправлен в доработку.

## 3. Контрольные точки (гейты) M0–M9

Каждый гейт = 4 универсальных пункта + специальные проверки. Универсальные: (a) все чекбоксы milestone отмечены; (b) CI зелёный — исполнитель прикладывает вывод; (c) Архитектор выборочно проверяет 2–3 AC по коду; (d) демонстрируемый результат из Milestone Map воспроизводится.

**Пятый универсальный пункт (А-2.1, действует с M6 раунд 5, бессрочно): гейт проходит сам исполнитель.** Playwright E2E полного демонстрируемого пути + скриншоты каждого шага + trace/video; артефакты коммитятся в репо (`artifacts/gate-M<N>/`), рапорт ссылается на них. Заказчик в тестировании не участвует. Архитектор принимает гейт по артефактам. Красный прогон = milestone не сдан. Формулировки «проходится руками» в таблице ниже читать как «проходится исполнителем через браузерную автоматизацию с артефактами».

|---|---|---|

## 4. Протокол сессий исполнителя (анти-дрейф)

1. **Начало каждой сессии:** перечитать `constitution.md` целиком + текущий milestone в `tasks.md` + хвост `decisions.md`. Не полагаться на память прошлых сессий — только на файлы и БД.
2. **Одна сессия ≤ один milestone.** Длинный контекст — главный источник дрейфа. Новый milestone = новая сессия.
3. **Красный CI/тест = полная остановка** до зелёного. Запрещено «вернусь к этому позже».
4. **Строгий порядок номеров** с учётом зависимостей (правило 2 CLAUDE.md). Параллельность допустима только по флагу Parallel-safe и только в 24-часовом режиме (§7Б).
5. **Идеи «сделать заодно»** → раздел Backlog в `decisions.md`, не реализуя (правило 5 CLAUDE.md).
6. **Стоп-правило гейта:** завершив milestone — остановиться и ждать приёмки. Самовольный переход к следующему milestone запрещён.

### Протокол BLOCKED (тупики)

Задача не сдвигается после **2 полноценных подходов** (или ~30 мин чистого времени):

1. Записать в `decisions.md`: `BLOCKED task <N>: <симптом> / <что пробовал (2 подхода)> / <гипотеза причины>`.
2. Взять следующую задачу текущего milestone с `Parallel-safe: yes`, чьи зависимости закрыты.
3. Таких нет → стоп, рапорт заказчику. **Запрещено:** менять архитектуру ради обхода, ослаблять тест, выключать проверку, «временно» нарушать constitution.

## 5. Амендменты ТЗ (управляемое изменение вместо дрейфа)

Если реализация доказала, что документ неточен (уровень 2–3):

1. Исполнитель останавливает затронутую задачу, формулирует проблему одним абзацем (что написано / что невозможно или противоречит / варианты).
2. Архитектор готовит **амендмент**: точечный diff к конкретному документу бандла + оценка волнового эффекта (какие задачи/AC затронуты).
3. Заказчик утверждает одним словом. Архитектор вносит правку в документ, добавляет строку в журнал `Amendments` в конце `decisions.md`.
4. Исполнитель продолжает уже по обновлённому ТЗ.

Так «единое ТЗ до конца проекта» остаётся истинным: документы могут уточняться, но только через явную процедуру с ведомой историей — никогда молча в ходе кодинга.

## 7. Оценка времени

Базовые факты: 103 задачи = 5 Small + 71 Medium + 27 Large. По легенде плана это **≈ 130–255 человеко-часов** (середина ≈ 190 ч). Машинное время исполнителя (OPUS 5) существенно меньше человеко-часов, но добавляются прогоны CI, доработки после гейтов (закладываю 20–35%) и калибровка промптов (З-1).

### Вариант Б — вся задумка за 24 часа (спринт)

Арифметика допускает: критический путь плана ≈ **20–22 ч чистого машинного времени**, всё остальное параллелится. Но резерва почти нет, поэтому нужны жёсткие условия и честные вероятности.

**Обязательные условия старта:**

1. Чек-лист §6 закрыт полностью — ни минуты таймера на заведение аккаунтов.
2. **3–4 параллельных исполнителя** (Claude Code в отдельных worktree/сессиях) по полосам: A — ядро/workflow, B — данные/auth/провайдеры, C — UI, D — тесты/E2E. Распределение уважает флаги Parallel-safe; сливает полосы один интегратор (полоса A).

### Карта режимов исполнителя (принято 2026-08-12, панель из 3 независимых линз)

Оценки §7 считались для одиночного исполнителя **без ultracode**. Ultracode не сжимает календарь обычного темпа: узкое место — последовательные зависимости, прогоны CI и гейты (параллельные банды покрывают ~¼ задач), а перерасход токенов душит лимиты и замедляет именно последовательную цепочку. Ценность ultracode — точечная (ширина поиска), ценность Opus MAX — глубина на риск-узлах.

| Сессия | Режим | Примечание |
|---|---|---|
| M0, M1 | **Opus high** | в промпте M1: задача 16 (immutability-триггер) — повышенная тщательность и саморевью, у неё максимальный радиус поражения |
| M2 | **Opus MAX** | ядро корректности (24–30); после приёмки задачи 30 допустимо переключить сессию на high |
| M3 | **Opus MAX** | риск-кластер 45–48 (стриминг/resume) — единственная неопределённость, не снятая спекой |
| M4, M5 | **Opus high** | в промпте M4: задача 61 (DecisionIntentResolver) — повышенная тщательность abstain-веток |
| M6 | **Opus high** | в промпте: задача 75 (session resume) — повышенная тщательность |
| M7 | **Opus high** | эскалация до MAX на 84–87 (staleness) только по факту затыка |
| M8 | **Opus high** + один ultracode red-team прогон на входе | fan-out атак (инъекции, санитайзер, секреты, authz) → список находок → фиксы на high |
| M9 | **Opus high** | |

> **А-2 (2026-08-14):** строки M7–M9 выше относятся к плану до амендмента. Для парити-программы действуют режимы из таблицы §3-bis: M7/M8 — MAX, M9/M10 — high, финал M10 — один ultracode-прогон парити-чек-листа. Red-team по безопасности из прежнего M8 переносится в Этап 2 (перед бетой).

**Лестница эскалации:** high → MAX → ultracode, только по триггеру, с деэскалацией после прохождения. Закрытый список триггеров ultracode: (1) BLOCKED после 2 подходов на MAX — параллельный веер гипотез вместо третьей слепой попытки; (2) red-team аудит на входе в M8; (3) калибровка З-1 после MVP — ансамблевая генерация + панель судей качества спек; (4) опционально при свободном бюджете — слепой предпрогон главного гейта M6; (5) 24-часовой спринт §7Б, если выбран сознательно. Всё остальное — анти-триггер: задачи «по контракту с готовыми AC» уже оплачены на этапе планирования.

Ожидаемый оверхед профиля к базе «всё на Opus high»: **+25–45% токенов**. Для сравнения: «всё на ultracode» ≈ 5–15× базы при нулевом или отрицательном выигрыше календаря.

### Рекомендация Архитектора

Гибрид: **спринт по схеме Б до гейта MVP (M6), затем темп варианта А** для M7–M9 и калибровки качества. Так за первые сутки материализуется вся копия-задумка (этап 1 заказчика), а полировка и Quality-дифференциатор не наследуют спринтовую спешку. Пословица «семь раз отмерь» уже исполнена бандлом `.specs/` — резать можно быстро.
