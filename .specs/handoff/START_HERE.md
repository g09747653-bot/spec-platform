## Порядок сессии

1. **Системные правки — первыми** (они судят и до-заход):
   - **(а) Вершинный критерий.** Финальный алерт «Проект завершён» обязан нести сверку с задумкой, когда конвейер ею располагает: число принятых задач + главный замер самопроверки (пороги/DEVIATIONS, если план их снимал) + путь к отчёту расхождений. Голая галочка при существующем DEVIATIONS.md — дефект. Тест на обе формы алерта.
   - **(б) Суд полноты плана — на интейке, ДО конвейера.** Модельная проверка «покрывает ли план задумку»: вход — задумка (seed) + список задач с охватами; выход — named-вердикт (полон / пробелы поимённо). Пробелы → интейк останавливается алертом с перечнем (по образцу роли Архитектора в нашем протоколе), решение продолжать/дополнить — за владельцем кнопкой. Провайдер — тот же шов роли; регрессия на слепке nvidia-плана (обязана найти отсутствие переноса контентной графики).
   - **(в) Пара моста для роли архитектора заданий — в штатный `loop/.env.example`** с комментарием (конфигурационная находка перезахода №2).
2. **До-заход конвейером** — твой же план из ленты: перенос графики из `tools/visual-diff/baseline/network/` (манифест URL→файл) в `assets/`, докраска девяти секций главной и карточек products по уже снятым JSON-координатам эталона, перепрогон сравнения с порогами. Оформи как до-заходные задачи в handoff той же рабочей директории (`tg-20260822-235200`), конвейер ведёт их штатно; суд полноты (б) обязан пройти по до-заходному плану и не найти пробелов. Операторские ходы — только через поверхности, поимённо.
3. **Итог заказчику**: алерт нового образца (а) + пути к продукту и отчёту сравнения; его глаза — и есть приёмка до-захода.
4. **Рапорт** — секция «До-заход приёмки» сверху в REPORT-M17a.md, две строки в чат.
