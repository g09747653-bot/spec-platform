### СДЕЛАНО

**Задача 11 — ядро схемы (PR [#5](https://github.com/g09747653-bot/spec-platform/pull/5), смержен).** `users`, `projects`, `sessions`, `workflow_state`. `projects.owner_id` — NOT NULL FK с каскадом, `sessions.project_id` — unique (связь 1:1 стала свойством БД). Два CHECK на `workflow_state` генерируются из тех же кортежей стадий, что и будущая таблица переходов (D-15), поэтому DDL и модель стадий физически не могут разойтись.

Тесты уровня БД идут на PGlite через штатный мигратор Drizzle (D-13) — то есть проверяется тот DDL, который поедет в прод. **Дефект, найденный при написании этих тестов:** `substage IN (...)` при `substage IS NULL` даёт NULL, а CHECK пропускает NULL — spec-стадия без подстадии сохранялась бы. Добавлено явное `IS NOT NULL`, негативный тест на это есть.

**Задачи 12–15 (PR [#6](https://github.com/g09747653-bot/spec-platform/pull/6), зелёный CI, ждёт переменных).**

- **12 — Auth.js.** Database session strategy (не предпочтение, а требование: FR-001 AC-6 требует отзываемой сессии, чего JWT-cookie не даёт), оба провайдера, cookie `httpOnly`/`SameSite=Lax`; `secure` наследуется от протокола ровно тем же выводом, которым Auth.js помечает csrf/state/pkce — переопределять его руками значит рассинхронизировать набор. Таблицы адаптера — `accounts`, `auth_sessions`, `verification_tokens`; сессия воркфлоу сохранила имя `sessions`.

  Проверено без браузера: 8 тестов гоняют **тот самый адаптер, который вызывает Auth.js**, против реального PostgreSQL — возвращающаяся идентичность переиспользует аккаунт (AC-3), незнакомая GitHub-идентичность создаёт новый (AC-2), два провайдера с одинаковым `providerAccountId` не смешиваются, удаление сессии перестаёт её резолвить (AC-6). Проверено запросом: `POST /api/auth/signin/{google,github}` отдаёт 302 на authorize-эндпоинт провайдера с PKCE и нашим `client_id` (AC-1). Живой OAuth-хоп автоматизировать нельзя — он в списке ручных проверок гейта.

- **13 — OwnerScope.** Класс с приватным конструктором и приватным полем: структурно похожий объектный литерал ему **не присваивается**, поэтому собрать scope из тела запроса нельзя, а `forAuthenticatedUser` — единственный конструктор, и его call-sites это полный аудит того, откуда берётся авторизация. Первый параметр каждого метода репозитория; `owner_id` уходит в SQL, включая записи. 15 тестов, все одной формы: запрос второго пользователя к строке первого возвращает пусто, а не «запрещено».

  Создание проекта+сессии+workflow_state — **один statement** (цепочка CTE): у прод-драйвера `neon-http` интерактивных транзакций нет вовсе (D-16), и три round-trip'а оставили бы проект без сессии при сбое. Тест на это есть: падение FK не оставляет ни одной строки.

- **14 — защита маршрутов.** `src/proxy.ts` — в Next 16 конвенция `middleware` переименована в `proxy` (D-17). Прокси принимает одно дешёвое решение (есть cookie или нет) и **не решает** ни валидность сессии, ни владение: первое подтверждает layout/handler запросом к БД, второе — предикат в SQL. Поэтому чужой проект даёт 404 без ветки, которая могла бы сделать из него 403.

- **15 — вход по промпту.** `GET`/`POST /api/projects`, форма, список с именем/стадией/временем, страница сессии. Правило «пустой промпт отклоняется» — одно правило, исполняемое дважды: браузер отвечает мгновенно, API решает.

**Задачи 16–23 (PR [#7](https://github.com/g09747653-bot/spec-platform/pull/7), стек поверх #6).**

- **16 — immutability, повышенная тщательность (как и просил Архитектор).** Правило сформулировано **от противного**: заморожено всё, кроме `approved`, — поэтому колонка, добавленная позже, заморожена по умолчанию, а не изменяема по забывчивости. Каждая колонка поднимает своё сообщение. `approved` ходит только `false → true`. DELETE запрещён **на обеих таблицах**, кроме каскада от проекта; каскад распознаётся тем, что родитель внутри `BEFORE DELETE` уже удалён. Охранять только ревизии было бы дырой: прямое удаление spec-файла унесло бы историю «каскадом».

  **39 тестов, и все — сырой SQL против БД**, а не через репозиторий: триггер обязан держать любого писателя (миграцию, psql, невнимательную руку), а не только наш код. В том числе `UPDATE`/`DELETE` без `WHERE` и замороженная колонка, спрятанная среди разрешённых.

  **Контрольный прогон** (техника, которую Архитектор отметил в M0): тот же `UPDATE` прогоняется на инстансе со **снятым** триггером — проходит, контент меняется; триггер возвращается — отказ возвращается. Иначе тест, ожидающий падения, зелёный по любой причине, включая опечатку в запросе.

  **Дефект, найденный этими тестами:** `btrim(content) <> ''` режет только пробелы, поэтому контент из одних переводов строки и табов проходил проверку «не пустой». Теперь `content ~ '[^[:space:]]'`.

- **17 — нумерация.** `revision_number` выделяется тем же statement'ом, который вставляет строку; гонка разрешается unique-констрейнтом и ретраем. Проверено 8 параллельными вставками: числа 1..8, каждое ровно один раз, без дыр. Три резолвера — latest, latest-approved, latest-pre-enrichment (последний по `origin='parity'`, что и делает правило экспорта A6 вычислимым, а не угадываемым).

- **18 — стаб-провайдер.** Детерминированные чанки, собирающиеся байт-в-байт; инъекция отказа на выбранном индексе чанка — ровно то, что нужно кластеру 43–48. Ни один тест репозитория не обращается к вендору.

- **19–22.** Позиция воркфлоу с оптимистичной блокировкой (устаревшая запись возвращает `null`, а не двойной переход) и stage rail; генерация, кладущая **ровно одну неодобренную** ревизию; решение по карточке (approve требует номер ревизии, который видел пользователь, иначе `PENDING_DECISION` — D-25); ZIP-экспорт, резолвящий каждый файл в последнюю одобренную parity-ревизию, с режимом и списком пропусков **в заголовках, а не внутри архива** (FR-015 AC-8).

- **23 — сквозной путь.** Вход → промпт → генерация → request changes → approve → скачивание, причём **архив распаковывается и проверяется**: внутри `constitution.md` и именно вторая (одобренная) ревизия, а не первая. Плюс: reload посреди решения возвращает ту же карточку; чужой пользователь получает 404 и в теле страницы нет ни слова о проекте; выход через кнопку «Sign out», после которого **тот же токен возвращается в браузер и обязан быть бесполезным** — иначе тест доказывал бы лишь очистку cookie, а не отзыв сессии (FR-001 AC-6). Добавление этого шага вскрыло ловушку окружения: `signOut` разворачивает относительный путь относительно `AUTH_URL`, поэтому E2E теперь гоняется с пустым `AUTH_URL` — то есть с выводом базового URL из запроса, как на деплое (D-30).

  E2E владеет своей БД: PGlite за протоколом PostgreSQL, миграции применены до открытия порта, ни контейнера, ни креда (D-18) — CI не держит ничего настоящего (S1). Приложение выбирает драйвер по строке подключения; прод-путь (Neon HTTP) не изменился ни на байт.
