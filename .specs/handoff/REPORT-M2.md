### СДЕЛАНО — кластер 24–30 (ядро корректности)

**Задача 24 — таблица переходов.** `src/modules/workflow/transition-table.ts`: плоский литеральный массив из **33 рёбер** над **17 позициями** (interview + 5 spec-стадий × 3 подстадии + complete). Каждая строка — `{id, from, to, gate}`, гейт по идентификатору; id выводится из концов ребра и разойтись с ними не может. Состав: interview-выход; по каждой spec-стадии 2 форвардных + 3 безусловных обратных ребра (FR-007 AC-5); 3 межстадийных `review→next/collect`; развилка `tasks.review → complete | quality.collect`; `quality.review → complete`; `complete → quality.collect` — **единственное** ребро из `complete` (FR-007 AC-8). Пара вне таблицы → `TRANSITION_NOT_IN_TABLE`, из `complete` → `SESSION_SEALED`.

**Задачи 25–27 — снапшот и гейты.** `WorkflowSnapshot` — плоский сериализуемый объект; ассемблер укладывается в **задокументированные ≤4 statement'а** (ровно 4, заасserчено прокси-счётчиком `execute`). Гейты — чистые синхронные функции без какого-либо I/O (NFR-012 AC-1): `interviewGate` называет **каждое** незакрытое условие (`unmet: grounding-input|answered-round|summary`, D-32), `collectGate` (≥1 отвеченный раунд стадии, D-33), `approvalGate` (**последняя** ревизия одобрена — редрафт после request-changes закрывает гейт заново), `reviewGate`, `completionGate` (4 core-файла имеют одобренную ревизию), `roundBudgetGate` (бюджет из `MAX_ROUNDS_PER_STAGE` через снапшот — конфигурация без правки кода). Разделение `specApproved` / `approvedRevisionExists` сделано именно из-за пары FR-009 AC-4 ↔ FR-020 AC-2 и покрыто отдельными негативными кейсами.

**Задача 28 — applyTransition.** Оценка всегда до записи; запись — под версией, на которой собирался снапшот: гонка двух переходов даёт ровно один успех и один `CONFLICT` (тест на PGlite), отклонённый гейт не пишет ничего.

**Задача 29 — эндпоинт.** `POST /api/sessions/:id/transition`: 409 с машиночитаемой причиной (`GATE_REJECTED` + `reason` + `unmet`; `CAPABILITY_NOT_REGISTERED` и `ROUND_LIMIT_REACHED` — собственными кодами по таблице ошибок solution.md; `CONFLICT` отдельно). HTTP-уровневые тесты гоняют **настоящий handler против настоящего PostgreSQL** (PGlite), замоканы только Auth.js-сессия и процессный db-handle: 401/404-неотличимость/422/409+reason/200+touch/гонка→CONFLICT.

**Задача 30 — исчерпывающая матрица.** `__tests__/transition-matrix.test.ts`:
- **все 289 упорядоченных пар** позиций перечислены программно; все 256 нетабличных пар отклонены под минимальным И под максимально удовлетворёнными снапшотами обеих конфигураций Quality — никакое состояние не открывает нетабличное ребро;

### СДЕЛАНО — интервью 31–38

**Задача 31 — схема.** Миграция `0004`: уникальности `(session,stage,round_number)` и `(session,stage,name)` (DR-13), CHECK стадий из тех же кортежей D-15, «ответ обязан нести содержание» (опции или непустой текст). Найденный при написании тестов дефект: `satisfied_by_round` с `ON DELETE RESTRICT` **ломал бы каскад удаления проекта** (RESTRICT проверяется немедленно, раньше второго пути каскада) — заменён на NO ACTION (проверка в конце statement'а), регрессионный тест каскада есть.

**Задача 32 — QuestionSetSchema.** 2–8 опций, single/multiple, обязательный `allowOther: true`, уникальные id вопросов и опций; наборы из 1 и 9 опций и без allowOther отклоняются; repair-once: валидация → один ремонт → валидация → `DRAFT_INVALID`, невалидный набор не персистится и не рендерится.

**Задача 33 — InterviewAgent.** Конвейер: текст модели → JSON (срез code-fence) → схема с детерминированным ремонтом (ремонт **ничего не изобретает** — только чинит allowOther/эхо стадии и отбрасывает нечинимое) → фильтр уже удовлетворённых потребностей (FR-005 AC-9) → раунд или «спрашивать нечего». Плюс reply-assessor (вердикт пересекается с объявленными потребностями раунда — выдуманное имя в реестр не попадает) и summary-агент (пустой результат → null, гейт остаётся закрыт). Весь milestone — на детерминированном стабе, LLM-ключи не использованы.

**Задачи 34–37 — карточки и маршруты.** `McqCard`: radio/checkbox по типу, **ровно один** free-text «other» на вопрос (рендерится из `allowOther` — конкурирующую опцию агент создать не может), reply-режим; пока карточка ждёт — генерация заблокирована. `POST /api/sessions/:id/rounds` (D-36): pending-раунд ре-презентуется (FR-017 AC-3), протухший указатель самоисцеляется, 4-й запрос — `409 ROUND_LIMIT_REACHED` со списком unmet needs. `POST /api/sessions/:id/answers` (D-37) — три формы: карточная (валидация строго против персистентного payload'а раунда: чужой вопрос/опция/двойной выбор в single/пропущенный вопрос → 422, и **ничего не записано**), reply (ответ сохраняется на pending-раунд → узкий follow-up при остатке бюджета, иначе `limit` с unmet needs) и fallback (прямые ответы на именованные потребности в пространстве `need:<имя>`, D-38). Ответы дуабельны до любого следующего шага (NFR-003 AC-1); повторная подача карточки → 409.

**Задача 38 — summary и гейт.** Summary обновляется после каждой принятой подачи interview-стадии и записывается только непустым; выход из interview проверен «в обе стороны» через настоящий transition-эндпоинт: до ответа — `409 INTERVIEW_INCOMPLETE` c `unmet: [answered-round, summary]`, после одной отвеченной карточки — 200. Утверждение агента гейт не открывает — у гейта просто нет такого входа (FR-006 AC-4).
