## Project Vision

Консольный планировщик личных дел — это минималистичный, быстрый и надежный инструмент для управления повседневными задачами непосредственно из терминала. Продукт ориентирован на индивидуальных пользователей (`single_user`), ценящих скорость работы клавиатуры, отсутствие лишнего графического интерфейса и полный контроль над своими данными. Программа позволяет мгновенно добавлять задачи с указанием конкретной даты, просматривать список дел на сегодня и отмечать задачи как выполненные. Все данные сохраняются локально на устройстве пользователя в простом текстовом формате, обеспечивая автономность и независимость от интернет-соединения или сторонних облачных провайдеров.

## Core Principles

*   **Локальность и автономность:** Все данные пользователя хранятся исключительно на его локальном компьютере. Приложение не требует подключения к сети Интернет, регистрации или создания учетных записей.
*   **Управление через аргументы командной строки (`arguments`):** Взаимодействие с планировщиком происходит мгновенно с помощью аргументов CLI, минуя интерактивные диалоги. Пользователь выполняет одну команду и сразу получает результат.
*   **Предсказуемость работы с датами (`strict_date`):** Система ожидает ввода даты в строго определенном формате. Никакой двусмысленности при парсинге дат — только валидные и четко заданные значения.
*   **Сохранение истории (`keep`):** Выполненные задачи не удаляются бесследно, а меняют свой статус, сохраняя историю активности пользователя для последующего анализа или отчетности.
*   **Информативность пустых состояний (`message_empty`):** Если на сегодня задач нет, программа не просто завершает работу с пустым экраном, а выводит строгое константное сообщение в стандартный поток вывода `stdout`, завершающееся символом перевода строки (`\n`): `На сегодня задач нет.`
*   **Быстрый сбой при ошибках (`crash_and_report`):** При возникновении непредвиденных ситуаций (например, повреждение файла данных) приложение завершает работу с аварийным кодом и выводит понятный отчет об ошибке для ее исправления.

## Technology Constraints

*   **Язык программирования:** Строго Python 3.10+. Использование других платформ разработки (таких как Node.js) или внешних тяжелых зависимостей запрещено. Разрешено использовать только встроенную стандартную библиотеку Python (например, `argparse`, `json`, `datetime`, `os`, `sys`).
*   **Формат хранения данных (`json`):** Локальная база данных представляет собой стандартный файл JSON. Использование внешних СУБД (PostgreSQL, MySQL, SQLite) запрещено.
*   **Локальная файловая система:** Чтение и запись производятся напрямую в локальный файл задач, путь к которому конфигурируется через переменную окружения или имеет фиксированный путь `~/.todo-tasks.json` в домашней директории пользователя в соответствии с правилами, описанными в разделе `Integration Points`.
*   **Формат ввода дат:** Строго ISO 8601 (`YYYY-MM-DD`). Любые другие форматы ввода должны отклоняться на этапе валидации аргументов.

## Architecture Constraints

*   **Интерфейс взаимодействия (`arguments`):**
    Приложение должно поддерживать вызовы со следующей структурой аргументов:
    *   Добавление задачи: `todo add "Текст задачи" [--date YYYY-MM-DD]`
        *   Параметр `--date` является опциональным. Если он не передан пользователем, приложение автоматически подставляет текущую системную дату в формате `YYYY-MM-DD`.
        *   При создании задачи поле `created_at` автоматически заполняется текущим системным временем в формате ISO 8601 в UTC (например, `YYYY-MM-DDTHH:MM:SSZ`).
        *   **Валидация текста задачи:** Текст задачи (параметр `"Текст задачи"`) проходит обязательную валидацию. Символы табуляции (`\t`) и перевода строки (`\n`) строго запрещены. При обнаружении этих символов утилита должна отклонить добавление, вывести информативное сообщение об ошибке в поток `stderr` и завершить работу с кодом выхода `1`.
    *   Просмотр задач на сегодня: `todo list` (выводит список задач, запланированных на текущую системную дату).
    *   Отметка задачи как выполненной: `todo done <task_id>` (где `<task_id>` — уникальный идентификатор задачи).
*   **Формат вывода списка задач:**
    При вызове команды `todo list` вывод должен осуществляться в стандартный поток `stdout`. Каждая задача должна быть выведена на новой строке в строго определенном табулированном формате:
    ```
    <id>\t<completed>\t<title>\t<due_date>
    ```
    Где:
    *   `<id>` — UUID v4 задачи.
    *   `\t` — символ табуляции.
    *   `<completed>` — строковое значение `true` (если задача выполнена) или `false` (если не выполнена).
    *   `<title>` — текст задачи (гарантированно не содержит `\t` и `\n` благодаря валидации при создании).
    *   `<due_date>` — дата в формате `YYYY-MM-DD`.
    
    **Сортировка списка задач:** Задачи в выводе команды `todo list` должны быть отсортированы по времени создания (поле `created_at`) в порядке возрастания (от более старых к более новым).
    
    Если список задач на сегодня пуст, программа выводит сообщение `На сегодня задач нет.` в стандартный поток вывода `stdout`, завершающееся символом перевода строки (`\n`).
*   **Обработка ошибок и исключительных ситуаций:**
    *   При передаче несуществующего или некорректного `<task_id>` для команды `todo done`, приложение должно вывести информативное сообщение об ошибке в поток ошибок `stderr` и завершить работу с кодом выхода `1`.
    *   Любые системные исключения (ошибки доступа к файлу, повреждение структуры JSON, неверный формат аргументов) должны перехватываться на верхнем уровне, выводить отчет об ошибке в поток `stderr` и завершать процесс с кодом выхода `1` (`crash_and_report`).
*   **Архитектурные слои:**
    1.  **CLI Entry Point (Парсер аргументов):** Отвечает за разбор входящих параметров командной строки, валидацию формата дат, валидацию текста задачи и вызов соответствующих сервисных методов.
    2.  **Domain Service (Бизнес-логика):** Содержит правила фильтрации задач на "сегодня", сортировки по времени создания, логику смены статуса задач и генерацию уникальных идентификаторов.
    3.  **Storage Adapter (Слой доступа к данным):** Отвечает за чтение и запись файла JSON, гарантируя атомарность операций записи (запись во временный файл с последующим переименованием во избежание повреждения данных).

## Testing Approaches

*   **Модульное тестирование (Unit Tests):**
    *   Тестирование парсера дат на строгое соответствие формату `YYYY-MM-DD` (включая проверку на несуществующие даты, например, 30 февраля).
    *   Тестирование логики валидации текста задачи (успешное прохождение валидации для корректных строк и вызов исключения при наличии `\t` или `\n`).
    *   Тестирование логики фильтрации задач на "сегодня" и их сортировки по полю `created_at` по возрастанию относительно переданной системной даты.
*   **Интеграционное тестирование (Integration Tests):**
    *   Проверка полного цикла работы: запуск команды добавления задачи (как с параметром `--date`, так и без него), чтение файла JSON и проверка физического наличия новой записи с корректной датой.
    *   Проверка поведения при пустом списке задач на сегодня (проверка точного вывода сообщения `На сегодня задач нет.` в `stdout`).
    *   Проверка корректности изменения флага `completed` в JSON файле при вызове команды `todo done`.
    *   Проверка строгого соответствия формата вывода `todo list` установленной схеме с разделителями табуляцией, а также корректного порядка сортировки задач.
*   **Тестирование устойчивости (Error Handling Tests):**
    *   Эмуляция поврежденного JSON-файла (невалидный синтаксис) и проверка, что приложение завершается аварийно (`crash_and_report`) с кодом возврата `1`, не пытаясь перезаписать испорченные данные пользователя.
    *   Проверка поведения при попытке выполнить несуществующую задачу (проверка вывода ошибки в `stderr` и кода завершения `1`).

## Coding Standards

*   **Чистота кода:** Использование строгой типизации (Type Hints в Python). Все сигнатуры функций должны быть типизированы.
*   **Форматирование:** Обязательное использование автоматического форматировщика кода `black` и линтера `flake8`/`pylint`.
*   **Структура JSON:**
    Корневым элементом JSON-файла является массив объектов `[ ... ]`. Каждая задача внутри этого массива должна представлять собой JSON-объект со строго определенными полями и типами данных. Идентификатор `id` должен быть строго строкой UUID v4. Поле `created_at` должно автоматически заполняться в формате ISO 8601 в UTC (`YYYY-MM-DDTHH:MM:SSZ`) при добавлении новой задачи. Пример структуры всего файла:
    ```json
    [
      {
        "id": "string (UUID v4)",
        "title": "string",
        "due_date": "string (YYYY-MM-DD)",
        "completed": "boolean",
        "created_at": "string (ISO datetime YYYY-MM-DDTHH:MM:SSZ)"
      }
    ]
    ```
*   **Логирование:** Отсутствие постороннего или отладочного вывода в стандартный поток вывода (`stdout`). Только чистый пользовательский интерфейс. Все системные предупреждения, ошибки и стек-трейсы направжаются строго в `stderr`.

## Security Constraints

*   **Открытый текст (`plaintext`):** Данные хранятся в незашифрованном виде. Безопасность данных обеспечивается правами доступа к файлу на уровне операционной системы. Файл данных по умолчанию должен создаваться с правами доступа, разрешающими чтение и запись только текущему владельцу (права `600` в Unix-системах).
*   **Отсутствие сетевой активности:** Приложение не должно совершать никаких сетевых запросов, отправлять телеметрию или обращаться к внешним API.
*   **Безопасность ввода:** Валидация входных аргументов на отсутствие инъекций управляющих символов в terminal, включая строгий запрет на табуляции и переводы строк в названии задачи.

## Performance Targets

*   **Время холодного запуска:** Менее 100 миллисекунд для любой команды. Пользователь не должен ощущать задержку при вызове утилиты в консоли.
*   **Потребление памяти:** Менее 50 МБ оперативной памяти при выполнении операций.
*   **Эффективность хранения:** Чтение и перезапись файла JSON должны происходить в один проход, так как размер файла для одного пользователя (`single_user`) в рамках ведения личных дел редко превышает несколько тысяч записей (несколько сотен килобайт).

## Integration Points

*   **Интеграция с файловой системой:**
    *   Путь к файлу данных определяется переменной окружения `TODO_DATA_PATH`.
    *   Если переменная окружения не задана, используется путь по умолчанию `~/.todo-tasks.json`.
    *   **Разрешение путей:** Путь, содержащий символ тильды (`~`), должен быть предварительно разрешен (раскрыт) до абсолютного пути к домашней директории пользователя с использованием стандартных средств Python (например, `os.path.expanduser` или `pathlib.Path.expanduser`) перед открытием файла или проверкой его существования.
*   **Интеграция с системным окружением (CLI):**
    *   Возврат кода `0` при успешном выполнении любой операции.
    *   Возврат кода `1` при возникновении критических ошибок (невалидная дата, наличие запрещенных символов в тексте задачи, отсутствие или повреждение файла данных, обращение к несуществующему ID задачи).
    *   Вывод списка задач в формате с табуляцией (`\t`), удобном для конвейерной обработки (pipe) другими консольными утилитами (например, `grep`, `awk` или `cut`).
