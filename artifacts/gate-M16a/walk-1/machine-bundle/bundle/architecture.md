## Overview

Консольный планировщик личных дел (CLI Task Planner) — это легковесное кроссплатформенное консольное приложение, предназначенное для быстрого, удобного и надежного управления персональными задачами непосредственно из терминала. Программа ориентирована на одного локального пользователя, гарантирует мгновенную скорость работы (холодный старт менее 50 мс) и минимальное потребление системных ресурсов (до 20 МБ оперативной памяти).

Основные функциональные возможности:
* Добавление задач с указанием названия и даты выполнения.
* Отображение списка дел на сегодня (включая невыполненные задачи с прошедшим сроком).
* Быстрая отметка задач как выполненных.
* Удаление задач с интерактивным подтверждением.
* Полная локальная автономность: данные сохраняются в локальном файле базы данных SQLite без шифрования (`sqlite_plain`).
* Автоматическое создание резервных копий базы данных перед операциями записи с ротацией до 5 файлов.

Приложение разрабатывается на языке Python версии 3.10 или выше без использования сторонних внешних библиотек. Все системные операции базируются исключительно на стандартных модулях Python (`sqlite3`, `argparse`, `os`, `sys`, `datetime`), обеспечивая независимость и простоту поддержки продукта.

## High-Level Architecture Design

Приложение спроектировано как локальный монолитный CLI-инструмент. Процесс обработки данных, логика интерфейса и работа с файловой системой происходят в рамках единого потока выполнения ОС. 

### Диаграмма компонентов системы

```
+---------------------------------------------------------------+
|                       Интерфейс (CLI)                         |
|                                                               |
|   Пользователь  <--->  [ CLI Controller (task_planner.cli) ]  |
+---------------------------------------------------------------+
                                 |
                                 v (Вызовы бизнес-логики)
+---------------------------------------------------------------+
|                      Бизнес-логика                            |
|                                                               |
|                 [ Core Manager (task_planner.core) ]          |
+---------------------------------------------------------------+
                                 |
                                 v (Запросы данных / Бэкап)
+---------------------------------------------------------------+
|                       Уровень данных                          |
|                                                               |
|             [ Storage Provider (task_planner.storage) ]       |
|                                |                              |
|                                v (Делегирование копирования)  |
|             [ Backup Service (task_planner.backup) ]          |
+---------------------------------------------------------------+
                                 |
                                 v (Локальные файлы)
+---------------------------------------------------------------+
|       Файловая система: tasks.db  и  tasks_*.db.bak           |
+---------------------------------------------------------------+
```

### Основные сценарии взаимодействия компонентов

1. **Инициализация:** При вызове команды `Storage Provider` определяет путь к рабочему файлу базы данных `tasks.db` с помощью встроенного алгоритма. В случае отсутствия целевых родительских директорий они автоматически создаются. Если база данных не существовала, разворачивается SQL-схема.
2. **Получение данных (Команда `list`):**
   * `CLI Controller` обрабатывает вызов и передает управление в `Core Manager`.
   * `Core Manager` вычисляет локальное системное время, определяет критерии фильтрации и запрашивает данные у `Storage Provider`.
   * `Storage Provider` обращается к базе данных через транзакционное read-only соединение.
   * Полученные записи возвращаются в `CLI Controller`, который форматирует их в ASCII-таблицу с применением цветовых ANSI-кодов и выводит в `stdout`.
3. **Модификация данных (Команды `add`, `complete`, `delete`):**
   * Перед тем как внести изменения в БД, `Storage Provider` проверяет, существует ли физический файл `tasks.db` на диске.
   * Если файл уже существует, вызывается метод `Backup Service`, который выполняет резервное копирование текущего состояния БД и осуществляет ротацию старых копий.
   * После завершения процесса бэкапа выполняется параметризованный SQL-запрос на запись данных.

## System Modules

Проект структурирован в виде единого пакета `task_planner`, разделенного на следующие функциональные модули:

### 1. `task_planner.cli` (CLI Controller)
* **Назначение:** Обработка аргументов командной строки, взаимодействие с пользователем через стандартные потоки (`stdout`, `stderr`, `stdin`), валидация входных данных на уровне интерфейса.
* **Ключевые функции:**
  * Парсинг команд и аргументов с использованием встроенного модуля `argparse`.
  * Валидация идентификаторов задач: при передаче нецелочисленного значения аргумента `<id>` (например, строки `'abc'`) для команд `complete` или `delete` модуль должен незамедлительно вывести сообщение `"Ошибка: ID задачи должен быть целым числом."` в поток `stderr` и завершить выполнение с кодом `1`, предотвращая некорректный парсинг или сбои базы данных.
  * Форматирование ASCII-таблицы: расчет ширины колонок, выравнивание данных (числовой ID — по правому краю, текстовые поля — по левому краю).
  * Раскраска вывода с использованием ANSI-кодов: зеленый (`\033[32m`) для выполненных строк, красный (`\033[31m`) для просроченных задач, сброс стилей (`\033[0m`).
  * Получение интерактивного подтверждения удаления задач через `sys.stdin`.
  * Управление кодами возврата процесса (Exit Codes).

### 2. `task_planner.core` (Core Manager)
* **Назначение:** Описание бизнес-сущностей, проверка бизнес-правил, фильтрация данных.
* **Ключевые функции:**
  * Валидация календарного формата дат `YYYY-MM-DD` через `datetime.date.fromisoformat`.
  * Определение текущей локальной системной даты для автоматической подстановки значения срока выполнения (due date).
  * Определение критериев отбора задач на сегодня: `due_date == today` (все задачи) ИЛИ `due_date < today AND is_completed == 0` (просроченные невыполненные задачи).

### 3. `task_planner.storage` (Storage Provider)
* **Назначение:** Работа с локальной СУБД SQLite, инициализация схемы, управление транзакциями.
* **Ключевые функции:**
  * Разрешение пути хранения `tasks.db` с учетом переменных окружения и специфики операционной системы.
  * Создание папок хранения и инициализация базы данных.
  * Выполнение безопасных параметризованных SQL-запросов (Prepared Statements).
  * Назначение прав доступа `0o600` на создаваемые файлы в Unix-подобных системах.

### 4. `task_planner.backup` (Backup Service)
* **Назначение:** Создание резервных копий рабочей БД и управление жизненным циклом бэкапов (ротация).
* **Ключевые функции:**
  * Создание полной физической копии файла базы данных `tasks.db` до совершения транзакции записи.
  * Именование файлов резервных копий по шаблону `{имя_файла_БД_без_расширения}_{YYYYMMDD_HHMMSS_ffffff}.db.bak`, где базовое имя файла — `tasks`, а дата и время берутся на момент выполнения операции бэкапа. Итоговое имя имеет вид: `tasks_YYYYMMDD_HHMMSS_ffffff.db.bak`.
  * Поиск и ротация бэкапов в директории БД: сканирование файлов по маске `tasks_*.db.bak`.
  * Если количество обнаруженных бэкапов превышает 5, автоматически удаляются самые старые файлы (определяемые по временной метке в их имени).
  * Изоляция ошибок резервного копирования: сбои при создании бэкапа или ротации не должны блокировать выполнение основной операции изменения данных (при возникновении сбоя выводится некритичное предупреждение в `stderr`).

### 5. `task_planner.__main__`
* **Назначение:** Обеспечение запуска приложения как исполняемого Python-модуля при вызове команды `python -m task_planner`.

## Data Model

Данные приложения хранятся локально в файле `tasks.db` базы данных SQLite.

### Схема таблицы `tasks`

```sql
CREATE TABLE IF NOT EXISTS tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    due_date TEXT NOT NULL,
    is_completed INTEGER NOT NULL DEFAULT 0
);
```

### Спецификация полей

| Имя поля | Тип данных SQLite | Ограничения | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Уникальный числовой идентификатор задачи. Используется для точечной адресации при изменении статуса или удалении. |
| `title` | `TEXT` | `NOT NULL` | Текстовое описание задачи. Не может быть пустым. |
| `due_date` | `TEXT` | `NOT NULL` | Дата выполнения задачи в строгом ISO-формате `YYYY-MM-DD`. Хранится как строка для упрощения лексикографического сравнения средствами SQL. |
| `is_completed` | `INTEGER` | `NOT NULL DEFAULT 0` | Статус выполнения: `0` — задача не выполнена, `1` — задача выполнена. |

### Разрешение пути хранения базы данных

Путь к файлу `tasks.db` рассчитывается динамически по следующему приоритетному алгоритму:

1. **Переопределение (Override):** Если в системе установлена переменная окружения `TASK_PLANNER_DB_PATH`, используется её точное значение как полный абсолютный путь к файлу базы данных. Данный механизм имеет высший приоритет.
2. **Unix-подобные ОС (GNU/Linux, macOS):** Если переменная окружения отсутствует, используется путь `~/.local/share/task_planner/tasks.db` (с раскрытием домашней директории через `os.path.expanduser`).
3. **Windows:** Если переменная окружения отсутствует, используется путь `%USERPROFILE%\AppData\Local\task_planner\tasks.db`.

Все промежуточные папки по вычисленному пути создаются автоматически во время инициализации базы данных.

## API / Protocol Design

Взаимодействие пользователя с приложением происходит локально через CLI. Ниже описаны спецификации команд, правила валидации аргументов, форматы вывода и соответствующие коды возврата.

### Спецификация CLI-команд

#### 1. Добавление задачи (`task add`)
* **Команда:** `task add "<title>" [--due <date>]`
* **Валидация параметров:**
  * `<title>`: Текст названия задачи. Если передан пустой текст `""` или строка, состоящая исключительно из пробелов, приложение выводит в `stderr` сообщение `"Ошибка: название задачи не может быть пустым."` и завершает работу с кодом `1`.
  * `--due`: Необязательный аргумент. Должен передаваться в формате `YYYY-MM-DD`. Если опущен, устанавливается текущая дата системы в формате `YYYY-MM-DD`.
  * Валидация даты: Если дата некорректна лексически или календарно, приложение выводит в `stderr` сообщение `"Ошибка: дата должна быть в формате YYYY-MM-DD."` и завершает работу с кодом `1`.
* **Успешный вывод (`stdout`):** `"Задача успешно добавлена с ID: {id}"`
* **Код возврата:** `0` — успех, `1` — ошибка валидации.

#### 2. Просмотр списка задач (`task list`)
* **Команда:** `task list`
* **Логика выборки данных:** На вывод поступают задачи, у которых `due_date` равен текущему дню на системных часах, а также все невыполненные задачи (`is_completed = 0`), у которых значение `due_date` хронологически меньше текущего дня.
* **Вывод пустого списка:** Если соответствующих задач нет, в поток `stdout` выводится текстовое сообщение:
  `«Нет задач на сегодня!»`
  Процесс завершается с кодом `0`.
* **Отображение таблицы:** Вывод формируется в виде структурированной ASCII-таблицы с фиксированным набором и порядком колонок: `ID`, `Название`, `Срок`, `Статус`.
  *Шаблон таблицы:*
  ```
  +----+----------------------+------------+--------+
  | ID | Название             | Срок       | Статус |
  +----+----------------------+------------+--------+
  | 12 | Купить молоко        | 2026-04-12 | [ ]    |
  | 15 | Сдать отчет          | 2026-04-15 | [v]    |
  +----+----------------------+------------+--------+
  ```
  Ширина каждой колонки рассчитывается динамически как `max_length + 2` (максимальная длина текстового значения в колонке, включая заголовок, плюс по одному пробелу отступа по бокам). Текстовые столбцы выравниваются по левому краю, числовой столбец `ID` — по правому краю.
  * **Визуальные стили и цвета (ANSI-коды):**
    * Выполненные задачи (`is_completed = 1`): Статус равен `[v]`. Строка окрашивается в зеленый цвет с помощью `\033[32m`.
    * Невыполненные на сегодня (`is_completed = 0`, `due_date == today`): Статус равен `[ ]`. Строка выводится в стандартном цвете терминала.
    * Невыполненные просроченные (`is_completed = 0`, `due_date < today`): Статус равен `[ ]`. Строка окрашивается в красный цвет с помощью `\033[31m`.
    * Каждая строка с измененным цветом завершается управляющим кодом сброса цвета `\033[0m`.
* **Код возврата:** `0`.

#### 3. Отметка задачи как выполненной (`task complete`)
* **Команда:** `task complete <id>`
* **Валидация ID:**
  * Если `<id>` не является целым числом (например, `abc` или `12.3`), приложение выводит в `stderr` сообщение `"Ошибка: ID задачи должен быть целым числом."` и завершает работу с кодом `1` (без обращений к БД).
  * Если задача с числовым `<id>` отсутствует в базе данных, приложение выводит в `stderr` сообщение `"Ошибка: задача с ID {id} не найдена."` и завершает работу с кодом `1`.
* **Успешный вывод (`stdout`):** `"Задача {id} успешно выполнена."`
* **Код возврата:** `0` — успех, `1` — ошибки валидации или отсутствие задачи.

#### 4. Удаление задачи (`task delete`)
* **Команда:** `task delete <id>`
* **Валидация ID и обработка подтверждения:**
  * Если `<id>` не является целым числом (например, `abc`), приложение выводит в `stderr` сообщение `"Ошибка: ID задачи должен быть целым числом."` и завершает работу с кодом `1` (диалог подтверждения не выводится).
  * Если задача отсутствует в базе данных, выводится в `stderr` сообщение `"Ошибка: задача с ID {id} не найдена."` и работа прекращается с кодом `1` (диалог подтверждения не выводится).
  * Если задача с числовым `<id>` найдена, приложение выводит в `stdout` запрос подтверждения:
    `"Вы действительно хотите удалить задачу {id}? (y/n): "`
  * Из стандартного потока ввода `sys.stdin` считывается ответ пользователя.
    * Если введен символ `y` или `Y`: запись удаляется, выводится `"Задача {id} успешно удалена."`, код возврата `0`.
    * Если введен символ `n`, `N`, пустая строка или любой другой символ: операция отменяется, выводится `"Удаление отменено."`, код возврата `0`.

## Security Architecture

Поскольку приложение является полностью локальным и однопользовательским, безопасность данных сфокусирована на защите от уязвимостей кода и разграничении локального доступа.

1. **Предотвращение SQL-инъекций:**
   Все запросы к SQLite реализуются строго через механизм параметризованных запросов СУБД (Prepared Statements). Передача параметров через интерполяцию или форматирование строк SQL-запроса категорически запрещена.

2. **Защита на уровне прав доступа файловой системы (Unix-подобные ОС):**
   При инициализации рабочего файла `tasks.db`, а также при создании любых файлов резервных копий `tasks_*.db.bak` в среде Linux или macOS, приложение явно устанавливает права доступа к файлу равными `0o600` (`chmod 600`), предоставляя права на чтение и запись исключительно владельцу процесса. В среде Windows используются стандартные унаследованные права директории `AppData`.

3. **Сетевая безопасность:**
   В коде приложения полностью отсутствуют импорты сетевых модулей, открытие сокетов, выполнение HTTP-запросов и механизмы передачи телеметрии.

## Deployment & Operations

### Сборка и дистрибуция

Сборка планировщика производится по стандартам современной инфраструктуры Python. В файле конфигурации пакета (например, `pyproject.toml`) регистрируется секция `console_scripts`, сопоставляющая команду `task` с главной функцией-точкой входа `task_planner.cli:main`.

У пользователя должны быть доступны два способа вызова приложения:
1. Запуск напрямую по имени команды в терминале:
   ```bash
   task list
   ```
2. Альтернативный запуск в качестве исполняемого модуля:
   ```bash
   python -m task_planner list
   ```

### Эксплуатационные требования к среде хранения

* Система автоматически создает промежуточные папки на диске при первом обращении к БД.
* Резервное копирование срабатывает автоматически непосредственно перед транзакцией записи в БД.
* Если процесс бэкапа падает (например, из-за нехватки дискового пространства), приложение выводит некритичное предупреждение в `stderr` и продолжает выполнение исходной операции записи, обеспечивая бесперебойную работу пользователя.

## Observability

Наблюдаемость состояния и поведения утилиты строится на стандартных механизмах терминального взаимодействия:

1. **Поток `stdout`:**
   * Списки задач в формате структурированной ASCII-таблицы.
   * Текстовые сообщения об успешных действиях пользователя.
   * Диалог-подтверждение перед удалением записи.

2. **Поток `stderr`:**
   * Ошибки валидации данных (ошибки парсинга дат, пустое название задачи, нецелочисленный формат ID).
   * Ошибки бизнес-логики (отсутствие задачи с запрашиваемым ID).
   * Системные ошибки доступа (отсутствие прав записи на диск) и некритичные предупреждения сбоев бэкапа.

3. **Коды завершения процессов (Exit Codes):**
   * `0` — успешное завершение работы команды.
   * `1` — возникновение ошибок валидации, отсутствие запрашиваемой задачи в базе данных, либо аппаратные/системные сбои при обработке.

## Testing Strategy

Стратегия тестирования обеспечивает стопроцентную воспроизводимость тестов в любых средах с использованием библиотеки `pytest`.

### 1. Юнит-тестирование
* Покрытие тестами функций валидации дат `YYYY-MM-DD` на корректных и заведомо ложных значениях.
* Тестирование логики фильтрации задач "на сегодня" в `Core Manager` с изоляцией системного времени через моки (например, `freezegun` или `unittest.mock`), чтобы исключить зависимость результатов тестов от даты их запуска.
* Тестирование логики предварительной валидации нецелочисленных ID в CLI контроллере: передача нецелочисленного идентификатора должна завершаться с кодом `1` и соответствующим текстом ошибки в `stderr`.

### 2. Интеграционное тестирование
* Изоляция тестов бэкенда: при запуске тестов переменная окружения `TASK_PLANNER_DB_PATH` переопределяется на временный путь в изолированной директории тестов (или используется база данных в памяти `:memory:`). Вся тестовая БД удаляется после прохождения тестов.
* Тестирование полного CRUD-цикла: добавление задачи -> проверка появления в БД -> отметка как выполненной -> проверка изменения статуса.
* Тестирование механизма авторезервирования: проверка того, что при выполнении модифицирующих команд создается файл бэкапа по шаблону `tasks_YYYYMMDD_HHMMSS_ffffff.db.bak`.
* Тестирование лимита ротации бэкапов: программное наполнение папки более чем 5 файлами бэкапов с последующим вызовом модифицирующей операции и проверка, что в папке осталось ровно 5 файлов резервных копий (самые старые удалены).

### 3. Тестирование интерфейса (CLI)
* Перехват вывода `stdout` и `stderr` для сравнения с ожидаемыми шаблонами таблиц и сообщений об ошибках.
* Мокирование потока `sys.stdin` для симуляции интерактивного выбора `y`/`n` в диалогах подтверждения удаления.

## Success Criteria

Продукт признается успешным и готовым к эксплуатации при выполнении следующих критериев:

1. **Функциональная полнота:** Реализованы все заявленные CLI-команды в соответствии со спецификацией.
2. **Производительность:** Холодный запуск приложения (от вызова команды в терминале до вывода таблицы в `stdout`) стабильно занимает менее 50 миллисекунд.
3. **Эффективность памяти:** Потребление ОЗУ процессом не превышает установленного лимита в 20 МБ.
4. **Устойчивость к сбоям бэкапа:** При искусственной блокировке прав на создание бэкапа (например, выставление `chmod 400` на родительскую директорию резервных копий) приложение выводит предупреждение в `stderr`, но успешно записывает данные в основной файл `tasks.db` и возвращает код `0`.
5. **Безопасность прав доступа:** Файлы базы данных и бэкапов в Unix-системах создаются исключительно с правами доступа `0o600`.
6. **Корректность обработки ошибок ID:** При попытке передать нецелочисленный идентификатор в команды `complete` или `delete` приложение гарантированно прерывает выполнение, возвращает код `1` и выводит сообщение в `stderr`, предотвращая некорректную работу СУБД.

## Key Solution Decisions

### 1. Выбор SQLite plain вместо JSON/CSV файлов
* **Обоснование:** Использование SQLite гарантирует транзакционную атомарность (ACID). Если в процессе записи произойдет сбой (например, отключение терминала), база данных не будет повреждена. Кроме того, SQLite встроен в стандартную библиотеку Python и не требует развертывания дополнительных сервисов.

### 2. Локальная изоляция без внешних библиотек
* **Обоснование:** Использование исключительно встроенных модулей минимизирует время импорта библиотек на старте, обеспечивая целевое время отклика менее 50 мс. Отсутствие сетевых пакетов исключает проблемы безопасности и гарантирует стабильную автономную работу.

### 3. Формат хранения дат ISO 8601 (`YYYY-MM-DD`)
* **Обоснование:** SQLite не имеет встроенного типа даты. Хранение даты в текстовом формате `YYYY-MM-DD` делает данные легко читаемыми при ручном просмотре БД и позволяет использовать эффективное лексикографическое сравнение строк на уровне SQL-запросов.

### 4. Временные метки с точностью до микросекунд в бэкапах
* **Обоснование:** Шаблон `tasks_YYYYMMDD_HHMMSS_ffffff.db.bak` с микросекундами гарантирует уникальность имен файлов бэкапов при частом вызове модифицирующих команд за короткий промежуток времени и исключает коллизии имен при ротации.

### 5. Валидация идентификаторов до обращения к базе данных
* **Обоснование:** Проверка того, что переданный ID является целым числом, на этапе CLI-парсинга позволяет избежать некорректных SQL-запросов и обеспечивает единообразный вывод понятных ошибок пользователю с кодом возврата `1`.
