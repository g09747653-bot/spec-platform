## Project Vision

Проект представляет собой консольный планировщик личных дел (CLI Task Planner), ориентированный на максимальную простоту, надежность и скорость работы для одного пользователя. Основная цель — предоставить инструмент, который позволяет мгновенно фиксировать задачи с датами выполнения, просматривать текущий список дел на сегодня и быстро отмечать выполненное непосредственно из терминала. Приложение исключает перегруженность сложными интерфейсами и сетевыми зависимостями, фокусируясь на локальной независимости и долговечности хранения данных.

## Core Principles

* **Локальная автономность:** Все данные хранятся исключительно на устройстве пользователя. Приложение не зависит от наличия интернет-соединения или внешних облачных сервисов.
* **Предсказуемость и надежность:** Использование проверенных технологий для хранения данных (SQLite) гарантирует транзакционную целостность и защиту от повреждения файлов при внезапном закрытии терминала.
* **Минимальное трение:** Добавление и выполнение задач должны требовать минимального количества нажатий клавиш. Интерфейс оптимизирован под быструю слепую печать.
* **Бережное отношение к данным:** Автоматическое резервное копирование защищает пользователя от случайной потери списка задач при сбоях операционной системы или диска.

## Technology Constraints

* **Платформа и ОС:** Кроссплатформенность. Приложение должно запускаться без изменений в средах Windows, macOS и GNU/Linux.
* **Язык разработки:** Python версии 3.10 или выше. Использование стандартной библиотеки Python является приоритетным для обеспечения простоты поддержки и кроссплатформенности.
* **Хранилище данных:** База данных SQLite без шифрования (`sqlite_plain`).
* **Алгоритм выбора пути хранения базы данных:** Для обеспечения стабильности тестирования и исключения потери или дублирования данных при запуске утилиты из разных рабочих каталогов, путь к файлу БД `tasks.db` определяется по следующему алгоритму:
  * **Переопределение для тестов (Override):** Если в системе установлена переменная окружения `TASK_PLANNER_DB_PATH`, приложение обязано использовать значение этой переменной в качестве полного пути к файлу базы данных SQLite. Данный механизм имеет наивысший приоритет.
  * **Unix-подобные системы (GNU/Linux, macOS):** Если переменная окружения отсутствует, используется путь `~/.local/share/task_planner/tasks.db` (в соответствии со спецификацией XDG Base Directory).
  * **Windows:** Если переменная окружения отсутствует, используется путь `%USERPROFILE%\AppData\Local\task_planner\tasks.db`.
  * Приложение должно автоматически создавать все промежуточные родительские директории при первом запуске, если они отсутствуют.
* **Зависимости:** Минимизация внешних зависимостей. Использование встроенных библиотек для работы с CLI (например, `argparse`) и базы данных (`sqlite3`).

## Architecture Constraints

* **Однопользовательская архитектура:** Система проектируется строго под обслуживание одного локального пользователя. Нет необходимости в механизмах аутентификации, сессий и разграничения прав доступа внутри приложения.
* **Модульная структура:**
  * **Модуль интерфейса (CLI Controller):** Отвечает за парсинг аргументов командной строки, форматирование вывода в терминал (таблицы, цвета) и обработку пользовательского ввода.
    * **Конфигурация запуска и упаковка:** 
      Для возможности вызова утилиты напрямую по имени `task` в консоли, проект должен настраивать секцию `console_scripts` (например, в `pyproject.toml` при использовании современных инструментов сборки), связывая команду `task` с главной функцией-точкой входа (например, `task_planner.cli:main`). Дополнительно должна быть обеспечена возможность запуска модуля в режиме разработки с помощью стандартной команды `python -m task_planner`.
    * **Спецификация CLI-команд:**
      * `add "<title>"` — Добавляет новую задачу.
        * Аргументы/Флаги: `--due` (необязательный) принимает дату в формате `YYYY-MM-DD`. Если флаг не передан, поле `due_date` автоматически заполняется текущей локальной датой системы в формате `YYYY-MM-DD`.
        * Примеры:
          * `task add "Купить молоко"` (создаст задачу с текущей датой)
          * `task add "Сдать отчет" --due 2026-04-15`
      * `list` — Отображает список задач на сегодня (задачи, у которых `due_date` равен текущей локальной дате, а также все невыполненные задачи с прошедшей датой).
        * **Формат вывода:** Задачи выводятся в виде структурированной текстовой таблицы со следующими колонками в указанном порядке: `ID`, `Название`, `Срок`, `Статус`.
        * **Визуальное отображение статусов:**
          * Выполненные задачи: в колонке `Статус` отображается символ `[v]`, вся строка или колонка статуса окрашивается в зеленый цвет (ANSI-код `\033[32m`).
          * Невыполненные задачи на сегодня: в колонке `Статус` отображается символ `[ ]`, строка выводится стандартным цветом терминала.
          * Просроченные невыполненные задачи (срок выполнения меньше текущей даты): в колонке `Статус` отображается символ `[ ]`, строка окрашивается в красный цвет (ANSI-код `\033[31m` или `\033[1;31m`).
        * **Пустой список задач:** Если на сегодня нет задач и отсутствуют просроченные невыполненные дела, приложение выводит текст-плейсхолдер: `«Нет задач на сегодня!»` и завершает работу.
        * Пример: `task list`
      * `complete <id>` — Отмечает задачу с указанным идентификатором как выполненную.
        * Пример: `task complete 12`
      * `delete <id>` — Удаляет задачу с указанным идентификатором. Данная команда требует интерактивного подтверждения от пользователя перед удалением.
        * Пример: `task delete 12`
  * **Бизнес-логика (Core Manager):** Управляет сущностями задач (Task), валидацией дат и статусов.
  * **Уровень данных (Storage Provider):** Реализует CRUD-операции над локальной БД SQLite, а также инкапсулирует логику резервного копирования.
    * **Схема базы данных:** Данные сохраняются в таблице `tasks` со следующей структурой:
      * `id`: `INTEGER PRIMARY KEY AUTOINCREMENT` — уникальный идентификатор задачи.
      * `title`: `TEXT NOT NULL` — название (описание) задачи.
      * `due_date`: `TEXT NOT NULL` — дата выполнения задачи в формате `YYYY-MM-DD`.
      * `is_completed`: `INTEGER NOT NULL DEFAULT 0` — статус выполнения задачи (0 — не выполнена, 1 — выполнена).
* **Стратегия резервного копирования:** Реализовано автоматическое создание резервных копий (`auto_backup`) по следующей схеме:
  * **Условие создания:** Перед выполнением любой операции, изменяющей данные (добавление, изменение статуса, удаление), система создает резервную копию файла базы данных. Резервная копия создается только при условии, что файл базы данных `tasks.db` уже физически существует на диске (чтобы предотвратить ошибки `FileNotFoundError` при первом запуске приложения до инициализации базы данных).
  * **Директория хранения:** Резервные копии сохраняются в той же директории, где находится основной файл базы данных (`tasks.db`).
  * **Шаблон именования:** Файлы резервных копий именуются по шаблону `tasks_YYYYMMDD_HHMMSS.db.bak`, где `YYYYMMDD_HHMMSS` — дата и время запуска операции создания бэкапа.
  * **Ротация и лимиты:** Система поддерживает стратегию ротации, сохраняя не более 5 последних резервных копий. При создании новой копии, если общее число бэкапов в директории превышает 5, автоматически удаляются самые старые файлы резервных копий (определяемые по временной метке в имени файла).

## Testing Approaches

* **Юнит-тестирование:**
  * Покрытие тестами функций валидации и парсинга дат.
  * Изолированное тестирование бизнес-логики с использованием моков (Mock) для системного времени, чтобы гарантировать корректность фильтрации задач "на сегодня".
* **Интеграционное тестирование:**
  * Использование переменной окружения `TASK_PLANNER_DB_PATH` для перенаправления записи БД во временную директорию тестового окружения с автоматическим удалением после прохождения тестов.
  * Тестирование слоя данных с использованием временных баз данных SQLite, разворачиваемых в памяти (`:memory:`) или во временной директории.
  * Проверка полного цикла: создание задачи -> отображение в списке -> отметка выполненной -> проверка изменения статуса в БД.
* **Тестирование CLI:**
  * Проверка корректности кодов возврата процесса (Exit Codes) при успешных операциях (0) и при возникновении ошибок валидации или отсутствия файлов (не-0).

## Coding Standards

* **Чистота кода:** Соблюдение стандартов форматирования кода PEP 8 для Python с использованием статических анализаторов `flake8` и форматировщика `black`.
* **Типизация:** Использование строгой статической типизации (Type Hinting) для минимизации ошибок на этапе разработки.
* **Обработка ошибок:**
  * Ошибки парсинга дат должны выводить понятные пользователю сообщения с примерами корректных форматов ввода.
  * Ошибки доступа к файлу базы данных (например, отсутствие прав на запись) должны перехватываться с выводом информативного сообщения, предотвращая падение рантайма по Unhandled Exception.
* **Документирование:** Каждая ключевая функция и класс должны быть снабжены кратким описанием (Docstrings) на русском или английском языке.

## Security Constraints

* **Локальный доступ:** Полное отсутствие сетевых сокетов, HTTP-запросов и телеметрии. Приложение не должно запрашивать доступ в сеть в правилах брандмауэра.
* **Безопасность СУБД:** Использование параметризованных SQL-запросов (Prepared Statements) для всех операций с БД с целью полного исключения SQL-инъекций, даже несмотря на то, что ввод осуществляется локальным пользователем.
* **Шифрование данных:** База данных хранится в открытом виде (`sqlite_plain`). Безопасность файла делегируется правам доступа файловой системы операционной системы:
  * На Unix-подобных операционных системах (GNU/Linux, macOS) файлу базы данных при создании должны принудительно назначаться права доступа, разрешающие чтение и запись только текущему владельцу процесса (права `0o600` / `chmod 600`). К создаваемым файлам резервных копий (`*.db.bak`) должны принудительно применяться те же самые права доступа `0o600` (`chmod 600`) во избежание создания небезопасных копий по умолчанию.
  * На операционных системах семейства Windows используются стандартные права создаваемого файла в директории AppData, без необходимости вызова специфичных системных API (таких как работа с ACL через pywin32).
* **Уровень подтверждений:** Запросы на подтверждение действий выводятся только при операциях удаления (`confirm_on_delete_only`). Операции добавления и отметки выполнения происходят мгновенно без дополнительных диалогов "Да/Нет".

## Performance Targets

* **Время запуска приложения:** Время от нажатия клавиши Enter в консоли до вывода списка задач не должно превышать 50 миллисекунд.
* **Эффективность памяти:** Потребление оперативной памяти процессом планировщика не должно превышать 15-20 МБ.
* **Использование диска:** Минимизация операций записи. Запись в БД происходит только при фактическом изменении данных пользователем.

## Integration Points

* **Внешние интеграции:** Отсутствуют согласно требованию локального использования (`strictly_local`). Приложение является полностью изолированным.
* **Интеграция с ОС:**
  * Чтение системных переменных окружения для определения путей к домашней директории пользователя (для хранения файла БД по умолчанию).
  * Поддержка чтения переменной окружения `TASK_PLANNER_DB_PATH` для кастомного переопределения пути к базе данных в рабочих или тестовых сценариях.
  * Стандартные потоки ввода-вывода:
    * `stdout` — для вывода списков задач и успешных уведомлений.
    * `stderr` — для вывода критических ошибок и предупреждений.
    * `stdin` — для получения интерактивного подтверждения при удалении задач.
