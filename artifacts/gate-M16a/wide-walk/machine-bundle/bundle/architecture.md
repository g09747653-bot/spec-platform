## Overview

Этот документ описывает архитектурное и техническое решение для набора из десяти независимых консольных утилит на Node.js: `temperature-converter`, `word-counter`, `password-generator`, `case-converter`, `roman-numerals`, `palindrome-checker`, `json-formatter`, `lorem-ipsum-generator`, `percentage-calculator`, `countdown-timer`. Он опирается на принципы, зафиксированные в `constitution.md`, и контракт, зафиксированный в `requirements.md`, и переводит их в конкретную архитектуру: как устроен репозиторий, из каких модулей состоит каждая утилита, какие данные передаются между её слоями, как выглядит протокол взаимодействия с пользователем (CLI как единственный "API"), как обеспечивается безопасность в отсутствие сети и состояния, как утилиты разворачиваются, как диагностируются и как тестируются.

Центральное архитектурное напряжение этого проекта — сочетание двух требований, которые в обычном проекте разрешались бы общей библиотекой: **отсутствие общего кода** между утилитами и **единообразие интерфейса** между ними. Решение, принятое во всём документе — согласованность достигается не общим модулем, а общим *шаблоном*, который вручную воспроизводится в каждой из десяти независимых кодовых баз. Это осознанный компромисс: он увеличивает объём дублируемого кода, но сохраняет главное свойство продукта — каждую утилиту можно понять, открыв ровно два её файла, не уходя в чужой каталог и не разбираясь в общей инфраструктуре.

Продукт не имеет сетевого API, базы данных, серверного компонента или UI — вся "система" исполняется локально, в терминале одного человека, разово при каждом вызове. Соответственно многие типовые разделы архитектурного документа (протокол, данные, деплой, наблюдаемость) здесь переосмыслены применительно к автономному CLI-инструменту, а не к сервису.

## High-Level Architecture Design

### Топология репозитория

Репозиторий — плоский, без корневого `package.json`, без workspaces и без общего кода:

```
/
├── temperature-converter/
├── word-counter/
├── password-generator/
├── case-converter/
├── roman-numerals/
├── palindrome-checker/
├── json-formatter/
├── lorem-ipsum-generator/
├── percentage-calculator/
├── countdown-timer/
└── README.md            (создаётся отдельным финальным шагом)
```

Каждая директория верхнего уровня — это независимый npm-пакет с собственным жизненным циклом: своей версией, своим `node_modules`, своими тестами, своей установкой. Между директориями не существует ни одной ссылки времени исполнения (`require('../other-utility/...')` запрещён архитектурно и должен отсутствовать в коде).

### Архитектура одной утилиты (повторяется десять раз)

Каждая утилита следует одному и тому же двухслойному шаблону, который является единственным механизмом переиспользования — переиспользуется не код, а *форма*:

```
<utility-name>/
├── package.json      # bin, зависимости, scripts: start/test
├── cli.js             # слой ввода-вывода: argv, stdin, stdout, stderr, exit code
├── lib.js              # слой чистой логики: только функции, без побочных эффектов
└── test/
    └── *.test.js       # unit-тесты lib.js + process-тесты cli.js
```

Разделение на `cli.js` и `lib.js` — не стилистическое, а архитектурное требование:

- `lib.js` не импортирует `fs`, `process`, `readline` и не выполняет ввод-вывод; это чистые функции, принимающие данные и возвращающие данные (или бросающие типизированную ошибку домена — см. раздел Data Model). Это позволяет тестировать всю бизнес-логику без порождения дочернего процесса.
- `cli.js` отвечает исключительно за оболочку: разбор `process.argv`, чтение `stdin` при необходимости, вызов `lib.js`, форматирование результата в `stdout`/`stderr`, установку `process.exitCode`. `cli.js` не содержит вычислительной логики домена.

Эта граница — то место, где "консистентность через соглашение" становится проверяемой: любая утилита, в которой валидация или форматирование просочились из `lib.js` в `cli.js` (или наоборот), нарушает архитектуру, даже если внешнее поведение корректно.

### Почему не общий пакет

Рассматривался и отклонён альтернативный вариант — вынести общий CLI-хелпер (`parseArgs`, `readStdinIfPiped`, `printError`) в общий npm-пакет или в локальный `file:`-зависимость. Он был отклонён, потому что:

- он создаёт скрытую связанность: изменение общего хелпера способно тихо сломать все десять утилит одновременно, что прямо противоречит принципу `read_source` (диагностика через чтение только двух файлов конкретной утилиты);
- он требует версионирования и синхронизации, что для личного инструмента, вызываемого раз в месяцы, создаёт больше сложности, чем экономит;
- дублируемый объём кода (разбор флагов, `--help`, обработка ошибок) — по объективной оценке несколько десятков строк на утилиту, что не является значимой инженерной ценой за полную независимость.

### Логическая схема потока данных

Единый поток одинаков для всех утилит, кроме `countdown-timer` (см. ниже):

```
argv / stdin ──▶ cli.js: parse & validate shape ──▶ lib.js: pure transform ──▶ cli.js: format ──▶ stdout (+ optional --out file)
                                                                                     │
                                                                                     └─▶ (ошибка) ──▶ stderr, exit 1
```

`countdown-timer` — единственная утилита с продолжённым во времени процессом: `cli.js` организует `setInterval`-цикл, на каждом тике вызывая чистую функцию `lib.js`, вычисляющую следующее отображаемое значение и признак завершения, что сохраняет тот же принцип (таймер как *чистая функция состояния*, а не как код, перемешивающий тайминг и форматирование).

## System Modules

Ниже перечислены десять модулей системы. Модуль в данном контексте — это независимая утилита-пакет; общего "оркестрирующего" модуля не существует.

| Модуль (директория / команда) | Назначение | Ключевой вход | Ключевой выход |
|---|---|---|---|
| `temperature-converter` | конвертация температуры между `c`/`f`/`k` | `--value`, `--from`, `--to` либо строка stdin `"<value> <from> <to>"` | одна строка `<число> <UNIT>` |
| `word-counter` | подсчёт строк/слов/символов в тексте | `--file <path>` либо текст из stdin | три строки `lines/words/chars` |
| `password-generator` | генерация случайных паролей | `--length`, `--count`, `--no-*`, `--symbols-set` | N строк-паролей |
| `case-converter` | преобразование регистра/стиля строки | `--text`/stdin, `--mode` | одна строка результата |
| `roman-numerals` | двунаправленная конвертация арабских чисел и римских цифр | `--number`/`--roman`/stdin | одна строка результата |
| `palindrome-checker` | проверка палиндрома | `--text`/stdin, `--strict` | `yes`/`no` |
| `json-formatter` | pretty-print JSON-файла | `--file`/stdin, `--indent` | отформатированный JSON |
| `lorem-ipsum-generator` | детерминированная генерация текста-заполнителя | `--paragraphs`/`--words`/`--sentences` | сгенерированный текст |
| `percentage-calculator` | вычисления процентов (`of`/`share`/`change`) | `--mode` + соответствующие числовые флаги | одна строка-число |
| `countdown-timer` | обратный отсчёт с финальным сигналом | `--duration`, `--quiet` | поток строк `MM:SS` + финальный блок |

### Внутренняя структура модуля (общая для всех десяти)

- **`cli.js`** — единственная точка входа процесса (shebang `#!/usr/bin/env node`). Обязанности: обработка `-h/--help` раньше любой другой валидации; разбор флагов; принятие решения о fallback на `stdin` (где применимо); вызов `lib.js`; запись в `stdout`/файл `--out` (где применимо); перехват исключений из `lib.js` и их перевод в единственную строку `stderr` с `process.exitCode = 1`.
- **`lib.js`** — модуль чистых функций домена. Экспортирует одну или несколько именованных функций (например, `convert(value, from, to)`, `countWords(text)`, `generate(options)`), каждая из которых детерминированно отображает вход в выход или бросает `Error` с человекочитаемым `message`, который `cli.js` без изменений выводит в `stderr`.
- **`test/`** — тесты в двух категориях (см. раздел Testing Strategy): модульные тесты `lib.js` через прямой вызов функций и процесс-тесты `cli.js` через `child_process.execFileSync`/`spawnSync`.
- **`package.json`** — декларирует `bin` (имя команды → `cli.js`), `scripts.start` (`node cli.js`), `scripts.test` (`node --test`), собственные зависимости (при необходимости), `"type"` не задаётся или явно `"commonjs"`.

Ни один модуль не знает о существовании остальных девяти. Единственное место в системе, где перечислены все десять модулей — финальный `README.md`, который не является программным компонентом и не участвует в исполнении.

## Data Model

Формальной персистентной модели данных в проекте нет — ни одна утилита не хранит состояние между вызовами. "Модель данных" здесь — это форма данных, которыми `cli.js` и `lib.js` каждой утилиты обмениваются в памяти процесса на протяжении одного вызова, плюс один статический встроенный набор данных (список слов для `lorem-ipsum-generator`).

### Форма данных на границе `cli.js` ↔ `lib.js`

Для каждой утилиты граница между слоями — это простой объект опций на входе и примитив (строка/число) либо структурированный объект на выходе, без общего типа между утилитами:

| Утилита | Вход в `lib.js` (концептуально) | Выход из `lib.js` |
|---|---|---|
| `temperature-converter` | `{ value: number, from: 'c'\|'f'\|'k', to: 'c'\|'f'\|'k' }` | `number` (результат до форматирования) |
| `word-counter` | `content: string` | `{ lines: number, words: number, chars: number }` |
| `password-generator` | `{ length, count, useLower, useUpper, useDigits, useSymbols, symbolsSet }` | `string[]` (пароли) |
| `case-converter` | `{ text: string, mode: string }` | `string` |
| `roman-numerals` | `{ number?: number, roman?: string }` | `string` (либо десятичная строка, либо римская запись) |
| `palindrome-checker` | `{ text: string, strict: boolean }` | `boolean` |
| `json-formatter` | `{ raw: string, indent: number }` | `string` (отформатированный JSON) |
| `lorem-ipsum-generator` | `{ paragraphs?, words?, sentences? }` | `string` |
| `percentage-calculator` | `{ mode: 'of'\|'share'\|'change', ...числовые поля }` | `number` |
| `countdown-timer` | `{ totalSeconds: number, elapsedSeconds: number }` (на каждый тик) | `{ display: string, done: boolean }` |

Эти формы — внутренний контракт конкретного модуля, не разделяемый ни с одной другой утилитой; они документируются комментарием в самом `lib.js` только там, где неочевидны (например, приоритет `--no-symbols` над `--symbols-set` в `password-generator`).

### Ошибки как данные

Ошибки домена моделируются как обычный `Error` со строкой `message`, совпадающей буквально с текстом, который должен появиться в `stderr` (см. `requirements.md`, раздел Functional Requirements, где эти строки зафиксированы дословно для каждой утилиты), за единственным исключением `json-formatter`, где для сценария невалидного JSON гарантирован только префикс `invalid JSON:` сообщения (см. разделы `API / Protocol Design` и `Testing Strategy`), а не его полный текст, поскольку хвост сообщения зависит от версии V8. `lib.js` не знает о `stderr` и кодах завершения — он лишь бросает исключение; трансляция в процесс-протокол происходит целиком в `cli.js`.

### Статические встроенные данные

Единственный нетривиальный набор данных в системе — фиксированный список классических латинских lorem-ipsum-слов, встроенный как массив констант непосредственно в `lorem-ipsum-generator/lib.js`. Он не загружается из файла и не через сеть, чтобы генерация оставалась детерминированной и не создавала файловую зависимость модуля от собственной директории при глобальной установке.

### Файловая система как источник/приёмник данных

`word-counter` и `json-formatter` читают содержимое ровно того пути, что передан в `--file`, как единственный внешний вход, кроме `argv`/`stdin`. `--out`, где поддерживается, — единственный вид записи во внешнее хранилище, и он всегда пишет ровно тот же текст, что уже выведен в `stdout` (не отдельный, потенциально расходящийся формат).

## API / Protocol Design

У системы нет сетевого API — единственный протокол взаимодействия с пользователем и с окружающими процессами (shell-пайплайны) — это **CLI-протокол**: аргументы командной строки, `stdin`, `stdout`, `stderr` и код завершения процесса. Он играет ту же роль, что HTTP-контракт в сервисном приложении: это единственная поверхность, по которой пишутся process-level тесты и по которой утилиты считаются взаимно согласованными.

### Общий конверт протокола (одинаков для всех десяти команд)

- **Справка:** `-h`/`--help` → `stdout`, exit `0`, обрабатывается до валидации прочих аргументов.
- **Успех:** результат — только в `stdout`, без ANSI, без баннеров.
- **Ошибка:** одна строка в `stderr`, без стек-трейса, exit `1`.
- **Коды завершения:** `0` (успех, включая `--help`) или `1` (любая ошибка); единственное исключение — `SIGINT` до завершения `countdown-timer`, тоже `1`.
- **`--out <path>`:** опционально дублирует `stdout` в файл; отсутствует у `password-generator` и `countdown-timer` (см. Security Architecture и требования соответствующих утилит).
- **stdin-fallback:** для утилит с единственным логическим текстовым/числовым входом — если обязательный флаг не передан и `stdin` не является TTY, вход читается из `stdin`; если `stdin` — TTY, ошибка `missing input: pass --<flag(s)> or pipe data via stdin`. Не действует для `percentage-calculator` и `countdown-timer` (см. `requirements.md`).
- **Кодировка и переносы строк:** UTF-8 на входе и выходе; `\n` как единственный разделитель строк в `stdout`, независимо от ОС.

### Протокол по каждой утилите

Полная таблица флагов, форматов вывода и текстов ошибок для каждой из десяти команд — авторитетно зафиксирована в `requirements.md` (раздел Functional Requirements) и не дублируется здесь во избежание расхождений между документами; этот раздел фиксирует, что именно она и есть протокол системы, а не побочный документ к нему. Ключевые протокольные решения, вынесенные на архитектурный уровень:

- **`roman-numerals`** — единственная утилита со взаимоисключающей парой флагов (`--number` / `--roman`), где протокол требует выбрать ровно один способ ввода; это моделируется в `cli.js` как явная XOR-проверка до вызова `lib.js`. Stdin-fallback для этой утилиты действует, но требует автоопределения формата: если ни `--number`, ни `--roman` не переданы, `cli.js` читает одну строку из `stdin`, приводит её к виду после `trim()` (обрезка пробельных символов и завершающего перевода строки) и трактует результат как `--number`, если он полностью соответствует регулярному выражению `^[0-9]+$`, иначе — как `--roman`.
- **`lorem-ipsum-generator`** — единственная утилита, где несколько флагов управления объёмом (`--paragraphs`/`--words`/`--sentences`) взаимоисключающие, но необязательные (есть протокольное значение по умолчанию `--paragraphs 3`).
- **`json-formatter`** — единственная утилита, где текст ошибки в `stderr` не является полностью стабильным протокольным контрактом: гарантирован только префикс `invalid JSON:`, а не хвост сообщения (он зависит от версии V8).
- **`countdown-timer`** — единственная утилита с протоколом непрерывного вывода: каждая секунда — отдельная строка `MM:SS\n` в `stdout`, финал — фиксированная байтовая последовательность `\x07` + `Time's up!` + `\n`.

### Совместимость с shell-пайплайнами

Поскольку единственные каналы ввода-вывода — `argv`, файлы, `stdin`, `stdout`, `stderr`, все утилиты по построению совместимы с `|`, `>`, `<` стандартной оболочки — это не отдельная фича, а прямое следствие протокольного дизайна.

## Security Architecture

Модель угроз этого продукта принципиально мала: единственный пользователь на собственной машине, отсутствие сети, отсутствие многопользовательского доступа. Тем не менее архитектура сознательно закрывает конкретные классы рисков, а не полагается на "личное использование" как оправдание их игнорировать.

### Периметр: полностью офлайн

Ни одна утилита ни при каких флагах не должна инициировать сетевое обращение. Это обеспечивается на трёх уровнях:

1. **Кодовый уровень** — ни в `cli.js`, ни в `lib.js` ни одной утилиты не должно быть `require('http')`, `require('https')`, `require('dns')`, глобального `fetch`.
2. **Зависимости** — любая добавляемая npm-зависимость проверяется вручную (не автоматизированным сканером) на отсутствие собственных сетевых вызовов до добавления в `package.json` конкретной утилиты; сетевые зависимости к добавлению запрещены архитектурно.
3. **Тестовый уровень** — для каждой утилиты предусмотрен статический тест, проверяющий исходный код `cli.js`/`lib.js` на отсутствие запрещённых `require`/`import`/`fetch` (см. Testing Strategy).

### Отсутствие состояния и файлового следа

Ни одна утилита не пишет в домашний каталог пользователя, системный кэш или временную директорию, и не читает файлы, кроме явно переданных через флаг. Наиболее строгое требование — у `password-generator`: сгенерированный пароль существует только в памяти процесса и в его единственном выводе `stdout`; утилита архитектурно не имеет кода записи в файл (`--out` для неё не реализован, а не просто не документирован — попытка передать `--out` возвращает `unknown flag: --out`).

### Источник случайности

`password-generator` обязан использовать `node:crypto` (`crypto.randomInt` либо эквивалент на основе `crypto.randomBytes`) как единственный источник случайности для генерации пароля — `Math.random` для этой утилиты запрещён архитектурно, поскольку он не является криптографически стойким и может допускать восстановление внутреннего состояния генератора по нескольким наблюдаемым выводам.

### Обработка недоверенного входа

- `json-formatter` разбирает содержимое исключительно через `JSON.parse`; `eval` и любые небезопасные динамические парсеры запрещены во всём проекте.
- Файловые пути (`--file` в `word-counter`, `json-formatter`) используются как есть, без обхода директорий и без неявного поиска "похожих" файлов; система доверяет локальному пользователю как единственному источнику пути (это личный офлайн-инструмент, а не сервис, принимающий пути от третьих лиц) — тем не менее ошибки чтения (не существует, директория, нет прав) перехватываются и переводятся в контролируемое сообщение `cannot read file: <path>`, а не приводят к необработанному исключению со стек-трейсом.
- Любая непредвиденная внутренняя ошибка (не только заранее предусмотренная ошибка валидации) обязана быть перехвачена в `cli.js` (верхнеуровневый `try/catch` вокруг вызова `lib.js`) и превращена в ту же форму — одна строка `stderr`, код `1`, без утечки внутренних деталей (путей модулей, номеров строк, имени функции движка) пользователю.

### Чувствительные данные во флагах

Поскольку конфигурация возможна только через флаги (`flags_only`), значения, переданные во флагах — в частности, текст, передаваемый через `--text` в `case-converter` и `palindrome-checker`, — могут попасть в историю команд оболочки. Это принято как осознанный компромисс личного инструмента (см. `constitution.md`) и не компенсируется файлами конфигурации или переменными окружения — так как это создало бы источник настроек за пределами `flags_only`, что архитектурно запрещено.

## Deployment & Operations

### Модель установки

У системы нет сервера, окружения выполнения в облаке или CI/CD-конвейера — "деплой" полностью локальный, на машину единственного пользователя.

- **Разработка / локальная проверка одной утилиты:** внутри директории утилиты — `npm start -- <флаги>` (эквивалент `node cli.js <флаги>`), без установки в PATH; `npm test` — независимый прогон `node --test` только для этой директории.
- **Разработка со сквозной проверкой команды:** `npm link` внутри директории утилиты регистрирует её `bin`-команду в PATH текущего окружения Node.js, не требуя публикации в реестр.
- **Повседневное личное использование:** `npm install -g <путь-к-директории-утилиты>` — глобальная установка с диска, без публикации в npm-реестр (публикация в реестр прямо исключена из рамок спецификации). После установки команда (например, `roman-numerals`) доступна из любой рабочей директории на неопределённо долгий срок.

Каждая из десяти команд устанавливается и обновляется этим способом *независимо* от остальных девяти — установка или удаление одной утилиты не затрагивает состояние других.

### Версионирование и обновление

Поскольку общего `package.json` нет, версия каждой утилиты — это `version` в её собственном `package.json`, изменяемая независимо. Обновление локально установленной команды выполняется повторным `npm install -g` из обновлённого каталога; отдельного механизма автообновления или проверки новых версий не предусмотрено и не должно быть реализовано — это противоречило бы принципу `offline_always`.

### Удаление

`npm uninstall -g <package-name>` удаляет глобальную бинарную ссылку конкретной утилиты; поскольку утилиты не хранят состояние вне своей директории (см. Security Architecture), удаление не оставляет остаточных файлов в домашнем каталоге или системном кэше пользователя.

### Среда выполнения

Единственная зависимость среды — установленный Node.js ≥ 20.x LTS в PATH. Кросс-платформенность (Windows, macOS, Linux) обеспечивается: использованием `path` вместо ручной конкатенации путей, отсутствием POSIX-специфичных вызовов shell внутри `cli.js`, фиксированным `\n` в качестве разделителя строк на выходе независимо от `os.EOL`.

### Область вне рамок

Настройка CI/CD, автоматизированная публикация в npm-реестр, контейнеризация — не предусмотрены этой архитектурой и не должны добавляться агентом по умолчанию: это личный инструмент с ручным, редким циклом установки, а не распространяемый пакет с релизным процессом.

## Observability

Классическая наблюдаемость (метрики, распределённый трейсинг, централизованные логи, дашборды) неприменима к продукту: нет сервера, нет сети, нет фоновых процессов, кроме управляемого пользователем `countdown-timer`, и нет второго наблюдателя, кроме самого пользователя в моменте вызова. Наблюдаемость здесь спроектирована как **сведение к минимально необходимому сигналу в моменте исполнения** плюс **диагностируемость постфактум через код**, а не как система мониторинга.

### Сигнал в моменте исполнения

Единственные каналы наблюдения за поведением утилиты — это её собственный протокол: код завершения процесса и содержимое `stderr`. Осознанное архитектурное решение — не вводить отдельного журнала работы (`--verbose`, `--log-file` и подобных флагов), поскольку это добавило бы конфигурируемость, прямо запрещённую принципом `flags_only`/минимализма, ради ценности, которая не нужна инструменту, вызываемому синхронно и наблюдаемому напрямую в терминале.

### Диагностика после сбоя — не логи, а код

Ключевое архитектурное решение (закреплённое также в `constitution.md`, принцип `read_source`): если утилита ведёт себя неожиданно спустя месяцы, единственный предусмотренный способ разобраться — открыть `cli.js`/`lib.js` этой конкретной утилиты и прочитать их. Это заменяет собой типичный цикл "посмотреть логи → найти корреляцию → воспроизвести": поскольку исполнение полностью детерминировано, без сети и без скрытого состояния, воспроизведение сценария локально всегда возможно без исторических данных о прошлых запусках.

Практическое следствие для реализации: сообщения об ошибках должны быть достаточно ясными сами по себе в момент показа (см. `clean_stderr_error` в `constitution.md`), но не обязаны накапливать диагностический контекст между вызовами — такого накопления архитектурно не существует.

### Ручная проверка вместо автоматического мониторинга

Для свойств, которые в сервисном приложении отслеживались бы метриками (задержка отклика, точность таймера), в этом продукте наблюдаемость сознательно ручная:

- Мгновенность отклика (`instant_run`) не инструментирована таймерами внутри кода — она проверяется однократно вручную при разработке каждой утилиты (см. Performance Targets в `constitution.md`) и неявно подтверждается процесс-тестами, которые сами были бы медленными при регрессии.
- Точность хода `countdown-timer` в реальном времени также не покрывается автоматической проверкой (только логика отсчёта и финальное событие) — она при необходимости проверяется вручную запуском таймера.

## Testing Strategy

Тестирование — единственный инструмент, гарантирующий, что независимая реализация каждой утилиты соблюдает общий протокол без общего кода. Стратегия закреплена на двух уровнях внутри каждой из десяти независимых директорий и не имеет над собой общего тестового рантайма или общего CI-конфига.

### Инструментарий

Единственный тестовый фреймворк — встроенный `node:test` + `node:assert`, запускаемый командой `npm test` (→ `node --test`) внутри директории каждой утилиты, независимо от остальных девяти. Внешние тестовые фреймворки (Jest, Mocha, Vitest) не используются ни в одной утилите. Тестовые хелперы не выносятся в общий модуль — если утилите нужен вспомогательный код для тестов, он дублируется локально внутри её `test/`.

### Уровень 1 — модульные тесты `lib.js`

Прямой вызов экспортируемых чистых функций, без порождения процесса. Обязательное покрытие: happy path, граничные случаи (пустой ввод, экстремальные значения, некорректный формат), где применимо — специфичные для утилиты границы (диапазон `1..3999` для `roman-numerals`, деление на ноль для `percentage-calculator`, абсолютный ноль для `temperature-converter`).

### Уровень 2 — процесс-тесты `cli.js`

Запуск реального дочернего процесса (`child_process.execFileSync`/`spawnSync`) с проверкой фактического протокола: код завершения, точное содержимое `stdout` для успешного сценария, точное содержимое `stderr` для сценария ошибки. Для девяти утилит с однократным выводом — побайтовое сравнение строки; единственное согласованное исключение — сценарий невалидного JSON в `json-formatter`, где проверяется только префикс `invalid JSON:` в `stderr` (нестабильность точного текста между версиями V8).

Тестирование непредвиденных внутренних ошибок (багов) отдельным сценарием не требуется — их корректная обработка (чистый `stderr`, код `1`, без стек-трейса) гарантируется структурой кода (верхнеуровневый `try/catch` в `cli.js`, описанный в Security Architecture), а не отдельным тестом.

### Специфичные тестовые сценарии по утилитам

- **`countdown-timer`** — CLI обязан принимать длительность через флаг, что позволяет тесту задать короткое значение (несколько секунд); процесс-тест проверяет только финальную строку/байтовую последовательность вывода и итоговый код завершения, не сверяя промежуточный таймлайн.
- **`password-generator`** — тест, подтверждающий отсутствие нового файлового следа: тест обязан проверять отсутствие новых файлов как минимум в следующих директориях — рабочая директория теста (`process.cwd()`), системная временная директория (`os.tmpdir()`) и домашний каталог пользователя (`os.homedir()`) — путём сравнения списка файлов в каждой из них до и после запуска утилиты.
- **Все десять утилит** — статический тест отсутствия сетевых обращений: проверка исходного кода `cli.js`/`lib.js` (и любых дополнительных внутренних файлов утилиты) на отсутствие `require`/`import` модулей `http`, `https`, `dns` и глобального `fetch`. Отсутствие сетевых npm-зависимостей в `package.json` таким автотестом не проверяется — это устанавливается вручную при добавлении каждой зависимости.
- **Реальные сетевые обращения в тестах запрещены** для всех утилит без исключения, независимо от того, что именно тестируется — согласуется с `offline_always` на уровне всего проекта, а не только на уровне production-кода.

## Success Criteria

Проект считается успешным, когда выполнены все нижеперечисленные условия (пункты 1–5, 7–9 — независимо проверяемые автоматически или статическим анализом; пункт 6 — подтверждается разовой ручной проверкой, см. ниже):

1. **Десять независимых пакетов.** В репозитории существуют ровно десять директорий верхнего уровня с именами, зафиксированными в `constitution.md`, каждая — валидный самостоятельный npm-пакет (`package.json`, `bin`, `scripts.start`, `scripts.test`).
2. **Ноль общего кода.** Ни один файл ни одной утилиты не содержит `require`/`import` пути, ссылающегося на другую директорию утилиты или на общий пакет за пределами своей директории; отсутствуют workspaces, отсутствует корневой `package.json`.
3. **Зелёные тесты у каждой утилиты по отдельности.** `npm test` внутри каждой из десяти директорий проходит независимо от состояния остальных девяти — обе категории тестов (модульные `lib.js` и процесс-тесты `cli.js`), включая специфичные сценарии (`countdown-timer`, `password-generator`, тест отсутствия сетевых обращений).
4. **Соблюдение общего протокола CLI во всех утилитах без исключения.** Для каждой из десяти команд: `-h`/`--help` работает и завершается кодом `0`; ошибки — единой строкой в `stderr` без стек-трейса и кодом `1`; успешный вывод — только в `stdout`, без ANSI; `\n` — единственный разделитель строк; UTF-8 на входе и выходе. Отклонение хотя бы в одной утилите — незакрытый дефект.
5. **Глобальная установка работает.** Каждая утилита после `npm link` или `npm install -g` вызывается по своему командному имени из произвольной рабочей директории на любой из трёх целевых ОС (Windows, macOS, Linux) без ошибок и без установленных зависимостей других утилит.
6. **Мгновенный отклик (проверяется вручную).** Для типичного ввода время от вызова команды до первого вывода не ощущается пользователем как задержка (порядок — время старта Node.js плюс единицы-десятки миллисекунд), для всех утилит, кроме заведомо продолжённого во времени `countdown-timer`. В отличие от остальных пунктов этого раздела, это свойство не проверяется автоматизированным тестом и не является формально верифицируемым условием — оно подтверждается разовой ручной проверкой при разработке каждой утилиты (см. `Observability`), а не составляет часть того же множества гарантий, что пункты 1–5 и 7–9.
7. **Полностью офлайн.** Статический тест на отсутствие `http`/`https`/`dns`/`fetch` проходит для всех десяти утилит; ни одна зависимость в `package.json` любой утилиты не выполняет сетевых вызовов (подтверждено вручную при добавлении).
8. **Без файлового следа за пределами явного `--out`.** Ни одна утилита, кроме явного использования флага `--out` пользователем, не создаёт и не изменяет файлы вне переданных пользователем путей; `password-generator` подтверждённо не оставляет никакого файлового следа ни при каких флагах.
9. **Финальный `README.md` — последний шаг.** Единый `README.md` в корне репозитория, перечисляющий все десять утилит (директория, команда, описание, пример вызова), создаётся и мержится только после того, как все десять утилит независимо прошли пункты 1–8; до этого момента корень репозитория не содержит объединяющего документа.

## Key Solution Decisions

- **Дублирование кода вместо общей библиотеки.** Даже там, где логика тривиально совпадает между утилитами (например, чтение `stdin`, если он не TTY), код не выносится в общий пакет. *Почему:* общий пакет создаёт скрытую связанность и подрывает `read_source` — диагностика по двум локальным файлам. *Как применять:* при добавлении новой похожей логики в будущем — копировать, а не импортировать из другой директории утилиты.

- **Двухслойная структура `cli.js`/`lib.js` в каждой утилите.** Ввод-вывод и чистая логика физически разделены на файловом уровне, а не просто на уровне функций внутри одного файла. *Почему:* это единственный способ тестировать логику модульно (Уровень 1) без порождения процесса, сохраняя при этом простоту одного файла для чтения при отладке. *Как применять:* новая функциональность внутри существующей утилиты добавляется как чистая функция в `lib.js`, а не как код, разбросанный по `cli.js`.

- **Протокол CLI как единственный контракт согласованности.** Единообразие интерфейса (`-h`, коды завершения, формат ошибок) фиксируется как контракт в `requirements.md` и воспроизводится вручную в каждой утилите. *Почему:* это разрешает архитектурное противоречие между "нет общего кода" и "consistent_interface" без нарушения ни одного из требований. *Как применять:* любое отклонение от протокола в одной утилите — дефект этой утилиты, а не повод централизовать код.

- **`node:test` вместо внешних тестовых фреймворков.** Единственная тестовая зависимость — встроенный модуль Node.js. *Почему:* исключает тяжёлые `node_modules` в простых инструментах и лишнюю точку версионирования в каждом из десяти независимых пакетов. *Как применять:* внешние тестовые библиотеки не добавляются ни в одну утилиту ни при каких обстоятельствах.

- **Fallback на `stdin` только там, где вход однозначен.** Соглашение `flags-with-fallback` применяется ко всем утилитам с единственным логическим текстовым/числовым входом, но явно исключено для `percentage-calculator` (набор обязательных флагов зависит от `--mode`) и `countdown-timer` (длительность процесса не имеет содержательного stdin-эквивалента). *Почему:* единый формат stdin для многозначного набора флагов был бы неоднозначным и снижал бы предсказуемость. *Как применять:* при появлении новой утилиты с несколькими зависимыми обязательными флагами — по умолчанию не проектировать для неё stdin-fallback, если формат неочевиден.

- **Криптографическая случайность в `password-generator`.** `node:crypto` вместо `Math.random`. *Почему:* пароли — единственный вывод, для которого предсказуемость генератора представляет прямой риск, даже в личном офлайн-инструменте. *Как применять:* это единственная утилита, где выбор источника случайности архитектурно фиксирован, а не оставлен на усмотрение реализации.

- **Детерминизм `lorem-ipsum-generator`.** Генерация без `Math.random`/`crypto.random*`, циклическим проходом по встроенному списку слов. *Почему:* позволяет процесс-тестам сравнивать точное содержимое `stdout`, как и у остальных девяти утилит, вместо ослабленной проверки одной лишь структуры вывода. *Как применять:* список слов остаётся статическим встроенным массивом, не расширяемым флагами или внешними файлами.

- **`--duration` в целых секундах, а не `HH:MM:SS`, для `countdown-timer`.** *Почему:* осознанное упрощение ради тестируемости — тест обязан задавать короткую длительность в несколько секунд, не ожидая произвольного реального времени. *Как применять:* формат ввода длительности не расширяется без пересмотра требований к тестируемости таймера.

- **`README.md` — программно неактивный, финальный, единственный интеграционный артефакт.** *Почему:* это единственная точка, где десять независимых утилит вообще упоминаются вместе, и она сознательно не является кодом, чтобы не создать десятую по счёту скрытую связь между независимыми пакетами. *Как применять:* работа над `README.md` не начинается, пока хотя бы одна из десяти утилит не прошла все критерии успеха из раздела Success Criteria.
