## Overview

Консольный планировщик личных дел — это минималистичное и высокопроизводительное CLI-приложение, предназначенное для автоматизации ведения персонального списка задач. Продукт ориентирован на пользователей, которые ценят высокую скорость работы, независимость от сторонних облачных сервисов и хотят уйти от ручного ведения списков дел в текстовых файлах.

Основная цель продукта — предоставить пользователю простой, надежный и мгновенный инструмент автоматизации рутинных операций через терминал. Приложение спроектировано для постоянного использования одним пользователем в локальном автономном режиме.

### Три базовых действия системы
1. **Добавление задачи (`add`)** с указанием описания и опциональной даты выполнения.
2. **Отображение списка дел на сегодня (`list`)**, который включает невыполненные задачи на текущий день, а также все просроченные невыполненные задачи за прошлые даты.
3. **Отметка о выполнении задачи (`done`)** по её уникальному целочисленному идентификатору.

### Ключевые технологические и архитектурные рамки
* **Стек технологий**: Python 3.10+ без использования тяжелых внешних зависимостей (используется исключительно стандартная библиотека).
* **Формат хранения**: Локальный JSON-файл. Путь по умолчанию — `~/.todo/tasks.json` (с возможностью переопределения через переменную окружения `TODO_FILE_PATH`).
* **Надежность и сохранность данных**: Использование механизма транзакционной безопасной записи (Safe Write) для предотвращения повреждения или потери данных при внезапном сбое.
* **Производительность**: Время отклика до 50 миллисекунд для базы данных объемом до 10 000 задач при потреблении памяти в пределах 30 МБ.
* **Локализация**: Интерфейс приложения, включая справочные сообщения, тексты ошибок и выводимые списки задач, должен быть полностью на русском языке.

## High-Level Architecture Design

Приложение представляет собой монолитную утилиту командной строки, поставляемую в виде единого исполняемого файла `todo`. Внутренняя структура приложения разделена на три логических слоя, что обеспечивает высокую тестируемость и изоляцию ответственности.

### Архитектурные слои

1. **CLI Controller (Интерфейсный слой)**:
   * Отвечает за парсинг аргументов командной строки.
   * Выполняет форматирование успешного вывода в `stdout`.
   * Перехватывает исключения бизнес-логики и файлового хранилища, форматирует сообщения об ошибках на русском языке для вывода в `stderr` и завершает процесс с соответствующим кодом выхода (`0` или `1`).

2. **Task Manager Service (Слой бизнес-логики)**:
   * Выполняет валидацию входных параметров: очистку описания задач, валидацию дат (соответствие формату `YYYY-MM-DD` и календарную корректность).
   * Содержит правила фильтрации задач на «сегодня» и просроченных.
   * Управляет генерацией уникальных идентификаторов по принципу автоинкремента.

3. **File Repository (Слой хранения данных)**:
   * Производит чтение и парсинг JSON-файла.
   * Автоматически создает структуру директорий и файл базы данных при их отсутствии.
   * Реализует механизм безопасной транзакционной записи (Safe Write).

### Сценарий безопасной транзакционной записи (Safe Write)

Для защиты базы данных от повреждения при внезапном сбое или прерывании процесса, запись изменений в файл `tasks.json` выполняется по следующему алгоритму:

```
[Объекты в памяти]
        |
        v
 1. Сериализация в JSON-строку
        |
        v
 2. Запись во временный файл "tasks.json.tmp"
        |
        v
 3. Применение прав доступа 0o600 (chmod) к временному файлу
        |
        v
 4. Принудительный сброс буферов на диск (fsync)
        |
        v
 5. Атомарное переименование (os.replace) временного файла в "tasks.json"
```

Этот подход гарантирует, что на диске всегда находится либо полностью корректная старая версия файла, либо полностью корректная новая версия файла. Права доступа `0o600` накладываются на временный файл *до* вызова замены, чтобы исключить потерю защитных атрибутов в операционных системах семейства UNIX.

## System Modules

Код приложения физически располагается в одном файле `todo`. Логически он делится на три класса-модуля и одну вспомогательную структуру данных.

### 0. Вспомогательная структура данных (`ParsedCommand`)

Структура данных `ParsedCommand` реализуется как класс данных (`dataclass`) с помощью модуля `dataclasses` стандартной библиотеки Python и содержит следующие строго типизированные поля:
* `command: str` — имя вызываемой команды (допустимые значения: `'add'`, `'list'`, `'done'`, `'help'`);
* `description: str | None` — очищенный текст описания задачи (используется для команды `'add'`; по умолчанию `None`);
* `due_date: str | None` — строковое значение даты в формате `YYYY-MM-DD` (используется для команды `'add'`; по умолчанию `None`);
* `task_id: int | None` — целочисленный идентификатор задачи (используется для команды `'done'`; по умолчанию `None`).

### 1. Модуль репозитория (`FileRepository`)

Класс инкапсулирует работу с файловой системой и гарантирует сохранность данных.

* **Методы**:
  * `resolve_file_path() -> Path`: 
    Определяет целевой путь к JSON-файлу. Если задана переменная окружения `TODO_FILE_PATH`, метод использует её значение. Если переменная отсутствует, используется значение по умолчанию `~/.todo/tasks.json`. Путь (как значение по умолчанию, так и пользовательское) **обязательно** обрабатывается методом `.expanduser()` для корректного раскрытия символа домашней директории (`~`) текущего пользователя операционной системы.
  * `ensure_storage_exists(file_path: Path) -> None`: 
    Проверяет существование директории и файла. Если они отсутствуют, создает директорию и инициализирует файл пустым JSON-массивом `[]`. В Unix-подобных системах (Linux, macOS) для создаваемой директории принудительно выставляются права доступа `0o700` (`chmod 700`), а для создаваемого файла — `0o600` (`chmod 600`).
  * `read_tasks(file_path: Path) -> list[dict]`: 
    Читает файл в кодировке `UTF-8` и десериализует его содержимое. При обнаружении синтаксических ошибок в JSON или несоответствии структуры корневого элемента (ожидается массив), выбрасывает исключение `DatabaseCorruptedException`.
  * `write_tasks_atomically(file_path: Path, tasks: list[dict]) -> None`: 
    Реализует безопасную запись. Сначала создается временный файл `tasks.json.tmp` в той же директории, что и основной файл. В него записываются сериализованные данные в кодировке `UTF-8`. Перед переименованием на временный файл накладываются права доступа `0o600` через `os.chmod` (в UNIX-окружении). Далее вызывается сброс буферов записи на диск (`fsync`). После этого вызывается `os.replace()`, который атомарно заменяет оригинальный файл временным.

### 2. Модуль бизнес-логики (`TaskManagerService`)

Класс содержит правила валидации данных, фильтрации и модификации задач.

* **Методы**:
  * `validate_description(description: str) -> str`: 
    Удаляет начальные и конечные пробелы (`strip`), заменяет символы перевода строки (`\n`, `\r`) на стандартные пробелы. Проверяет длину очищенной строки: она должна быть строго в диапазоне от 1 до 255 символов включительно. При несоответствии выбрасывает `ValidationError`.
  * `validate_date(date_str: str) -> datetime.date`: 
    Проверяет строку даты на соответствие формату `YYYY-MM-DD` и проверяет реальность календарного дня. При неверном формате или несуществующей дате выбрасывает `ValidationError`.
  * `generate_next_id(tasks: list[dict]) -> int`: 
    Находит максимальное значение ключа `id` среди существующих задач в списке и возвращает `max_id + 1`. Если список пуст, возвращает `1`.
  * `add_task(tasks: list[dict], description: str, due_date_str: str | None) -> tuple[dict, list[dict]]`: 
    Проводит валидацию описания. Если `due_date_str` передан, валидирует его, иначе использует текущую системную дату. Генерирует новый уникальный `id`. Создает структуру задачи, устанавливая `is_completed = False`. Добавляет задачу в общий список и возвращает кортеж из созданной задачи и обновленного списка.
  * `filter_active_tasks_for_today(tasks: list[dict], today: datetime.date) -> list[dict]`: 
    Отбирает невыполненные задачи (`is_completed == False`), у которых `due_date` равен текущему дню или хронологически меньше его (просроченные). Сортирует полученный список по возрастанию даты `due_date`, а при равных датах — по возрастанию `id`.
    *Ограничение и сопоставление типов*: Даты в словарях задач в оперативной памяти всегда хранятся в виде строк (`str`) формата `YYYY-MM-DD`. Метод `filter_active_tasks_for_today` принимает параметр `today` типа `datetime.date`. Для выполнения корректного сравнения дат без вызова исключения `TypeError`, метод `filter_active_tasks_for_today` должен преобразовывать строковые значения `due_date` из словарей задач в объекты `datetime.date` (используя `datetime.date.fromisoformat()`) перед сопоставлением с `today`.
  * `complete_task(tasks: list[dict], task_id: int) -> list[dict]`: 
    Ищет задачу по `id`. Если задача не найдена, выбрасывает `TaskNotFoundError`. Если задача найдена, устанавливает её поле `is_completed = True`. 
    *Особое поведение (Идемпотентность)*: Если задача с указанным `id` уже была выполнена ранее (`is_completed` уже равен `True`), повторный вызов выполняется успешно: статус остается `True`, изменения фиксируются (или файл остается без изменений), и метод завершает работу штатно, без генерации ошибок.

### 3. Контроллер интерфейса (`CLIController`)

Класс отвечает за разбор аргументов командной строки, вызов методов сервиса и отображение результатов.

* **Методы**:
  * `parse_arguments(args: list[str]) -> ParsedCommand`: 
    Разбирает входящие аргументы командной строки с учетом кастомных правил объединения слов описания и извлечения флага даты. Возвращает строго типизированный объект `ParsedCommand`.
  * `execute(args: list[str]) -> int`: 
    Главная точка выполнения. Инициализирует `FileRepository` и `TaskManagerService`, запускает обработку команды. В случае успешного завершения возвращает `0`. Перехватывает все ожидаемые исключения (`ValidationError`, `TaskNotFoundError`, `DatabaseCorruptedException` и др.), выводит лаконичное сообщение на русском языке в `stderr` и возвращает код `1`.

## Data Model

Данные хранятся локально в формате JSON. Корневой элемент представляет собой массив JSON-объектов.

### JSON Schema для файла задач

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "TaskList",
  "type": "array",
  "items": {
    "type": "object",
    "required": ["id", "description", "due_date", "is_completed"],
    "additionalProperties": false,
    "properties": {
      "id": {
        "description": "Уникальный автоинкрементный целочисленный идентификатор задачи",
        "type": "integer",
        "minimum": 1
      },
      "description": {
        "description": "Очищенный текст описания задачи",
        "type": "string",
        "minLength": 1,
        "maxLength": 255
      },
      "due_date": {
        "description": "Дата планирования в формате YYYY-MM-DD",
        "type": "string",
        "pattern": "^[0-9]{4}-[0-9]{2}-[0-9]{2}$"
      },
      "is_completed": {
        "description": "Флаг выполнения задачи",
        "type": "boolean"
      }
    }
  }
}
```

### Пример содержимого файла данных `tasks.json`

```json
[
  {
    "id": 1,
    "description": "Купить продукты в магазине",
    "due_date": "2026-03-30",
    "is_completed": false
  },
  {
    "id": 2,
    "description": "Запустить автотесты для CLI планировщика",
    "due_date": "2026-03-29",
    "is_completed": true
  }
]
```

*Примечание*: Выполненные задачи сохраняются в JSON-файле навсегда (`is_completed: true`). Автоматическая очистка или удаление не предусмотрены. Это гарантирует сохранение истории идентификаторов для бесконфликтного автоинкремента.

## API / Protocol Design

Взаимодействие с приложением осуществляется через вызов исполняемого файла `todo` с параметрами командной строки.

### Правила обработки справки и некорректного запуска

1. **Явный запрос справки (Успешный сценарий)**:
   Если пользователь запрашивает справку явно через аргументы `--help`, `-h` или отдельную команду `help` (например, `./todo --help`), приложение обязано:
   * Вывести подробное руководство по использованию на русском языке в стандартный поток вывода `stdout`.
   * Завершить работу с успешным кодом выхода `0`.

2. **Неявный некорректный запуск (Сценарий ошибки)**:
   Если утилита запущена без аргументов, с неизвестной командой или некорректными параметрами (например, `./todo add` без описания задачи), приложение обязано:
   * Вывести справочную информацию и сообщение об ошибке на русском языке в поток ошибок `stderr`.
   * Завершить работу с кодом выхода `1`.

### Спецификация CLI команд

#### 1. Добавление задачи (`add`)
Добавляет новое дело в список.

* **Синтаксис вызова**:
  `./todo add <текст задачи> [--date YYYY-MM-DD]`
  или без использования кавычек:
  `./todo add <слово1> <слово2> ... <словоN> [--date YYYY-MM-DD]`
* **Правила разбора**:
  * Если флаг `--date` передан в произвольном месте списка аргументов (например, перед описанием задачи или в середине), утилита должна извлечь сам флаг и следующее за ним значение. Все остальные аргументы объединяются через один пробел в единую строку описания.
  * Если флаг `--date` передан без последующего значения, или если в командной строке содержится несколько флагов `--date` (используется последнее переданное значение), утилита валидирует параметры. При ошибке валидации выводится понятное сообщение в `stderr` и работа завершается с кодом `1`.
  * Если флаг `--date` отсутствует, в качестве даты выполнения автоматически устанавливается текущая дата операционной системы.
* **Результат при успешном выполнении**:
  В `stdout` выводится только сгенерированный целочисленный `id` созданной задачи. Код возврата `0`.
* **Пример вывода**: `3`

#### 2. Отображение списка задач (`list`)
Выводит актуальный список невыполненных задач.

* **Синтаксис вызова**:
  `./todo list`
* **Правила отбора и сортировки**:
  * Отбираются только задачи со значением `is_completed == false`, у которых `due_date` равен текущей дате операционной системы или меньше текущей даты (просроченные).
  * Отобранные задачи сортируются по возрастанию даты `due_date`, а при равных датах — по возрастанию числового значения `id`.
* **Результат при успешном выполнении**:
  Задачи выводятся построчно в `stdout` строго в формате: `ID [YYYY-MM-DD] Описание`. Код возврата `0`.
  *Если подходящих задач нет, `stdout` остается пустым, код возврата `0`.*
* **Пример вывода**:
  ```
  1 [2026-03-29] Вчерашнее просроченное дело
  3 [2026-03-30] Важная задача на сегодня
  4 [2026-03-30] Вторая задача на сегодня
  ```

#### 3. Отметка о выполнении (`done`)
Переводит статус задачи в выполненное состояние.

* **Синтаксис вызова**:
  `./todo done <id>`
* **Правила разбора**:
  * Параметр `<id>` должен быть строго целым положительным числом. Любой другой формат аргумента приводит к выводу ошибки в `stderr` и завершению работы с кодом `1`.
  * Если задача с таким `id` отсутствует в файле данных, выводится ошибка на русском языке в `stderr`, код возврата `1`.
  * Если задача найдена, статус `is_completed` меняется на `true`. 
  * Если задача с указанным `id` уже была выполнена ранее, повторный вызов команды `done` обрабатывается успешно и идемпотентно: статус остается `true`, файл данных перезаписывается, и приложение завершается с кодом возврата `0` (поток `stdout` остается пустым).
* **Результат при успешном выполнении**:
  Стандартный вывод `stdout` остается пустым. Изменения сохраняются на диск. Код возврата `0`.

## Security Architecture

Система безопасности приложения разработана с учетом его локального характера функционирования.

### 1. Полная сетевая изоляция
В коде приложения полностью отсутствуют модули для работы с сетью (`socket`, `urllib`, `http`, `requests` и т.д.). У утилиты нет технической возможности отправлять телеметрию или связываться с внешними веб-сервисами.

### 2. Разграничение прав доступа к файлам на уровне ОС (POSIX)
* При создании директории данных (по умолчанию `~/.todo`) приложение накладывает маску прав `0o700` (`chmod 700`). Это запрещает другим пользователям операционной системы просматривать или изменять содержимое директории.
* При создании и последующей перезаписи файла данных `tasks.json` утилита гарантирует сохранение маски прав `0o600` (`chmod 600`).
* Для предотвращения потери этих прав в процессе безопасной атомарной перезаписи (поскольку при обычном создании временного файла `tasks.json.tmp` операционная система использует права по умолчанию на основе системной маски `umask`), приложение **принудительно** применяет к файлу `tasks.json.tmp` права `0o600` перед вызовом системного метода `os.replace()`.
* В операционных системах семейства Windows данные низкоуровневые ограничения прав опускаются для обеспечения совместимости.

### 3. Защита целостности структуры данных (Sanitization)
* Все входные строки очищаются от начальных и конечных пробелов.
* Символы переводов строк (`\n`, `\r`) преобразуются в пробелы.
* Длина текста строго лимитируется значением в 255 символов, предотвращая потенциальное переполнение дискового пространства или перегрузку при разборе огромных невалидных JSON-строк.

Утилита относится к классу программ с нулевым администрированием (Zero-Ops).

### Требования к целевой системе

* **Внешние зависимости**: Отсутствуют. Используются исключительно библиотеки, входящие в стандартную поставку Python.

### Установка приложения
1. Скопировать исходный код утилиты в файл с именем `todo` (строго без расширения).


## Observability

Наблюдаемость работы утилиты базируется на стандартных POSIX-концепциях управления потоками и кодами возврата.

### 1. Разделение потоков вывода

* **Стандартный вывод (`stdout`)**:
  Предназначен строго для передачи полезной информации в случае успешного выполнения команд.
  * Для `add` — выводит только сгенерированный ID.
  * Для `list` — выводит форматированный список задач.
  * Для `done` — остается пустым.
  * Для успешного вызова справки (`--help`, `-h`, `help`) — выводит справочную информацию.

* **Вывод ошибок (`stderr`)**:
  Предназначен для отображения любых диагностических данных и сообщений о сбоях.
  * Ошибки парсинга аргументов.
  * Ошибки валидации (неверный формат даты, превышение лимита символов в тексте).
  * Системные ошибки (файл поврежден, нет прав доступа к директории).
  * Вывод справки при некорректном запуске (без аргументов).

### 2. Коды возврата (Exit Codes)
* `0` — Операция успешно завершена. Все изменения сохранены на физический диск.
* `1` — Произошла ожидаемая или неожидаемая ошибка. Изменения не сохранены, либо команда не выполнена.

### 3. Понятные сообщения об ошибках
Приложение перехватывает все исключения и выводит краткие сообщения на русском языке в `stderr` без системного стека вызовов (traceback).
* *Вместо `json.decoder.JSONDecodeError` выводится*: `Ошибка: Файл данных поврежден или имеет неверный формат JSON.`
* *Вместо `PermissionError` выводится*: `Ошибка: Отсутствуют права доступа на чтение или запись файла данных.`

## Testing Strategy

Стратегия тестирования направлена на проверку надежности работы утилиты в экстремальных условиях эксплуатации.

### 1. Юнит-тестирование (Unit Tests)
* **Парсинг аргументов**:
  * Проверка парсинга команды `add` при передаче аргументов без кавычек (слияние слов).
  * Проверка правильности извлечения параметра `--date` из середины, начала и конца строки аргументов.
  * Проверка корректности выбора даты при дублировании флага `--date` (использование последнего значения).
  * Проверка вызова явной справки (`-h`, `--help`, `help`): подтверждение вывода в `stdout` и возврата кода `0`.
* **Бизнес-логика**:
  * Валидация дат: високосные годы (29 февраля), несуществующие даты (31 апреля), невалидные форматы.
  * Санитизация текста задачи: обрезка пробелов, замена `\n` и `\r` на пробелы, реакция на длину описания (0 символов, 255 символов, 256 символов).
  * Идемпотентность отметки о выполнении: повторный вызов `done` для одной и той же задачи не должен приводить к ошибкам и должен завершаться с кодом `0`.

### 2. Интеграционное тестирование (Integration Tests)
* **Управление путями и создание директорий**:
  * Проверка того, что путь со знаком тильды `~` корректно обрабатывается через `.expanduser()` и не создает папку `~` буквально в текущей рабочей директории.
  * Проверка автоматического создания структуры каталогов и инициализации файла пустым массивом `[]`.
  * Проверка выставления UNIX-прав доступа `0o700` на папку и `0o600` на файл данных.
* **Надежность транзакционной записи (Safe Write)**:
  * Проверка сохранения прав доступа `0o600` на файле `tasks.json` после выполнения операции обновления данных (проверка работы `chmod` на `tasks.json.tmp` перед вызовом `os.replace`).
  * Симуляция повреждения JSON-файла: запись некорректной строки в файл и проверка вывода понятной ошибки в `stderr` при последующем чтении.

### 3. Нагрузочное тестирование (Performance & Volume Testing)
* Автоматическая генерация тестового файла с 10 000 невыполненных задач.
* Запуск операций добавления, фильтрации списка и переключения статуса. Проверка соответствия времени отклика целевым 50 миллисекундам и объема потребляемой оперативной памяти в пределах 30 МБ.

## Success Criteria

Реализация проекта признается успешной при выполнении следующих критериев:

1. **Функциональная полнота**:
   Все три команды (`add`, `list`, `done`) работают в точном соответствии со спецификацией.
2. **Идемпотентность операций**:
   Повторное выполнение команды `done` на уже выполненной задаче завершается успешно с кодом `0`.
3. **Безопасность и сохранение прав**:
   Файл данных защищен от чтения другими пользователями на UNIX-системах. Права доступа `0o600` не сбрасываются при перезаписи файла утилитой.
4. **Надежность**:
   Механизм атомарной записи Safe Write предотвращает появление поврежденных файлов данных при принудительном завершении процесса.
5. **Соответствие стандартам CLI**:
   * Явный вызов справки завершается с кодом `0` и выводит информацию в `stdout`.
   * Неявные ошибки запуска и ошибки валидации выводят информацию в `stderr` и завершают работу с кодом `1`.
   * Полностью отсутствуют системные трассировки стека (tracebacks) при ожидаемых сбоях.
6. **Производительность**:
   Время отклика на любой операции с базой до 10 000 задач составляет менее 50 мс, потребление памяти — менее 30 МБ.

## Key Solution Decisions

### 1. Отказ от SQLite в пользу JSON-хранилища
Для локального однопользовательского планировщика с объемом данных до 10 000 задач использование полноценной СУБД избыточно. JSON-формат обеспечивает полную прозрачность данных для пользователя, позволяя ему легко просматривать, бэкапить и редактировать задачи стандартными текстовыми редакторами.

### 2. Реализация Safe Write с сохранением прав доступа
Прямая перезапись файла JSON опасна возможностью его повреждения при сбое. Схема с записью во временный файл `tasks.json.tmp` решает эту проблему. Решение принудительно вызывать `chmod 0o600` на временный файл перед вызовом `os.replace` защищает утилиту от уязвимости, при которой права доступа оригинального файла сбрасывались бы на стандартные системные права `umask` (например, `0o644`).

### 3. Кастомный разбор аргументов вместо `argparse`
Стандартная библиотека `argparse` навязывает жесткую последовательность аргументов и плохо справляется со слиянием произвольного количества слов описания задачи без кавычек, если флаг даты `--date` указан в середине вызова. Собственный парсер позволяет гибко обрабатывать любые варианты ввода пользователя, ускоряет импорт модулей и сокращает время старта приложения.

### 4. Обязательный вызов `.expanduser()` для путей данных
Стандартные библиотеки Python не раскрывают символ `~` автоматически при передаче пути в конструктор `Path()`. Решение принудительно вызывать `.expanduser()` предотвращает ошибочное создание директории с буквальным именем `~` в текущем рабочем каталоге пользователя.

### 5. Идемпотентность команды `done`
Интеграция планировщика в скрипты автоматизации требует предсказуемого поведения. Если скрипт повторно отправляет команду `done <id>` для уже закрытой задачи, падение с кодом ошибки `1` может нарушить работу сценария автоматизации. Идемпотентная обработка повторного вызова с успешным кодом завершения `0` делает интеграцию утилиты надежной.
