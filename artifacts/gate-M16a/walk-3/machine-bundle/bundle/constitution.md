## Project Vision

Проект представляет собой консольный планировщик личных дел (CLI-приложение), ориентированный на максимальную скорость работы, простоту и локальное владение данными. Основная цель продукта — избавить пользователя от необходимости ручного ведения списков дел в текстовых файлах, предоставив ему удобный, надежный и мгновенный инструмент автоматизации рутинных операций через терминал. 

Продукт предназначен для персонального использования одним пользователем в режиме постоянного доступа. Вся логика работы строится вокруг трех базовых действий: быстрое добавление задачи с датой, отображение списка дел на сегодня и отметка о выполнении. В системе отсутствуют перегружающие интерфейс элементы, такие как подзадачи, теги, сложные приоритеты и история изменений. Данные хранятся локально на устройстве пользователя, гарантируя приватность и независимость от сторонних облачных сервисов.

## Core Principles

* **Минимализм и фокус**: Приложение должно решать только три заявленные задачи. Любое расширение функционала (например, добавление подзадач, тегов, категорий или истории выполненных дел) строго запрещено для сохранения чистоты и простоты продукта.
* **Надежность и сохранность данных**: Локальный файл с задачами является единственным источником правды. Приложение должно гарантировать, что некорректное завершение процесса или сбой питания не приведут к потере или повреждению файла данных.
* **Скорость и доступность**: Время отклика интерфейса должно быть мгновенным. Утилита проектируется для работы в терминале, позволяя пользователю интегрировать её в ежедневные сценарии автоматизации и командные скрипты.
* **Прозрачность формата**: Данные должны храниться в открытом и легко читаемом формате, чтобы пользователь при необходимости мог просмотреть или скопировать их без использования специальных инструментов.

## Technology Constraints

* **Локальное окружение**: Приложение должно работать полностью в автономном режиме. Использование сети Интернет, внешних API или сетевых баз данных исключено.
* **Стек технологий**: В качестве среды выполнения используется Python 3.10+ без использования тяжелых внешних зависимостей. Для работы приложения достаточно стандартной библиотеки Python, что обеспечивает легкую переносимость между различными операционными системами (Linux, macOS, Windows).
* **Формат хранения**: Локальное хранилище данных реализуется в виде единого файла в формате JSON. Использование полноценных СУБД (например, SQLite или PostgreSQL) избыточно и запрещено.
* **Отсутствие веб-интерфейса**: Интерфейс взаимодействия ограничен исключительно командной строкой (CLI). Добавление графических (GUI) или веб-интерфейсов (Web UI) не планируется.

## Architecture Constraints

* **Однопользовательская архитектура (Single-user)**: Приложение не предусматривает одновременную работу нескольких пользователей, авторизацию, разграничение прав доступа или синхронизацию между устройствами.
* **Монолитная структура**: Кодовая база должна быть простой и понятной. Архитектура делится на три логических слоя:
  1. *CLI Controller*: парсинг аргументов командной строки, форматирование вывода.
  2. *Task Manager Service*: бизнес-логика валидации дат, фильтрации и изменения статуса задач.
  3. *File Repository*: чтение, валидация структуры JSON и безопасная запись на диск.
* **Атомарная запись (Safe Write)**: Изменение файла данных должно происходить транзакционно с использованием временного файла. Сначала данные записываются во временный файл в той же директории, после чего происходит его переименование (замена оригинального файла), что предотвращает повреждение базы при внезапном сбое.
* **Схема данных**: Файл данных должен представлять собой корневой JSON-массив объектов задач. Каждая запись задачи в этом массиве должна строго содержать следующие поля:
  * `id` (уникальный идентификатор, представляющий собой строго целое число (integer). Идентификатор генерируется автоматически по принципу автоинкремента: берется максимальное значение `id` среди существующих в файле задач и увеличивается на 1. Если файл пуст или задач нет, генерация начинается с 1);
  * `description` (строка с текстом дела);
  * `due_date` (дата в формате YYYY-MM-DD);
  * `is_completed` (логическое значение true/false).

## Testing Approaches

* **Юнит-тестирование**:
  * Тестирование парсера командной строки для различных комбинаций аргументов (добавление, просмотр, завершение).
  * Тестирование логики валидации дат (включая високосные года, некорректные форматы и граничные значения вроде смены часовых поясов или перехода суток).
  * Тестирование фильтрации списка задач на "сегодня".
* **Интеграционное тестирование**:
  * Тестирование операций чтения/записи JSON-файла.
  * Тесты на обработку исключительных ситуаций: отсутствие файла данных (автоматическое создание), пустой файл, поврежденный или невалидный JSON (вывод понятной ошибки пользователю вместо падения приложения).
  * Проверка механизма безопасной атомарной записи при симуляции прерывания процесса записи.
* **Автоматизация**: Тесты должны запускаться локально одной командой и легко интегрироваться в базовые сценарии CI.

## Coding Standards

* **Чистота кода**: Код должен строго соответствовать стандарту PEP 8. Обязательно использование статической типизации (Type Hinting) для всех функций и методов.
* **Понятная обработка ошибок**: Приложение не должно выводить системные трассировки стека (traceback) конечному пользователю при возникновении ожидаемых ошибок (например, неверный формат даты или отсутствие файла). Вместо этого должна выводиться лаконичная и понятная инструкция на русском языке в поток `stderr`.
* **Документирование**: Все ключевые функции должны быть снабжены краткими docstring-комментариями на русском языке, объясняющими их назначение и возвращаемые значения.
* **Локализация**: Интерфейс приложения, включая справочные сообщения, тексты ошибок и выводимые списки задач, должен быть полностью на русском языке.

## Security Constraints

* **Изоляция сети**: Приложение не имеет права открывать сетевые порты, запускать локальные веб-серверы или отправлять какую-либо телеметрию.
* **Права доступа к файлу**: При создании директории и файла данных должны выставляться права доступа, ограничивающие чтение и запись для других пользователей операционной системы. Данное ограничение (аналог `chmod 600` или `chmod 700`) применяется исключительно в Unix-подобных операционных системах (Linux, macOS). В операционной системе Windows данные ограничения опускаются или реализуются стандартными средствами создания файлов без генерации ошибок и без использования внешних API операционной системы.
* **Безопасность ввода**: Все входные данные, передаваемые пользователем через консоль (текст задачи, дата), должны проходить обязательную очистку и валидацию перед записью в файл. Необходимо обрезать начальные и конечные пробелы в тексте задачи (метод `strip`), удалять или заменять любые символы перевода строки (`\n`, `\r`) на пробелы, а также ограничить максимальную длину описания задачи (`description`) в 255 символов. Дата должна строго валидироваться на соответствие формату `YYYY-MM-DD`.

## Performance Targets

* **Время запуска и выполнения**: Любая операция (добавление, вывод списка, переключение статуса) должна выполняться менее чем за 50 миллисекунд. Пользователь не должен ощущать задержки при вызове команды.
* **Потребление ресурсов**: Объем используемой оперативной памяти не должен превышать 30 МБ в пиковые моменты выполнения.
* **Масштабируемость хранилища**: Система должна без потери производительности и задержек обрабатывать локальный файл, содержащий до 10 000 задач.

## Integration Points

* **Входные точки (CLI Args)**: При запускe утилиты без каких-либо аргументов или субкоманд приложение должно выводить справочное сообщение (help) по использованию команд в поток ошибок (`stderr`) и завершать работу с ненулевым кодом выхода. Приложение поддерживает стандартные POSIX-совместимые аргументы и субкоманды:
  * `add "<текст задачи>"` `[--date YYYY-MM-DD]` — добавление задачи (если дата не указана, по умолчанию берется текущая дата системы).
  * `list` — отображение списка невыполненных задач, запланированных на сегодня, а также всех невыполненных (просроченных) задач за прошлые даты. Задачи в списке должны быть отсортированы по дате (due_date) по возрастанию, а при равных датах — по их идентификатору (id) по возрастанию.
  * `done <id>` — отметить задачу с указанным идентификатором как выполненную. В случае, если в качестве `<id>` передан несуществующий в базе данных идентификатор или передан идентификатор в невалидном формате (например, буквенное значение вместо числа), приложение должно вывести понятное сообщение об ошибке на русском языке в поток ошибок (`stderr`) и завершить работу с ненулевым кодом выхода.
* **Потоки вывода**:
  * Успешные результаты работы и списки задач выводятся в стандартный поток вывода (`stdout`).
  * Каждая задача при выводе списка (команда `list`) должна выводиться на новой строке строго в формате: `ID [YYYY-MM-DD] Описание` (например: `1 [2023-10-27] Купить продукты`).
  * Команда `add` при успешном выполнении должна выводить в `stdout` только ID созданной задачи.
  * Команда `done` не должна выводить ничего в `stdout` при успешном выполнении.
  * Ошибки валидации, системные предупреждения и справочная информация (включая вызов без аргументов) выводятся в поток ошибок (`stderr`).
* **Файл данных**: Путь к файлу конфигурации и данных по умолчанию должен быть `~/.todo/tasks.json` с возможностью переопределения через переменную окружения `TODO_FILE_PATH`.
