## Project Vision

Проект представляет собой консольную игру в жанре «текстовый квест» (Text Adventure), запускаемую в среде Node.js. Главная цель проекта — предоставить игрокам интерактивный и атмосферный игровой процесс прямо в терминале, минимизируя барьеры для входа. Игра распространяется как исполняемый пакет и запускается мгновенно с помощью команды `npx` (`npx_execution`), что исключает необходимость предварительной ручной установки или настройки окружения.

Сюжет, структура сцен, предметы, переходы и условия победы или поражения полностью отделены от движка игры и описываются во внешних файлах формата JSON. Это позволяет легко масштабировать проект, создавать новые сценарии и делиться ими без изменения исходного кода самого движка. Игрок взаимодействует с игрой, выбирая доступные варианты действий с клавиатуры. Прогресс прохождения может быть сохранен в локальный файл и загружен из главного меню. В конце игры выводится подробный итог прохождения, зависящий от решений, принятых игроком.

## Core Principles

При разработке игры необходимо руководствоваться следующими ключевыми принципами:

* **Разделение кода и данных (Data-Driven Design):** Движок игры является исключительно интерпретатором сценариев. Вся игровая логика, тексты сцен, условия переходов и характеристики персонажей должны быть описаны в файле сценария JSON.
* **Простота запуска (Zero-Configuration):** Игрок должен иметь возможность начать игру одной командой через `npx`, не заботясь о зависимостях или глобальной установке пакетов.
* **Строгая валидация (Fail-Fast):** Любой файл сценария должен проходить автоматическую проверку структуры перед запуском. Ошибки в сценарии должны выявляться на этапе загрузки, а не приводить к падению игры посреди прохождения.
* **Удобство интерфейса (UX в терминале):** Несмотря на ограничения CLI, взаимодействие должно быть интуитивно понятным. Игрок совершает выбор с помощью клавиатуры (например, стрелками или вводом номеров вариантов), а важная текстовая информация визуально выделяется.
* **Переносимость прогресса:** Файлы сохранений должны легко читаться движком на любой платформе, где запущен Node.js, обеспечивая бесшовное продолжение игры.

## Technology Constraints

* **Платформа выполнения:** Node.js (LTS версии 18 и выше). Код должен быть совместим с основными операционными системами (Windows, macOS, Linux).
* **Способ распространения:** Пакет npm, оптимизированный для запуска через `npx` (`npx_run`). Пакет должен содержать корректное поле `bin` в файле `package.json`.
* **Зависимости интерфейса:** Для реализации интерфейса выбора вариантов использовать легковесные библиотеки (например, `inquirer` или `prompts`). Сложные TUI-фреймворки (типа `blessed` или `neo-blessed`) запрещены. Оформление вывода ограничивается стилизованным текстом (`styled_text`) с использованием ANSI-последовательностей или библиотеки `chalk` / `yoctocolor`.
* **Валидация сценариев:** Использовать JSON Schema для валидации файлов игровых сцен. Библиотека валидации (например, `ajv`) должна быть легковесной и быстрой.
* **Моделирование инвентаря и состояния:** Все игровые предметы и элементы инвентаря полностью моделируются через логические переменные состояния (флаги в `variables`, `requiredState` и `setState`). Специализированные массивы под инвентарь в схеме не используются во избежание дублирования данных.
* **Инициализация состояния:** Для явной инициализации стартовых переменных в корневой объект сценария добавлено необязательное поле `initialState` (объект с булевыми значениями). При старте новой игры все переменные, не упомянутые в `initialState` или в файле сохранения, неявно инициализируются значением `false`.
* **Спецификация структуры JSON-сценария:**
  Файл сценария должен строго соответствовать следующей JSON-схеме (поле `options` является необязательным, что позволяет лаконично описывать финальные сцены без необходимости указывать пустой массив):
  ```json
  {
    "$schema": "http://json-schema.org/draft-07/schema#",
    "type": "object",
    "properties": {
      "title": { "type": "string" },
      "description": { "type": "string" },
      "initialSceneId": { "type": "string" },
      "initialState": {
        "type": "object",
        "additionalProperties": { "type": "boolean" }
      },
      "scenes": {
        "type": "object",
        "additionalProperties": {
          "type": "object",
          "properties": {
            "description": { "type": "string" },
            "options": {
              "type": "array",
              "items": {
                "type": "object",
                "properties": {
                  "text": { "type": "string" },
                  "nextSceneId": { "type": "string" },
                  "requiredState": {
                    "type": "object",
                    "additionalProperties": { "type": "boolean" }
                  },
                  "setState": {
                    "type": "object",
                    "additionalProperties": { "type": "boolean" }
                  }
                },
                "required": ["text", "nextSceneId"]
              }
            },
            "isEnding": { "type": "boolean" },
            "endingType": { "type": "string", "enum": ["win", "lose"] }
          },
          "required": ["description"]
        }
      }
    },
    "required": ["title", "description", "initialSceneId", "scenes"]
  }
  ```
* **Работа с файловой системой:** Использовать встроенные модули Node.js (`fs` или `fs/promises`). Использование сторонних тяжелых ORM или баз данных для хранения сохранений запрещено.

## Architecture Constraints

Архитектура приложения должна быть разделена на изолированные модули со строгими границами ответственности:

* **Модуль валидации (Scenario Validator):**
  * Отвечает за проверку загружаемых JSON-файлов на соответствие схеме сценария (`schema_validation`).
  * Проверяет связность графа сцен на структурном уровне переходов. Проверка связности выполняется как для обычного ориентированного графа без учета динамических значений условий `requiredState` (все существующие в `options` переходы `nextSceneId` считаются потенциально проходимыми; проверяется отсутствие изолированных или недостижимых подграфов, а также корректность всех идентификаторов сцен).
  * Выполняет строгую проверку сцен без вариантов выбора: каждая сцена в сценарии должна либо содержать непустой массив `options` (или доступные переходы), либо иметь установленный флаг `isEnding: true`. Создание сцен без вариантов выбора и без флага завершения игры запрещено.
* **Движок состояния (State Machine & Game Loop):**
  * Управляет текущим состоянием игрока (текущая сцена и переменные состояния).
  * Вычисляет доступные варианты выбора на основе текущих флагов состояния и условий, описанных в JSON сценария.
  * Числовой параметр здоровья и другие не описанные в схеме сущности не поддерживаются движком напрямую; вся логика базируется исключительно на булевых переменных состояния (`variables`).
* **Интерфейс ввода-вывода (CLI View):**
  * Отвечает за отрисовку текста текущей сцены с применением цветового кодирования.
  * Формирует список доступных опций и обрабатывает нажатия клавиш игрока.
* **Менеджер сохранений (Save/Load Manager):**
  * Записывает текущее состояние игры в файл сохранения.
  * Сохранения записываются исключительно в текущую рабочую директорию запуска (`current_directory`).
  * Реализует функционал загрузки сохранений через стартовое или игровое меню (`menu_load`).
  * **Правила именования файлов сохранений:** Имя файла сохранения вводится пользователем, должно состоять только из латинских букв и цифр (`^[a-zA-Z0-9]+$`), а расширение `.json` добавляется движком автоматически.
  * **Структура объекта сохранения:** Файл сохранения должен иметь строго определенный формат (инвентарь и прогресс выражаются только через переменные состояния):
    ```json
    {
      "currentSceneId": "string",
      "variables": {
        "hasKey": true,
        "isTired": false
      }
    }
    ```
* **Ограничение источников данных:** Сценарии загружаются только из локальной файловой системы (`local_only`). Возможность скачивания сценариев по сети HTTP/HTTPS в рамках MVP отсутствует.

## Testing Approaches

Проект должен быть покрыт тестами для обеспечения стабильности при изменении логики движка или структуры сценариев:

* **Модульное тестирование (Unit Tests):**
  * Тестирование логики переходов машины состояний (State Machine) на основе предопределенных мок-сценариев.
  * Тестирование валидатора JSON-сценариев: подача заведомо корректных и некорректных файлов и проверка ожидаемого поведения.
  * Тестирование функций сохранения и загрузки с изоляцией дисковых операций (использование виртуальной файловой системы или моков для `fs`).
* **Интеграционное тестирование (Integration Tests):**
  * Эмуляция игрового цикла (Game Loop) с перехватом потоков `stdin` и `stdout` для симуляции прохождения квеста от начала до конца.
  * Тестирование меню сохранения/загрузки в процессе игры.
* **Инструменты тестирования:** Использование встроенного тест-раннера Node.js (`node:test`) или фреймворка `Jest`/`Vitest`. Тесты должны запускаться локально одной командой `npm test`.

## Coding Standards

* **Язык программирования и стек:**
  * Использовать чистый JavaScript ESM (ECMAScript Modules) без этапа сборки (no build step) для обеспечения максимальной скорости запуска, простоты распространения и отсутствия необходимости в компиляции.
* **Форматирование и стиль:**
  * Обязательное использование ESLint (с конфигурацией, близкой к `eslint-config-clean` или `standard`) и Prettier для поддержания единообразия кода.
* **Принципы написания кода:**
  * Чистые функции (Pure Functions) для вычисления переходов состояний. Машина состояний не должна иметь неконтролируемых побочных эффектов.
  * Асинхронный неблокирующий ввод-вывод для всех операций с файловой системой (использование `fs/promises` и конструкции `async/await`).
  * Понятная и информативная обработка ошибок. Игрок не должен видеть сырые стек-трейсы Node.js при попытке загрузить поврежденный файл сохранения или некорректный сценарий.

## Security Constraints

* **Предотвращение выхода за пределы директории (Path Traversal):**
  * При чтении локальных сценариев или файлов сохранений из текущей директории движок должен строго валидировать пути. Имя файла сохранения не должно содержать символов перехода на уровень выше (`../`), чтобы предотвратить чтение или перезапись системных файлов пользователя. Строгая валидация по регулярному выражению `^[a-zA-Z0-9]+$` для имени сохранения полностью исключает угрозу Path Traversal при записи сохранений.
* **Безопасная десериализация JSON:**
  * Избегать использования небезопасных методов разбора данных, уязвимых к Prototype Pollution.
  * Валидация схемы JSON должна выполняться *до* того, как данные сценария будут переданы в логику машины состояний.
* **Валидация пользовательского ввода в CLI:**
  * Любой ручной ввод игрока (например, ввод имени сохранения или кастомного ответа) должен санироваться и ограничиваться по длине во избежание переполнения буфера или зависания консольного интерфейса.

## Performance Targets

* **Время холодного запуска:** Запуск игры через `npx` (при условии, что пакет уже находится в кэше npm) до отображения главного меню должен занимать не более 300 мс.
* **Потребление оперативной памяти:** Общий объем используемой памяти процессом Node.js во время игры не должен превышать 50 МБ.
* **Отклик интерфейса:** Отрисовка сцены и реакция на выбор игрока должны происходить мгновенно (задержка ввода-вывода менее 16 мс), обеспечивая плавный и комфортный игровой процесс.

## Integration Points

Приложение взаимодействует со следующими внешними системами и окружением:

* **Терминал пользователя (TTY):**
  * Интеграция с потоками `process.stdout` и `process.stdin` для вывода стилизованного текста и считывания нажатий клавиш.
  * Определение поддержки цветов терминалом игрока для адаптивного переключения режимов стилизации (`styled_text`).
* **Локальная файловая система (Local FS):**
  * Чтение файлов игровых сценариев JSON из указанной пользователем локальной папки или из папки по умолчанию внутри пакета (`local_only`).
  * Запись и чтение файлов сохранений (например, `savegame.json`) непосредственно в текущей рабочей директории запуска приложения (`current_directory`).
* **CLI-интерфейс выбора сценария:**
  * Путь к файлу сценария передается как первый позиционный аргумент командной строки (например, `npx my-quest ./scenarios/dungeon.json`). Если аргумент отсутствует, игра предлагает выбрать встроенный сценарий по умолчанию или ввести путь к внешнему JSON-файлу интерактивно через меню выбора.
