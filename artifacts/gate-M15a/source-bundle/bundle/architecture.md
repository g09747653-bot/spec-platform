## Overview

Данный проект представляет собой консольную игру в жанре «текстовый квест» (Text Adventure), разработанную для выполнения в среде Node.js (LTS версии 18 и выше). Основная цель проекта — создание легкого, расширяемого и надежного игрового движка, который полностью отделяет сюжет, сцены, переходы и логику от самого исполняемого кода.

Сюжет и логика квеста описываются во внешних JSON-файлах сценариев. Игра распространяется как npm-пакет и запускается мгновенно с помощью утилиты `npx` (`npx_run`, `npx_execution`), избавляя пользователя от необходимости ручной настройки окружения. Игрок взаимодействует с игрой через интерактивное CLI-меню в терминале, совершая выбор вариантов с клавиатуры. Прогресс прохождения автоматически сохраняется после каждого принятого решения во избежание потери данных, а в конце игры выводится подробная статистика и итог прохождения. Движок работает полностью локально и автономно (`fully_offline`).

## High-Level Architecture Design

Архитектура системы построена на принципах слабой связанности (Loose Coupling) и высокой внутренней зацепленности (High Cohesion). Вся логика разделена на изолированные модули, взаимодействующие через строго определенные ESM-интерфейсы.

Ниже представлена высокоуровневая схема прохождения данных и управления в рамках игровой сессии:

```
                  |         Консоль пользователя          |
                  |             (TTY / CLI)               |
                  +---+-------------------------------+---+
                      |                               ^
        Аргументы /   |                               | Стилизованный вывод
        Ввод игрока   v                               | (styled_text)
                  +---+-------------------------------+---+
                  |           Входной модуль              |
                  |              (index.js)               |
                  +---+-------------------------------+---+
                      |                               |
                      | Загрузка сценария             | Инициализация / Загрузка
                      v                               v
                  +---+-------------------------------+---+
                  |      Scenario Validator           |
                  |     - Проверка схемы (Ajv)        |
                  |     - Проверка связности          |
                  +---+-------------------------------+---+
                      |                               |
        Сценарий      |                               | Инициализация
        валидирован   v                               v
                  +---+-------------------------------+---+
                  |     State Machine & Game Loop     |
                  |     - Текущее состояние           |

                      |               |               |

         Загрузка     |               | после выбора  | файлов сохранений
                      |               v               |
                  +---+---------------+---------------+---+
                  |            Save/Load Manager          |
                  |      - Запись/Чтение с диска          |

                  +-------------------+-------------------+
```

### Основные сценарии взаимодействия

1. **Инициализация игры:** Движок запускается через `npx`. Модуль `index.js` проверяет наличие переданного в аргументах пути к сценарию. Если путь отсутствует, активируется интерактивное CLI-меню выбора встроенных сценариев (из каталога `scenarios/`) или ручного ввода пути к файлу сценария.
2. **Валидация сценария:** Выбранный JSON-файл передается в `Scenario Validator`. Проводится проверка соответствия JSON-схеме, проверка связности ориентированного графа переходов и наличия тупиковых сцен без флага `isEnding`. При обнаружении ошибок игра завершается с выводом понятного сообщения на русском языке.
3. **Стартовое меню и сессия сохранения:** Игрок видит главное меню: «Начать новую игру» (требуется ввести имя сохранения `^[a-zA-Z0-9]+$`), «Загрузить сохраненную игру» (позволяет выбрать существующий файл `.save.json`) или «Выход». Выбранное имя сохранения фиксируется в сессии.
4. **Игровой цикл (Game Loop):** 
   - `State Machine` запрашивает описание текущей сцены.
   - Фильтруются варианты выбора (`options`) на основе текущих переменных состояния (`variables`) и условий доступа (`requiredState`).
   - `CLI View` отрисовывает текст сцены и доступные варианты.
   - Игрок делает выбор с клавиатуры.
   - `State Machine` обновляет переменные согласно `setState`, переключает `currentSceneId` и инкрементирует `stepsCount`.
   - `Save/Load Manager` немедленно выполняет автосохранение прогресса в файл `{saveName}.save.json`.
   - Цикл повторяется, пока не будет достигнута сцена с `"isEnding": true`.
5. **Финал игры:** Отрисовывается итоговый экран со статистикой прохождения (сделанные шаги, финальные переменные), после чего предлагается меню завершения.

## System Modules

### 1. Входной модуль (Bootstrapper / CLI Entrypoint)
* **Файл:** `bin/index.js`
* **Ответственность:**
  * Парсинг аргументов командной строки (`process.argv`).
  * Обеспечение быстрого запуска квеста по переданному пути.
  * Логика интерактивного выбора сценария из папки встроенных квестов (`scenarios/`) при отсутствии аргументов.
  * Передача управления в `State Machine & Game Loop`.
  * Глобальный перехват и обработка ошибок (исключение вывода сырых стек-трейсов Node.js для пользователя).

### 2. Валидатор сценариев (Scenario Validator)
* **Файл:** `lib/validator.js`
* **Ответственность:**
  * Валидация структуры загруженного JSON-сценария на соответствие JSON Schema с использованием библиотеки `ajv`.
  * Статическая проверка связности графа сцен: обход графа из `initialSceneId` (без учета динамических значений в `requiredState`) для выявления недостижимых или изолированных сцен, а также проверки существования всех целевых `nextSceneId`.
  * Валидация бесвыходных сцен: проверка того, что каждая сцена в сценарии имеет либо непустой массив `options` (свойство `minItems: 1` в схеме), либо флаг `"isEnding": true` и заполненное поле `endingType`.
  * Генерация детализированных человекочитаемых сообщений об ошибках структуры сценария на русском языке.

### 3. Движок состояния (State Machine)
* **Файл:** `lib/state-machine.js`
* **Ответственность:**
  * Хранение и обновление текущего состояния игры: `currentSceneId`, `stepsCount` (счетчик шагов), `variables` (объект с булевыми флагами).
  * Вычисление доступных для выбора опций текущей сцены. Функция `getAvailableOptions(scene)` сопоставляет `requiredState` опций со значениями в `variables` (хранящимися внутри экземпляра класса).
  * Неявная инициализация переменных: любая переменная состояния, используемая в сценарии, но не объявленная в `initialState` или в файле сохранения, по умолчанию инициализируется логическим значением `false`.
  * Применение изменений состояния `applyStateChanges(setState)` и осуществление перехода на новую сцену.
  * Сброс состояния до начальных параметров (`initialState`) при перезапуске квеста.

### 4. Менеджер сохранений (Save/Load Manager)
* **Файл:** `lib/save-manager.js`
* **Ответственность:**
  * Сканирование текущей рабочей директории (`process.cwd()`) на наличие файлов сохранений с расширением `.save.json` и валидация их имен по регулярному выражению `^[a-zA-Z0-9]+$`.
  * Чтение файлов сохранений, проверка их на соответствие схеме сохранения.
  * Маркировка поврежденных сохранений меткой `[Поврежден]` в списке выбора без их скрытия из меню. Вывод предупреждения на русском языке при попытке загрузить поврежденный файл.
  * Запись текущего состояния игрока (`currentSceneId`, `stepsCount`, `variables`) и пути к текущему сценарию `scenarioPath` в JSON-файл сохранения.
  * Защита от Path Traversal при чтении параметра `scenarioPath` из файла сохранения (проверка, что отрезолвленный абсолютный путь лежит внутри `process.cwd()` или папки встроенных сценариев пакета).

### 5. Модуль интерфейса (CLI View)
* **Файл:** `lib/cli-view.js`
* **Ответственность:**
  * Интерактивный рендеринг меню (Главное меню, Выбор вариантов, Меню финала) с использованием легковесной библиотеки `prompts` или `inquirer`.
  * Цветовая стилизация текста с использованием библиотеки `chalk` или `yoctocolor` (выделение концовок, предметов, предупреждений).
  * Определение поддержки цветов терминалом и переключение в бесцветный режим при отсутствии поддержки.
  * Санитария и ограничение длины вводимого пользователем текста (имени файла сохранения) для предотвращения сбоев интерфейса терминала.

## Data Model

### JSON-схема сценария (Scenario Schema)

Спецификация структуры сценария описывается следующей JSON-схемой. Она включает строгую условную валидацию (`anyOf`) для гарантирования того, что каждая сцена либо предлагает варианты выбора, либо является логическим завершением игры.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "title": { "type": "string" },
    "description": { "type": "string" },
    "initialSceneId": { "type": "string" },
    "initialState": {
      "type": "object",
      "additionalProperties": { "type": "boolean" }
    },
    "scenes": {
      "type": "object",
      "additionalProperties": {
        "type": "object",
        "properties": {
          "description": { "type": "string" },
          "options": {
            "type": "array",
            "minItems": 1,
            "items": {
              "type": "object",
              "properties": {
                "text": { "type": "string" },
                "nextSceneId": { "type": "string" },
                "requiredState": {
                  "type": "object",
                  "additionalProperties": { "type": "boolean" }
                },
                "setState": {
                  "type": "object",
                  "additionalProperties": { "type": "boolean" }
                }
              },
              "required": ["text", "nextSceneId"]
            }
          },
          "isEnding": { "type": "boolean" },
          "endingType": { "type": "string", "enum": ["win", "lose"] }
        },
        "required": ["description"],
        "anyOf": [
          {
            "properties": { "isEnding": { "const": true } },
            "required": ["isEnding", "endingType"]
          },
          {
            "required": ["options"]
          }
        ]
      }
    }
  },
  "required": ["title", "description", "initialSceneId", "scenes"]
}
```

```json
{
  "title": "Побег из запертой комнаты",
  "description": "Классический демонстрационный квест.",
  "initialSceneId": "start_room",
  "initialState": {
    "hasKey": false
  },
  "scenes": {
    "start_room": {
      "description": "Вы просыпаетесь в темной комнате. Дверь заперта. На столе лежит блестящий предмет.",
      "options": [
        {
          "text": "Осмотреть стол и взять предмет",
          "nextSceneId": "take_key",
          "requiredState": { "hasKey": false }
        },
        {
          "text": "Попробовать открыть дверь",
          "nextSceneId": "door_locked",
          "requiredState": { "hasKey": false }
        },
        {
          "text": "Открыть дверь ключом и выйти",
          "nextSceneId": "victory",
          "requiredState": { "hasKey": true }
        }
      ]
    },
    "take_key": {
      "description": "Вы взяли маленький стальной ключ. Теперь у вас есть доступ к замку.",
      "options": [
        {
          "text": "Вернуться к двери",
          "nextSceneId": "start_room",
          "setState": { "hasKey": true }
        }
      ]

    "door_locked": {
      "description": "Дверь заперта наглухо. Без ключа замок не поддается.",

      "endingType": "win"

```

### Схема сохранения (Save File Schema)

Файл сохранения записывается в формате JSON со специализированным расширением `.save.json`. Структура строго валидируется по следующей схеме:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "scenarioPath": { "type": "string" },
    "currentSceneId": { "type": "string" },
    "stepsCount": { "type": "integer", "minimum": 0 },
    "variables": {
      "type": "object",
      "additionalProperties": { "type": "boolean" }
    }
  },
  "required": ["scenarioPath", "currentSceneId", "stepsCount", "variables"]
}
```

#### Пример файла сохранения (`player1.save.json`):

```json
{
  "scenarioPath": "scenarios/demo.json",
  "currentSceneId": "start_room",
  "stepsCount": 2,
  "variables": {
    "hasKey": true
  }
}
```

## Security Architecture

### 1. Предотвращение Path Traversal (Обход директорий)

Угроза обхода директорий возникает при ручном вводе имени сохранения игроком, а также при автоматическом чтении параметра `scenarioPath` из ранее созданных файлов сохранения.

* **Защита при записи сохранений:**
  Ввод имени файла сохранения строго валидируется регулярным выражением:
  ```javascript
  const SAFE_SAVE_NAME_REGEX = /^[a-zA-Z0-9]+$/;
  ```
  Любые символы перехода на уровень выше (`..`, `/`, `\`) физически не могут пройти проверку. Движок самостоятельно добавляет расширение `.save.json`, формируя путь в виде `path.join(process.cwd(), `${validatedName}.save.json`)`. Это полностью исключает запись файлов за пределами текущей рабочей директории.
* **Защита при чтении `scenarioPath` из файлов сохранения:**
  При загрузке сохранения значение `scenarioPath` преобразуется в абсолютный путь через `path.resolve`. 
  Движок применяет следующий алгоритм разрешения путей для встроенных сценариев и локальных файлов:
  1. Сначала проверяется существование файла по относительному пути непосредственно в текущей рабочей директории запуска (`process.cwd()`).
  2. Если файл по данному пути не найден или значение `scenarioPath` начинается со специального префикса (например, `scenarios/`), движок пытается разрешить этот путь относительно каталога встроенных сценариев `scenarios/` внутри директории установки самого npm-пакета.
  3. Полученный в результате абсолютный путь проверяется на безопасность: итоговый разрешенный абсолютный путь должен физически находиться строго внутри текущей рабочей директории (`process.cwd()`) или папки встроенных сценариев установленного npm-пакета. Если путь выходит за рамки этих директорий, загрузка отклоняется с выводом предупреждения на русском языке.

### 2. Безопасная десериализация JSON (Prototype Pollution Prevention)

* Для разбора файлов JSON используется стандартный `JSON.parse()`.
* Все полученные объекты перед передачей в логические модули машины состояний и интерфейса проходят обязательную жесткую валидацию через библиотеку `ajv` на соответствие JSON-схеме с флагом `additionalProperties: false` (или явным описанием всех допустимых свойств). Это гарантирует невозможность внедрения скрытых свойств (таких как `__proto__` или `constructor.prototype`), способных повлиять на логику выполнения Node.js.

### 3. Санитария CLI-ввода

* Длина строки ввода имени сохранения ограничивается на уровне интерфейса (максимум 30 символов).
* Недопустимые символы отсекаются на этапе ввода, предотвращая переполнение буфера ввода терминала и некорректное отображение интерактивного меню.

## Deployment & Operations

### Конфигурация дистрибутива (package.json)

Для успешного запуска через `npx` пакет должен содержать в корне `package.json` поле `bin`, указывающее на точку входа:

```json
{
  "name": "node-text-quest-engine",
  "version": "1.0.0",
  "type": "module",
  "bin": {
    "text-quest": "./bin/index.js"
  },
  "engines": {
```

## Observability

Ввиду полностью локального формата исполнения, традиционные серверные инструменты мониторинга (APM, внешнее логирование) отсутствуют. Наблюдаемость системы обеспечивается за счет локальных механизмов:

### 1. Уровни логирования и обработка ошибок

Все ошибки разделяются на два класса:
* **Пользовательские ошибки (Игровой уровень):** Невалидный файл сохранения, отсутствие прав доступа к директории, ошибки структуры квеста. Они перехватываются глобальным обработчиком, стилизуются с помощью красного цвета и выводятся пользователю в понятном текстовом виде на русском языке. Приложение корректно завершает работу с кодом `1` (или возвращает пользователя в меню, если ошибка не критична для продолжения работы движка).
* **Системные ошибки (Исключения выполнения):** Внутренние непредвиденные ошибки движка. Выводится краткая информация об ошибке в терминал.

### 2. Режим отладки для создателей сценариев (Debug Mode)

Для создателей сценариев в движке предусмотрен режим отладки, который активируется с помощью флага окружения `QUEST_DEBUG=1` или аргумента командной строки `--debug`. 

При включенном режиме отладки:
* В процессе инициализации сценария в стандартный поток ошибок (`process.stderr`) выводится подробный отчет о графе сцен (список всех вершин, обнаруженные связи, изолированные вершины, тупиковые вершины).
* При каждом переходе игрока выводится лог изменений переменных состояния: `[DEBUG] State changed: "hasKey" (false -> true), Current Scene: "take_key"`.
* Выводится точное время, затраченное на парсинг и валидацию сценария (в миллисекундах).

## Testing Strategy

Стабильность движка обеспечивается трехуровневым тестированием с использованием встроенного тест-раннера Node.js (`node:test`). Тесты запускаются локально командой `npm test`.

### 1. Модульное тестирование (Unit Tests)

* **Тестирование Машины состояний (`test/state.test.js`):**
  * Подача мок-состояния и проверка фильтрации опций на основе `requiredState`.
  * Проверка корректности применения переходов и изменения переменных (`setState`).
  * Проверка инкрементации счетчика шагов (`stepsCount`).
  * Проверка неявной инициализации необъявленных переменных значением `false`.
* **Тестирование Валидатора (`test/validator.test.js`):**
  * Подача корректного JSON-сценария и проверка успешного прохождения валидации.
  * Подача JSON-файлов с нарушенной структурой (отсутствие обязательных полей) и сверка списка возвращаемых ошибок.
  * Подача графов с изолированными вершинами или несуществующими переходами `nextSceneId` для проверки алгоритмов статического обхода графа.
  * Проверка отбраковки сцен без опций выбора и без флага окончания игры.
* **Тестирование Менеджера сохранений (`test/save.test.js`):**
  * Использование виртуальной файловой системы (мокирование модуля `fs/promises`) для проверки записи и чтения сохранений.
  * Тестирование регулярного выражения для валидации имен файлов.
  * Попытка передачи некорректного (небезопасного) пути в качестве параметра `scenarioPath` и проверка срабатывания защиты от Path Traversal.

### 2. Интеграционное тестирование (Integration Tests)

* **Тестирование игрового цикла (`test/integration.test.js`):**
  * Эмуляция потоков `process.stdin` и `process.stdout` с помощью потоков чтения-записи (Streams).
  * Симуляция последовательности выборов игрока от старта до победного финала на базе тестового сценария.
  * Верификация того, что после каждого шага файл сохранения действительно обновляется на диске, а итоговая статистика в конце выводится в верном формате.

## Key Solution Decisions

Ниже перечислены и обоснованы ключевые архитектурные компромиссы и решения, принятые в процессе проектирования текстового квеста:

1. **Использование нативного ESM без транспиляции (No Build Step):**
   * *Решение:* Писать код на чистом современном JavaScript ES-модулей без использования Babel, TypeScript или Webpack.
   * *Обоснование:* Это гарантирует мгновенный запуск игры, минимизирует размер npm-пакета, упрощает отладку кода и избавляет от необходимости поддержки сложных конфигураций сборщиков.
2. **Исключение сложных TUI фреймворков:**
   * *Решение:* Использовать `prompts`/`inquirer` для выбора вариантов вместо тяжелых TUI библиотек вроде `blessed`.
   * *Обоснование:* `blessed` и его аналоги имеют плохую совместимость со многими эмуляторами терминалов (особенно на Windows в старых версиях CMD) и увеличивают потребление памяти. Легковесный CLI-интерфейс со стилизованным текстом гарантирует 100% стабильность отображения на любой платформе.
3. **Единоразовый ввод имени сохранения при старте:**
   * *Решение:* Запрашивать имя сохранения только один раз при начале «Новой игры», фиксировать его в рамках сессии и автоматически перезаписывать этот файл на каждом шаге без дополнительных вопросов к пользователю.
   * *Обоснование:* Это обеспечивает бесшовность игрового процесса. Игрок не отвлекается на подтверждение сохранений во время чтения сюжета, а его прогресс гарантированно защищен от внезапного закрытия терминала.
4. **Отображение поврежденных файлов сохранений с меткой:**
   * *Решение:* Не скрывать поврежденные файлы `.save.json` из меню загрузки, а помечать их как `[Поврежден]` и блокировать выбор.
   * *Обоснование:* Если бы движок просто скрывал битые файлы, игрок мог бы подумать, что его прогресс безвозвратно пропал из-за бага программы. Вывод поврежденного файла с понятным сообщением об ошибке позволяет пользователю понять истинную причину проблемы (например, некорректное ручное редактирование файла).
5. **Отказ от массивов инвентаря в пользу флагов состояния:**
   * *Решение:* Моделировать предметы и квестовый инвентарь только в виде булевых флагов в объекте `variables` (например, `"hasKey": true`).
   * *Обоснование:* Это сильно упрощает JSON Schema и логическую машину состояний. Нет необходимости реализовывать сложные операции поиска по массивам, проверки емкости инвентаря и т.д. Логика переходов полностью укладывается в классическую булеву алгебру условий.
