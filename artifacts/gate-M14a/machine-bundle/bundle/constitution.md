## Project Vision

Проект представляет собой сверхлегкий, надежный и быстрый консольный планировщик личных дел для одного пользователя (`single_user`), работающий полностью локально. Основная цель продукта — предоставить пользователю мгновенный доступ к управлению задачами прямо из терминала без необходимости подключения к сети (`completely_offline`) или использования сложных веб-интерфейсов. 

Планировщик ориентирован на максимальную простоту использования и следование методологии персональной продуктивности: быстро зафиксировать задачу с датой выполнения, просмотреть актуальные дела на сегодня и отметить задачу как выполненную. Все данные хранятся локально на компьютере пользователя, обеспечивая стопроцентную приватность и независимость от сторонних облачных сервисов.

## Core Principles

* **Интерфейс командной строки (`cli_arguments`):** Все взаимодействия осуществляются посредством аргументов командной строки. Никаких сложных интерактивных меню или графических интерфейсов. Утилита (назовем ее `todo`) должна строго поддерживать следующий набор команд, аргументов и опций:
  * `todo add "<title>" [--date YYYY-MM-DD]` — Добавить новую задачу с указанным названием. Если опция `--date` не указана, по умолчанию используется текущая дата системы в формате `YYYY-MM-DD`.
  * `todo list [--all]` — Вывести список задач на сегодня, включая все просроченные и невыполненные задачи из прошлого (`overdue_included`). По умолчанию выводятся только невыполненные задачи. При использовании дополнительного флага `--all` выводятся все невыполненные задачи (включая просроченные), а также выполненные задачи, у которых дата выполнения совпадает с текущей датой. Список должен быть отсортирован по дате выполнения (`due_date`) по возрастанию, а задачи с одинаковой датой — по ID по возрастанию.
  * `todo done <id>` — Отметить задачу с указанным числовым идентификатором `<id>` как выполненную. Если задачи с указанным `<id>` не существует в базе данных, утилита должна вывести понятное сообщение об ошибке в поток ошибок `stderr` и завершить работу с кодом возврата `1`.
* **Локальная автономность (`completely_offline`):** Приложение не имеет доступа к сети Интернет. Это гарантирует полную конфиденциальность данных, стабильность работы в любых условиях и отсутствие задержек на сетевые запросы.
* **Надежность хранения данных (`auto_backups`):** Любое изменение данных сопровождается автоматическим созданием резервных копий, минимизируя риск потери информации при сбоях системы.
* **Прямолинейная логика фокусировки (`overdue_included`):** Просмотр задач на сегодня должен показывать не только запланированные на текущую дату дела, но и все ранее просроченные и невыполненные задачи. Это помогает держать фокус на долгах и не терять важные дела из виду.
* **Ограничение скоупа ради простоты (Out of Scope):** В системе жестко исключены любые сложные связи между задачами (`no_relations`), вложенные файлы (`no_attachments`), повторяющиеся события (`no_recurrence`) и инструменты совместной работы (`no_collaboration`). Продукт остается чистым и прямолинейным списком задач.

## Technology Constraints

* **Язык разработки:** Python 3.10+ (или иной выбранный компилируемый/интерпретируемый язык, обеспечивающий мгновенный запуск в терминале).
* **База данных (`sqlite_format`):** Использование СУБД SQLite для хранения данных. База данных представляет собой локальный файл `todo.db` в рабочей директории приложения (определяемой согласно разделу `Integration Points`).
* **Безопасность БД (`plain_sqlite`):** База данных хранится в стандартном, нешифрованном формате SQLite. Приложение не должно использовать библиотеки шифрования базы данных (такие как SQLCipher), полагаясь на стандартные права доступа операционной системы к файлу.
* **Отсутствие сетевого стека:** В коде приложения запрещено использование библиотек для работы с сетью (`requests`, `urllib`, сокеты и т.д.). Любая попытка сетевого взаимодействия должна блокироваться на этапе сборки и статического анализа кода.
* **Зависимости:** Минимальное количество внешних библиотек. Для парсинга аргументов командной строки должны использоваться стандартные средства (например, `argparse` для Python) или легковесные проверенные библиотеки.

## Architecture Constraints

* **Тип интерфейса (`cli_arguments`):** Архитектура должна быть разделена на три четких слоя:
  1. *CLI-интерфейс:* отвечает за разбор аргументов командной строки, валидацию входных параметров и форматирование вывода для пользователя.
  2. *Сервисный слой (Бизнес-логика):* содержит правила обработки задач (например, логику отбора задач для списка на сегодня, включая просроченные — `overdue_included`).
  3. *Слой доступа к данным (DAO/Repository):* инкапсулирует работу с файлом SQLite.
* **Схема базы данных:** Таблица `tasks` со следующей структурой:
  * `id` (INTEGER, PRIMARY KEY, AUTOINCREMENT)
  * `title` (TEXT, NOT NULL)
  * `due_date` (TEXT/DATE, NOT NULL) — дата в формате ISO 8601 (`YYYY-MM-DD`)
  * `is_completed` (INTEGER/BOOLEAN, DEFAULT 0)
  * `created_at` (TEXT/DATETIME, DEFAULT CURRENT_TIMESTAMP)
* **Миграции БД (`clean_slate`):** Применяется подход создания структуры с чистого листа. При первом запуске приложение должно автоматически создавать рабочую директорию и поддиректорию `backups`, если они еще не существуют на диске. Если файл базы данных отсутствует, он создается автоматически, и в нем разворачивается актуальная схема таблиц. Исторические миграции старых версий отсутствуют, схема инициализируется единоразово.
* **Механизм резервного копирования (`auto_backups`):** Перед выполнением любой транзакции записи в БД (добавление дела, отметка о выполнении) приложение должно создать резервную копию текущего файла базы данных в поддиректорию `backups`. Имя файла резервной копии должно формироваться как `todo.db.bak.<timestamp>`, где `<timestamp>` — временная метка в формате `YYYYMMDDHHMMSS`. Приложение должно хранить ровно 5 последних резервных копий. При создании нового бэкапа самый старый файл в директории `backups` должен автоматически удаляться.

## Testing Approaches

* **Модульное тестирование (Unit Testing):**
  * Тестирование парсера аргументов командной строки на корректность разбора дат, названий задач, флагов и некорректных аргументов.
  * Тестирование логики фильтрации задач "на сегодня": валидация того, что в список попадают задачи с текущей датой, а также невыполненные задачи с датой в прошлом (`overdue_included`).
  * Тестирование корректности поведения при запросе выполненных задач с флагом `--all`.
* **Интеграционное тестирование (Integration Testing):**
  * Тестирование взаимодействия с реальной базой данных SQLite на временных файлах (создание схемы `clean_slate`, запись, обновление статуса, чтение).
  * Тестирование поведения при попытке отметить выполненной несуществующую задачу: проверка записи ошибки в `stderr` и возврата кода `1`.
  * Тестирование механизма `auto_backups`: проверка, что перед записью создается корректный бэкап-файл с правильным именем `todo.db.bak.<timestamp>`, а в случае сбоя записи исходный файл БД остается неповрежденным. Проверка автоматического удаления старых резервных копий с сохранением ровно 5 последних.
* **Системное тестирование (E2E / CLI Testing):**
  * Автоматический запуск CLI-утилиты в изолированном окружении с различными параметрами командной строки и проверка кодов возврата (Exit Codes) и вывода в `stdout`/`stderr`.

## Coding Standards

* **Форматирование кода:** Обязательное соответствие официальным стандартам используемого языка (например, PEP 8 для Python). Использование автоматических линтеров и форматировщиков кода перед каждым коммитом.
* **Обработка ошибок:**
  * Ошибки синтаксиса CLI (неверные опции, ошибки парсинга аргументов) должны приводить к завершению работы с кодом `2`.
  * Семантические ошибки данных (такие как несуществующий ID при вызове `todo done`, неверный формат даты при добавлении задачи) должны приводить строго к завершению работы с кодом `1`.
  * При возникновении ошибок утилита должна выводить понятное сообщение об ошибке в поток ошибок `stderr`.
  * Системные ошибки (невозможность записать файл базы данных, повреждение SQLite) должны выводить информативное сообщение о проблеме с правами доступа или целостностью данных в `stderr` и завершаться с кодом `1`. Трейсбеки не должны показываться конечному пользователю в штатном режиме работы.
* **Логирование:** Ввиду специфики консольного утилитарного интерфейса, логирование в консоль по умолчанию отключено. Допускается запись логов отладки в файл, путь к которому может быть настроен через переменные окружения.
* **Именование переменных и методов:** Должно быть самодокументируемым. Все идентификаторы, имена полей базы данных, ключи JSON и CLI-опции пишутся на английском языке и строго соответствуют контрактам (например, `--date`, `todo list`, `todo done`).

## Security Constraints

* **Локальный доступ (`plain_sqlite`):** Так как база данных не шифруется, безопасность данных целиком ложится на разграничение прав доступа в операционной системе. Приложение должно создавать файл базы данных с правами доступа, разрешающими чтение и запись только текущему пользователю (например, `chmod 600` в UNIX-подобных системах).
* **Валидация ввода:** Защита от SQL-инъекций. Все SQL-запросы к локальной SQLite должны выполняться строго с использованием параметризованных запросов (placeholder-ов). Прямая склейка строк для формирования SQL-запросов категорически запрещена.
* **Отсутствие сетевых уязвимостей:** В силу принципа `completely_offline` риски удаленного выполнения кода (RCE) или утечки данных через сеть сведены к нулю. Запрещено использовать любые зависимости, требующие сетевого подключения или открывающие локальные порты.

## Performance Targets

* **Время отклика (Latency):** Время выполнения любой команды (например, добавление дела или вывод списка) не должно превышать 50-100 миллисекунд. Пользователь должен ощущать работу утилиты как мгновенную.
* **Потребление ресурсов:** Минимальный объем оперативной памяти при работе (не более 15-20 МБ для интерпретируемых языков, менее 5 МБ для компилируемых).
* **Индексация данных:** В таблице `tasks` базы данных SQLite должны быть созданы индексы по полям `due_date` и `is_completed` для обеспечения мгновенной выборки задач на сегодня даже при накоплении тысяч записей в истории.

## Integration Points

* **Локальная файловая система:**
  * Путь к рабочей директории приложения (где хранятся база данных и резервные копии) определяется по следующему приоритету:
    1. Переменная окружения `TODO_WORK_DIR`.
    2. Стандартная директория конфигурации пользователя в ОС (например, `~/.config/todo/` на Linux/macOS или `%APPDATA%/todo/` на Windows).
  * Резервные копии складываются в поддиректорию `backups` внутри рабочей директории.
* **Интеграция с потоками терминала:**
  * Стандартный вывод (`stdout`) используется для вывода списков задач и успешных подтверждений. При успешном выполнении `todo add` в `stdout` должен выводиться только ID созданной задачи. При успешном выполнении `todo done` в `stdout` ничего не выводится (утилита завершается молча). Каждая задача при выводе списка должна отображаться на отдельной строке. Поля разделяются символом табуляции (`\t`) в следующем формате: `<id>\t<статус>\t<дата>\t<название>`, где `<статус>` равен `[ ]` для невыполненных задач и `[X]` для выполненных задач (которые выводятся только при указании флага `--all` в команде `todo list`), а `<дата>` представлена в формате `YYYY-MM-DD`. Вывод должен быть чистым, пригодным для обработки стандартными UNIX-утилитами (`grep`, `awk`, `xargs`).
  * Поток ошибок (`stderr`) строго зарезервирован для вывода сообщений об ошибках парсинга параметров, проблем с файловой системой, попыток обработки несуществующих ID или иных некорректных действий пользователя.
