## Overview

Проект представляет собой сверхлегкий, надежный и быстрый консольный планировщик личных дел для одного пользователя (`single_user`), работающий полностью локально в автономном режиме (`completely_offline`). Основная цель продукта — предоставить пользователю мгновенный доступ к управлению задачами прямо из терминала без необходимости подключения к сети или использования сложных графических интерфейсов.

Планировщик ориентирован на максимальную простоту использования и персональную продуктивность: быстро зафиксировать задачу с датой выполнения, просмотреть актуальные дела на сегодня и отметить задачу как выполненную. Все данные хранятся локально на компьютере пользователя в СУБД SQLite (`sqlite_format`, `plain_sqlite`), обеспечивая стопроцентную приватность и независимость от сторонних облачных сервисов.

В соответствии с принципом фокуса на простоте из области проектирования (Out of Scope) полностью исключены:
* Любые связи и зависимости между задачами (`no_relations`).
* Прикрепление файлов или документов к задачам (`no_attachments`).
* Повторяющиеся задачи или регулярные события (`no_recurrence`).
* Инструменты совместной работы, синхронизации или многопользовательского доступа (`no_collaboration`).

Управление планировщиком осуществляется исключительно через аргументы командной строки (`cli_arguments`). Ключевые возможности включают в себя быстрое добавление задачи с датой, вывод списка невыполненных задач на сегодня с автоматическим включением просроченных дел из прошлого (`overdue_included`), а также отметку задач как выполненных с автоматическим созданием резервных копий базы данных перед любым изменением (`auto_backups`).

## High-Level Architecture Design

Архитектура системы разработана по принципу разделения ответственности и организована в виде трех автономных слоев внутри единого исполняемого CLI-приложения (Standalone CLI pipeline):

1. **CLI Presentation Layer (Интерфейс командной строки):**
   * Отвечает за синтаксический анализ аргументов командной строки.
   * Выполняет первичную валидацию типов данных (например, проверка, что идентификатор задачи вводится как положительное целое число).
   * Осуществляет форматирование вывода в потоки `stdout` и `stderr`, а также обеспечивает возврат соответствующих кодов завершения процесса (Exit Codes 0, 1, 2) в операционную систему.

2. **Business Logic Layer (Сервисный слой):**
   * Реализует основные бизнес-правила приложения.
   * Управляет логикой выборки задач «на сегодня» с учетом текущей системной даты, включая фильтрацию просроченных и невыполненных задач (`overdue_included`).
   * Оркестрирует процесс транзакционной записи: инициирует создание резервной копии базы данных перед вызовом методов изменения данных в репозитории.
   * Контролирует ротацию резервных копий в поддиректории `backups`.

3. **Data Access Layer (Слой доступа к данным / Репозиторий):**
   * Инкапсулирует все прямые обращения к локальной базе данных SQLite.
   * Выполняет автоматическую инициализацию базы данных и создание табличной структуры с чистого листа при первом запуске (`clean_slate`).
   * Выполняет SQL-запросы, используя исключительно параметризованные выражения (placeholders) для исключения рисков SQL-инъекций.

### Схема управления и потоков данных (Data & Control Flow)

```
 [ Пользователь ] 
        │
        ▼ (Команда CLI с аргументами)
┌────────────────────────────────────────────────────────┐
│ CLI Presentation Layer (todo)                          │
│                                                        │
│  1. Разбор аргументов командной строки                 │
│  2. Валидация входного синтаксиса                      │
│  3. Обработка исключений и вывод в stdout/stderr       │
└───────────────────────┬────────────────────────────────┘
                        │
                        ▼ (Вызов бизнес-методов)
┌────────────────────────────────────────────────────────┐
│ Business Logic Layer (TaskService & BackupService)     │
│                                                        │
│  1. Определение текущей даты системы                   │
│  2. Проверка ограничений (непустой заголовок, даты)    │
│  3. Запуск создания резервной копии (перед записью)    │
│  4. Проведение ротации бэкапов (до 5 файлов)           │
└───────────────────────┬────────────────────────────────┘
                        │
                        ▼ (SQL-транзакции)
┌────────────────────────────────────────────────────────┐
│ Data Access Layer (TaskRepository)                     │
│                                                        │
│  1. Авто-инициализация БД (clean_slate)                │
│  2. Выполнение параметризованных запросов к todo.db    │
└────────────────────────────────────────────────────────┘
```

## System Modules

Приложение состоит из следующих функциональных модулей:

* **CLI Parser Module (Модуль разбора аргументов):**
  Реализует разбор входных аргументов командной строки на базе стандартных библиотек парсинга (например, `argparse` для Python). Отвечает за выявление синтаксических ошибок (неизвестные флаги, отсутствие обязательных параметров). В случае обнаружения ошибок разбора завершает работу с кодом возврата `2`.
* **Environment Bootstrapper (Модуль инициализации окружения):**
  Выполняется при старте приложения. Проверяет наличие рабочей директории (по приоритету: `TODO_WORK_DIR` -> путь по умолчанию в ОС). Если папки отсутствуют, создает их (применяя корректные права доступа), включая поддиректорию `backups`. Проверяет наличие файла `todo.db`. При его отсутствии инициирует создание схемы данных с чистого листа (`clean_slate`).
* **Task Service (Сервис управления задачами):**
  Координирует выполнение операций над задачами. Содержит логику валидации даты выполнения (проверка диапазона 1900–2100 гг., валидность календаря). Перед вызовом методов добавления или изменения задачи в БД запрашивает у `Backup Service` создание резервной копии.
* **Backup Service (Сервис резервного копирования):**
  Отвечает за создание резервных копий файла `todo.db` в директории `backups` с уникальным именем, содержащим временную метку высокого разрешения UTC. Реализует алгоритм ротации: считывает содержимое директории бэкапов, сортирует файлы лексикографически и удаляет самый старый, если общее количество копий превышает 5. В случае сбоя копирования генерирует исключение, приводящее к отмене транзакции.
* **Database Repository (Репозиторий базы данных):**
  Отвечает за непосредственное соединение с файлом SQLite, открытие транзакций, чтение и запись данных. Создает индексы для ускорения поиска. Обеспечивает безопасное выполнение SQL-команд через биндинг параметров.

## Data Model

Все данные хранятся локально в единственном файле базы данных SQLite с именем `todo.db`. Структура базы данных состоит из одной таблицы `tasks` и двух индексов.

### Схема таблицы `tasks`

```sql
CREATE TABLE IF NOT EXISTS tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    due_date TEXT NOT NULL,
    is_completed INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### Описание полей таблицы `tasks`

| Поле | Тип данных в SQLite | Ограничения | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | PRIMARY KEY AUTOINCREMENT | Уникальный автоинкрементный идентификатор задачи в системе. |
| `title` | `TEXT` | NOT NULL | Название задачи. Строка не может быть пустой или состоять только из пробелов. |
| `due_date` | `TEXT` | NOT NULL | Дата выполнения в формате ISO 8601: `YYYY-MM-DD`. |
| `is_completed` | `INTEGER` | NOT NULL DEFAULT 0 | Статус выполнения: `0` (не выполнено), `1` (выполнено). |
| `created_at` | `TEXT` | NOT NULL DEFAULT CURRENT_TIMESTAMP | Системное время создания записи в формате UTC (`YYYY-MM-DD HH:MM:SS`). |

### Индексы базы данных

Для обеспечения высокой производительности поиска и фильтрации задач при накоплении записей в БД создаются следующие индексы:

```sql
CREATE INDEX IF NOT EXISTS idx_tasks_due_date ON tasks(due_date);
CREATE INDEX IF NOT EXISTS idx_tasks_is_completed ON tasks(is_completed);
```

### Формат резервных копий

Резервные копии базы данных представляют собой полные физические копии файла `todo.db`.
* **Директория хранения:** `<WORK_DIR>/backups/`
* **Шаблон именования:** `todo.db.bak.YYYYMMDDHHMMSSffffff`, где `ffffff` — микросекунды в формате UTC. Это предотвращает коллизии имен при высокой частоте вызовов (например, во время выполнения автоматических тестов или скриптов пакетного импорта).
* **Пример имени файла:** `todo.db.bak.20260330154500123456`

## API / Protocol Design

Взаимодействие с утилитой осуществляется исключительно через вызов консольной команды `todo` с аргументами. Результаты выводятся в потоки `stdout`/`stderr`. Код возврата (Exit Code) сообщает о статусе завершения.

### 1. Команда добавления задачи (`todo add`)

* **Формат вызова:** `todo add "<title>" [--date YYYY-MM-DD]`
* **Входные параметры:**
  * `<title>` (строка, обязательный) — название создаваемой задачи. Должно содержать хотя бы один непробельный символ.
  * `--date` (строка, опциональный) — дата выполнения в формате `YYYY-MM-DD`. Если не указан, подставляется текущая системная дата. Дата должна находиться в диапазоне от `1900-01-01` до `2100-12-31` и быть реальной календарной датой.
* **Результат при успешном выполнении:**
  * Поток `stdout`: выводится строго числовой идентификатор (`id`) созданной задачи и символ перевода строки. Никаких дополнительных символов или текста.
  * Поток `stderr`: пустой.
  * Код возврата: `0`.
* **Обработка ошибок:**
  * Передана пустая строка или пробелы в `<title>`: вывод в `stderr` сообщения об ошибке валидации, код возврата `1`.
  * Неверный формат даты или несуществующая дата: вывод в `stderr` сообщения об ошибке формата даты, код возврата `1`.
  * Сбой при создании резервной копии или записи в БД: вывод в `stderr` сообщения о системной ошибке, транзакция откатывается, код возврата `1`.
  * Ошибка синтаксиса CLI (например, неизвестный флаг): вывод в `stderr`, код возврата `2`.

### 2. Команда просмотра списка задач (`todo list`)

* **Формат вызова:** `todo list [--all]`
* **Входные параметры:**
  * `--all` (опциональный флаг) — указывает на необходимость вывода выполненных за сегодня задач в дополнение к невыполненным.
* **Логика фильтрации задач:**
  Для обеспечения корректности фильтрации при разнице часовых поясов приложение **категорически не должно** использовать встроенную функцию SQLite `CURRENT_DATE` (которая всегда возвращает дату в часовом поясе UTC). Вместо этого текущая локальная системная дата вычисляется на стороне приложения в его локальном часовом поясе и явно передается в качестве строкового параметра в SQL-запрос.
  * **Без флага `--all`:** выбираются все невыполненные задачи (`is_completed = 0`), у которых `due_date <= ?`, где плейсхолдер заменяется на текущую локальную системную дату приложения в формате `YYYY-MM-DD` (включая просроченные — `overdue_included`).
  * **С флагом `--all`:** выбираются все невыполненные задачи (`is_completed = 0`), включая просроченные, а также выполненные задачи (`is_completed = 1`), у которых `due_date = ?`, где плейсхолдер заменяется на текущую локальную системную дату приложения в формате `YYYY-MM-DD`.
* **Сортировка вывода:**
  * Поле `due_date` по возрастанию (ASC).
  * При совпадении дат — по поле `id` по возрастанию (ASC).
* **Формат вывода при успешном выполнении:**
  * Данные выводятся в поток `stdout` в текстовом виде. Каждая задача выводится на отдельной строке. Вывод не содержит строку заголовков столбцов (строка заголовка полностью отсутствует). Поля разделяются исключительно символом табуляции (`\t`):
    `<id>\t<статус>\t<дата>\t<название>`
  * Строгое описание строкового представления статуса задачи:
    * Для невыполненных задач в поле статуса выводится строка `[ ]` (открывающая квадратная скобка, пробел, закрывающая квадратная скобка).
    * Для выполненных задач в поле статуса выводится строка `[X]` (открывающая квадратная скобка, заглавная латинская буква X, закрывающая квадратная скобка).
  * *Пример вывода:*
    `12\t[ ]\t2026-03-30\tКупить молоко`
    `15\t[X]\t2026-03-30\tПозвонить коллеге`
  * Если подходящих задач нет, поток `stdout` остается пустым.
  * Поток `stderr`: пустой.
  * Код возврата: `0`.
* **Обработка ошибок:**
  * Системные ошибки чтения файла БД: вывод в `stderr`, код возврата `1`.
  * Ошибка синтаксиса CLI: вывод в `stderr`, код возврата `2`.

### 3. Команда завершения задачи (`todo done`)

* **Формат вызова:** `todo done <id>`
* **Входные параметры:**
  * `<id>` (обязательный) — числовой идентификатор задачи.
* **Поведение при повторном завершении задачи:**
  * Если задача с указанным `<id>` уже имеет статус выполненной (`is_completed = 1`), утилита выполняет успешную холостую операцию (noop). В этом случае утилита возвращает код `0`, не создает резервную копию базы данных и не производит никаких операций перезаписи файла базы данных, так как статус задачи не изменился.
* **Результат при успешном выполнении (включая сценарий noop):**
  * Поток `stdout`: пустой.
  * Поток `stderr`: пустой.
  * Код возврата: `0`.
* **Обработка ошибок:**
  * Параметр `<id>` не является положительным целым числом: расценивается как синтаксическая ошибка CLI, вывод сообщения в `stderr`, код возврата `2`.
  * Задача с указанным `<id>` отсутствует в базе данных: вывод сообщения в `stderr`, код возврата `1`.
  * Ошибка создания автоматической резервной копии или сбой транзакции записи (для задач, статус которых действительно меняется с `0` на `1`): вывод сообщения в `stderr`, операция отменяется, код возврата `1`.

### Матрица кодов возврата (Exit Codes)

| Код возврата | Тип ошибки | Описание сценария | Направление вывода |
| :---: | :--- | :--- | :--- |
| **0** | Успех / Noop | Команда выполнена успешно, либо выполнена холостая операция (noop) для уже завершенной задачи. | `stdout` (согласно спецификации команды) |
| **1** | Семантическая или системная ошибка | Неверный формат даты, пустой заголовок, несуществующий ID задачи, сбой дисковой подсистемы, ошибка создания бэкапа. | `stderr` (сообщение на русском языке) |
| **2** | Синтаксическая ошибка CLI | Передана неизвестная команда, неверные флаги, отсутствует обязательный параметр, нечисловой ID в `todo done`. | `stderr` (сообщение на русском языке) |

## Security Architecture

Поскольку приложение спроектировано для работы в изолированном локальном окружении (`completely_offline`), архитектура безопасности сфокусирована на защите локальных данных и предотвращении угроз внедрения кода:

1. **Разграничение прав доступа в операционной системе:**
   * База данных хранится в открытом (нешифрованном) формате SQLite, что исключает накладные расходы на криптографические библиотеки.
   * При работе в UNIX-подобных операционных системах (Linux, macOS) приложение при создании рабочей директории и поддиректории `backups/` принудительно устанавливает права доступа `0700` (`chmod 700`), разрешая чтение, запись и переход (выполнение) исключительно владельцу процесса. Без флага исполнения (`x`) на директории доступ к файлу базы данных при повторном запуске утилиты будет заблокирован операционной системой.
   * Для файлов базы данных (`todo.db`) и резервных копий (`todo.db.bak.*`) устанавливаются права доступа `0600` (`chmod 600`), разрешающие чтение и запись исключительно владельцу файла.
   * В системах семейства Windows используются права доступа, наследуемые по умолчанию для папки `%APPDATA%`, без вызова низкоуровневых ACL API.
2. **Защита от SQL-инъекций:**
   * Категорически запрещено динамическое построение SQL-запросов путем конкатенации строк.
   * Все параметры, передаваемые пользователем (название задачи, дата, ID), подставляются в SQL-запросы исключительно с использованием механизмов параметризации СУБД (символы `?` или именованные плейсхолдеры).
3. **Отсутствие сетевого вектора атак:**
   * В коде приложения полностью отсутствуют импорты сетевых библиотек и сокетов. Утилита не открывает порты и не отправляет запросы во внешнюю сеть. Это гарантирует нулевой риск удаленного выполнения кода (RCE) или несанкционированной утечки данных.

## Deployment & Operations

### Требования к среде выполнения

* **Платформа:** Python 3.10+ (без внешних зависимостей, кроме стандартной библиотеки).
* **Операционные системы:** Linux (совместимые с POSIX), macOS, Windows 10/11.

### Определение рабочей директории (`TODO_WORK_DIR`)

При запуска приложение определяет путь к своей рабочей директории в следующем порядке приоритетности:
1. Значение переменной окружения `TODO_WORK_DIR` (если она задана в системе).
2. Стандартный путь в домашней папке пользователя:
   * На Linux / macOS: `~/.config/todo/` (символ `~` автоматически преобразуется в абсолютный путь к домашней директории текущего пользователя).
   * На Windows: `%APPDATA%/todo/` (переменная окружения Windows разворачивается в системный путь к данным приложений).

### Жизненный цикл инициализации окружения (`clean_slate`)

При первом запуске утилиты или при отсутствии необходимых файлов на диске приложение автоматически выполняет следующие действия:
1. Создает рабочую директорию по вычисленному пути (с правами доступа `0700` в UNIX-подобных системах).
2. Создает поддиректорию `backups/` внутри рабочей директории (с правами доступа `0700` в UNIX-подобных системах).
3. Создает файл базы данных `todo.db` строго по абсолютному пути `<WORK_DIR>/todo.db` (с правами доступа `0600` в UNIX-подобных системах), исключая создание БД в текущем каталоге запуска терминала (CWD).
4. Выполняет инициализацию табличной схемы (таблица `tasks` и индексы) с чистого листа, без применения каких-либо исторических файлов миграций.

### Алгоритм автоматического резервного копирования и ротации

Перед выполнением транзакций изменения данных (команды `add` и `done` в случае, если задача действительно меняет статус):
1. **Создание копии:** Текущий рабочий файл `<WORK_DIR>/todo.db` копируется в папку `backups/` под именем `todo.db.bak.YYYYMMDDHHMMSSffffff`, где временная метка генерируется на основе системного времени UTC с точностью до микросекунд. Файл создается с правами доступа `0600` в UNIX-подобных системах.
2. **Проверка успешности:** Если копирование завершилось ошибкой (например, из-за нехватки места на диске или отсутствия прав), транзакция изменения данных отменяется, на экран в `stderr` выводится сообщение об ошибке, работа завершается с кодом `1`.
3. **Ротация:** 
   * Считывается список файлов в папке `backups/`, подходящих под шаблон `todo.db.bak.*`.
   * Полученный список сортируется лексикографически по имени файлов. Так как формат временной метки `YYYYMMDDHHMMSSffffff` обеспечивает совпадение алфавитного и хронологического порядков, сортировка гарантирует правильное распределение файлов по времени создания от старых к новым.
   * Если файлов бэкапов в списке больше 5, приложение удаляет самые старые файлы с диска, оставляя ровно 5 последних резервных копий.

## Observability

Специфика консольного интерфейса накладывает жесткие рамки на наблюдаемость работы приложения. Утилита должна быть полностью предсказуемой и удобной для интеграции с другими консольными инструментами Unix (такими как `grep`, `awk`, `xargs`, `cut`).

### Выделение потоков вывода

* **Стандартный вывод (`stdout`):** Предназначен исключительно для успешных результатов работы. Любой вывод в этот поток должен быть чистым, без декоративного оформления (рамок, пустых строк, приветствий, интерактивных вопросов).
* **Поток ошибок (`stderr`):** Строго зарезервирован для вывода сообщений об ошибках, предупреждений и отладочной информации.

### Обработка ошибок в консоли

При возникновении любых нештатных ситуаций (семантических, системных или синтаксических ошибок) приложение должно:
1. Вывести лаконичное текстовое описание проблемы на русском языке в поток `stderr`. Сообщение должно завершаться символом перевода строки.
2. Категорически запрещается выводить системный трассировочный вывод (stack trace/traceback) в консоль в штатном режиме работы. Пользователь должен видеть только понятную причину сбоя (например: *"Ошибка: Задача с указанным ID не найдена"* или *"Ошибка: Неверный формат даты. Ожидается YYYY-MM-DD"*).
3. Завершить процесс с корректным кодом возврата (`1` или `2`).

### Отладочное логирование (Debug Mode)

Для упрощения диагностики системных проблем (например, сбоев доступа к диску или повреждения файла SQLite) в приложении предусмотрен скрытый режим отладки:
* Если в операционной системе установлена переменная окружения `TODO_DEBUG=1`, приложение начинает записывать подробный технический лог работы (включая stack trace ошибок и выполняемые SQL-запросы) в текстовый файл `todo.log`, который создается непосредственно в рабочей директории приложения. По умолчанию и при отсутствии этой переменной логирование в файл не производится.

## Testing Strategy

Стратегия обеспечения качества консольного планировщика состоит из трех уровней тестирования: модульного, интеграционного и системного (E2E).

### 1. Модульное тестирование (Unit Testing)

Модульные тесты выполняются изолированно без обращения к файловой системе и базе данных (с использованием mock-объектов при необходимости):
* **Тестирование CLI Parser:**
  * Проверка корректности разбора валидных команд (`todo add "Задача" --date 2026-03-30`, `todo list --all`, `todo done 5`).
  * Проверка реакции на синтаксические ошибки (передача неизвестных флагов, отсутствие кавычек в заголовке задачи, нечисловой ID в `todo done`) — ожидается генерация исключения парсера для последующего возврата кода `2`.
* **Тестирование валидатора дат:**
  * Положительные сценарии: корректный разбор дат в формате `YYYY-MM-DD` (включая високосные года, например `2024-02-29`).
  * Отрицательные сценарии: некорректный формат (например, `30.03.2026`), несуществующие календарные даты (например, `2026-02-30`), выход за диапазон лет (например, `1899-12-31` или `2101-01-01`).
* **Тестирование бизнес-логики фильтрации:**
  * Проверка формирования списка задач "на сегодня": подтверждение того, что в выборку без флага `--all` попадают просроченные невыполненные задачи (`overdue_included`), а выполненные задачи прошлого и текущего дня отсекаются.
  * Проверка формирования списка с флагом `--all`: подтверждение попадания выполненных задач, у которых дата выполнения совпадает с переданной локальной датой системы.

### 2. Интеграционное тестирование (Integration Testing)

Интеграционные тесты проверяют взаимодействие модулей приложения с реальной базой данных SQLite и файловой системой:
* **Тестирование инициализации (`clean_slate`):**
  * Запуск приложения в пустой временной директории. Проверка успешного автоматического создания структуры каталогов, папки `backups` и файла `todo.db` с корректными правами доступа (`0700` для папок и `0600` для файлов на Unix). Проверка, что файл создается строго внутри вычисленной `<WORK_DIR>`, а не в текущей рабочей директории терминала (CWD).
* **Тестирование репозитория БД:**
  * Проверка выполнения транзакций добавления, чтения и изменения статуса задач.
  * Проверка поведения при повторной попытке отметить как выполненную (`todo done`) уже выполненную задачу: тест должен верифицировать успешный возврат кода `0`, отсутствие генерации нового файла бэкапа и отсутствие повторной перезаписи БД (холостая операция / noop).
  * Проверка устойчивости к попыткам SQL-инъекций (передача в качестве заголовка строки вида `"'; DROP TABLE tasks; --"` не должна приводить к повреждению структуры базы данных).
* **Тестирование механизма автоматического резервного копирования (`auto_backups`):**
  * Проверка создания файла бэкапа перед операцией записи в БД с корректной точностью имени до микросекунд.
  * Проверка стабильной работы при пакетном быстром добавлении задач (несколько добавлений в секунду): тесты должны подтвердить отсутствие коллизий и перезаписей файлов благодаря микросекундной точности временных меток.
  * Проверка ротации: программное создание более 5 файлов резервных копий во временной папке и выполнение операции изменения данных. Ожидается автоматическое удаление старейшего файла и сохранение ровно 5 последних копий на диске на основе лексикографической сортировки их имен.
  * Симуляция ошибки записи бэкапа (например, ограничение прав на запись в папку `backups`). Проверка того, что транзакция в базе данных откатывается, исходный файл `todo.db` не изменяется, а приложение завершает работу с кодом `1`.

### 3. Системное тестирование (E2E / CLI Testing)

Системные тесты представляют собой автоматический запуск скомпилированной утилиты или интерпретируемого скрипта через интерфейс командной строки операционной системы в изолированном окружении:
* Проверка кодов возврата процесса (Exit Codes) для всех сценариев использования.
* Сравнение выводимых строк в потоках `stdout` и `stderr` с эталонными шаблонами.
* Проверка интеграции с конвейерами Unix: выполнение цепочек команд командной строки (например, перенаправление вывода `todo list` через конвейер в утилиты `grep`, `awk` или `wc -l` для подсчета количества активных задач).

## Success Criteria

Продукт считается готовым к эксплуатации при выполнении следующих критериев успешности:

1. **Мгновенный отклик (Latency):** Время выполнения любой команды утилиты при работе с базой данных объемом до 10 000 записей не превышает 100 миллисекунд (пользователь ощущает работу как мгновенную).
2. **Минимальное потребление ресурсов:** Приложение в процессе выполнения пиковых нагрузок потребляет не более 20 МБ оперативной памяти.
3. **Стабильность данных:** Ни при каких условиях сбоя дисковой подсистемы в процессе записи база данных не должна приходить в неконсистентное состояние. Наличие механизма ротируемых резервных копий гарантирует возможность восстановления данных до состояния на момент перед последней ошибочной операцией записи.
4. **Безопасность по умолчанию:** В UNIX-подобных системах папки создаются с правами доступа `0700` (что позволяет владельцу входить в них), а файлы базы данных и бэкапов гарантированно создаются с правами доступа `0600` по пути `<WORK_DIR>/todo.db`, полностью исключая чтение данных другими пользователями операционной системы.
5. **Совместимость со стандартами автоматизации:** Вывод списка задач утилиты стабильно парсится стандартными утилитами Unix за счет использования разделителей табуляции (`\t`), строгого формата статусов (`[ ]` и `[X]`), а также полного отсутствия строки заголовков и постороннего текстового шума.

## Key Solution Decisions

Для обеспечения соответствия требованиям и ограничениям системы были приняты следующие ключевые архитектурные решения:

* **Выбор СУБД SQLite без шифрования (`sqlite_format`, `plain_sqlite`):**
  Решение отказаться от шифрования БД (такого как SQLCipher) обосновано требованием максимальной простоты развертывания и отсутствия внешних бинарных зависимостей. Безопасность полностью делегирована механизмам операционной системы через ограничение прав доступа к директориям (`0700`) и файлам (`0600`).
* **Микросекундная точность временных меток бэкапов UTC (`YYYYMMDDHHMMSSffffff`):**
  Использование микросекундной точности при именовании резервных копий полностью устраняет риск коллизий имен файлов бэкапов при быстрых пакетных вызовах утилиты или при выполнении автоматического интеграционного тестирования в рамках одной секунды. Простая лексикографическая сортировка имен файлов по алфавиту гарантирует точную хронологическую последовательность без сбоев на стыках часовых поясов благодаря принудительному использованию UTC.
* **Разделение прав доступа (chmod 700 / chmod 600) в POSIX-окружении:**
  Принято решение создавать папки с флагом исполнения (`0700`), а файлы данных — без него (`0600`). Это предотвращает частую системную ошибку, при которой права `0600` на директорию блокируют переход текущего пользователя в нее, делая невозможным чтение базы данных при повторном запуске приложения.
* **Успешный холостой запуск (noop) при повторном `todo done`:**
  Выполнение команды `todo done` для уже завершенной задачи трактуется как успешное событие без изменения состояния. Это решение экономит дисковый ввод-вывод (I/O), предотвращает раздувание папки бэкапов дублирующими копиями одной и той же конфигурации базы данных и обеспечивает бесконечную идемпотентность вызовов в скриптах автоматизации.
* **Логика фокуса с включением просроченных дел (`overdue_included` / `auto_include`):**
  Отображение просроченных невыполненных задач в списке на "сегодня" является ключевым решением для личной продуктивности. Это гарантирует, что забытые задачи из прошлого не потеряются и будут перед глазами пользователя, пока он не изменит их дату или не отметит выполненными с помощью `todo done`.
* **Явная передача локальной системной даты приложения в SQL-запрос:**
  Решение отказаться от использования встроенной функции SQLite `CURRENT_DATE` в SQL-запросах обусловлено предотвращением рассинхронизации часовых поясов. Так как `CURRENT_DATE` в SQLite всегда вычисляется по UTC, пользователи в часовых поясах, отличных от UTC, сталкивались бы с некорректной фильтрацией задач на сегодня. Локальная системная дата вычисляется на уровне приложения и явно передается в качестве строкового параметра, гарантируя корректное сопоставление дат в любое время суток.
* **Изолированное создание базы данных строго в `<WORK_DIR>/todo.db`:**
  Прямая фиксация пути создания файла `todo.db` внутри вычисленной директории `<WORK_DIR>` исключает вероятность непреднамеренного засорения текущей рабочей папки пользователя (CWD) файлом базы данных. Это гарантирует предсказуемость файловой структуры приложения и сохраняет целостность пользовательских папок.
