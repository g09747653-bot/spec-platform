## Overview

В данном документе представлен детальный план разработки и список технических задач для реализации консольного планировщика личных дел на языке Python 3.10+. Архитектура утилиты спроектирована как автономный CLI-конвейер без сетевых зависимостей (`completely_offline`), использующий локальную базу данных SQLite в качестве хранилища (`plain_sqlite`) и поддерживающий автоматическое создание резервных копий (`auto_backups`) с ротацией.

Реализация разделена на логические этапы (фазы), которые разработчик или кодирующий агент может выполнять последовательно. Каждая задача сопровождается техническими требованиями, критериями приемки и указанием ожидаемого поведения системы.

---

### Этапы реализации (Phases of Implementation)

#### Фаза 1: Инициализация окружения и путей (Bootstrapping)
* **Задача 1.1: Определение и разрешение путей рабочей директории**
  * *Описание:* Реализовать логику определения пути рабочей директории на основе переменной окружения `TODO_WORK_DIR` или системных путей по умолчанию (`~/.config/todo/` для Linux/macOS и `%APPDATA%/todo/` для Windows).
  * *Критерии приемки:* Путь корректно преобразуется в абсолютный. Корректно обрабатывается символ `~` в UNIX-системах.
* **Задача 1.2: Создание структуры папок и разграничение прав доступа**
  * *Описание:* Реализовать автоматическое создание рабочей директории и поддиректории `backups`. На UNIX-подобных системах применить системные вызовы для установки прав доступа `0700` (`chmod 700`) для создаваемых директорий.
  * *Критерии приемки:* Папки создаются автоматически при их отсутствии. В Linux/macOS права доступа строго соответствуют `0700`.

#### Фаза 2: Слой доступа к данным (Data Access Layer & clean_slate)
* **Задача 2.1: Инициализация базы данных и схемы (`clean_slate`)**
  * *Описание:* Реализовать проверку наличия файла базы данных `todo.db` в вычисленной рабочей директории. Если файл отсутствует, он должен создаваться автоматически с правами `0600` на POSIX-системах. При создании файла должна разворачиваться схема таблицы `tasks` и создаваться индексы `idx_tasks_due_date` на поле `due_date` и `idx_tasks_is_completed` на поле `is_completed`. Инициализация выполняется с чистого листа без использования исторических миграций.
  * *Критерии приемки:* Файл `todo.db` создается автоматически строго внутри вычисленной `<WORK_DIR>`. Схема содержит таблицу `tasks` со столбцами: `id` (INTEGER PRIMARY KEY AUTOINCREMENT), `title` (TEXT NOT NULL), `due_date` (TEXT NOT NULL), `is_completed` (INTEGER NOT NULL DEFAULT 0), `created_at` (TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP). Индексы успешно созданы. На POSIX права файла равны `0600`.
* **Задача 2.2: Реализация репозитория задач (`TaskRepository`)**
  * *Описание:* Написать класс репозитория для работы с SQLite. Все запросы на чтение и запись должны выполняться с использованием параметризованных запросов (placeholders `?`) во избежание SQL-инъекций. Реализовать методы: `insert_task(title, due_date)`, `get_task_by_id(task_id)`, `update_task_status(task_id, is_completed)`, `fetch_active_tasks(local_today)`, `fetch_all_tasks(local_today)`.
  * *Критерии приемки:* Ни один запрос не использует прямую склейку строк. Операции изменения данных (`insert`, `update`) выполняются строго в рамках транзакций.

#### Фаза 3: Сервис резервного копирования и ротации (Backup & Rotation Service)
* **Задача 3.1: Механизм автоматического бэкапа перед транзакциями записи**
  * *Описание:* Реализовать модуль `BackupService`, копирующий рабочий файл `todo.db` в папку `backups` перед совершением любых транзакций записи (добавление новой задачи, изменение статуса существующей задачи). Имя файла должно соответствовать шаблону `todo.db.bak.YYYYMMDDHHMMSSffffff`, где временная метка вычисляется по UTC с точностью до микросекунд.
  * *Критерии приемки:* Копия файла успешно создается до момента физической записи в рабочий файл БД. В UNIX-системах копия создается с правами `0600`. При ошибке создания бэкапа (например, нет места на диске) текущая транзакция записи прерывается, выводится сообщение в `stderr`, утилита завершает работу с кодом `1`.
* **Задача 3.2: Алгоритм ротации резервных копий**
  * *Описание:* Реализовать логику контроля количества бэкапов. После успешного создания новой копии сервис должен проверить общее количество бэкап-файлов в папке `backups`. Если их больше 5, файлы сортируются лексикографически по имени, и самый старый файл удаляется.
  * *Критерии приемки:* В папке `backups` всегда сохраняется ровно 5 последних файлов резервных копий. Алгоритм ротации корректно отрабатывает при высокой частоте вызовов.

#### Фаза 4: Бизнес-логика планировщика (Business Logic Layer)
* **Задача 4.1: Валидация входных данных бизнес-слоя**
  * *Описание:* Реализовать валидацию заголовка задачи (не пустой, содержит не только пробелы) и даты (формат `YYYY-MM-DD`, реальная календарная дата в диапазоне лет 1900–2100).
  * *Критерии приемки:* Ошибки валидации вызывают исключения бизнес-логики для последующей обработки на уровне представления.
* **Задача 4.2: Логика фильтрации задач на сегодня (`overdue_included` / `auto_include`)**
  * *Описание:* На стороне приложения вычислить текущую локальную системную дату в формате `YYYY-MM-DD` (без использования функций времени SQLite вроде `CURRENT_DATE`, чтобы избежать смещения поясов). Реализовать выборку задач согласно следующим правилам:
    * *Без флага `--all`:* выбираются только невыполненные задачи (`is_completed = 0`), у которых `due_date <= local_today` (что включает просроченные задачи из прошлого).
    * *С флагом `--all`:* выбираются невыполненные задачи (`is_completed = 0`), у которых `due_date <= local_today`, а также выполненные задачи (`is_completed = 1`), у которых `due_date = local_today`.
  * *Критерии приемки:* Логика фильтрации однозначно исключает будущие невыполненные задачи при запросе списка задач. Выборка содержит просроченные дела из прошлого. Сортировка записей в выборке: по `due_date` (ASC), затем по `id` (ASC).
* **Задача 4.3: Идемпотентность закрытия задач (noop для `todo done`)**
  * *Описание:* Перед выполнением отметки задачи как выполненной проверить ее текущий статус в БД. Если задача уже выполнена (`is_completed = 1`), то операция записи не инициируется, бэкап не создается, транзакция записи не открывается. Происходит успешный холостой возврат (noop).
  * *Критерии приемки:* Повторный вызов `todo done <id>` завершается успешно (код `0`) мгновенно, не плодя новые файлы бэкапов и не перезаписывая диск.

#### Фаза 5: CLI Интерфейс и форматирование (CLI Presentation & Integration)
* **Задача 5.1: Разбор аргументов командной строки (CLI Parser)**
  * *Описание:* С помощью стандартного модуля `argparse` реализовать парсинг трех команд: `add`, `list`, `done`. Настроить поведение параметра `--date` для команды `add`: если параметр `--date` опущен в CLI, в качестве `due_date` в базу данных должна записываться текущая локальная системная дата в формате `YYYY-MM-DD`.
  * *Критерии приемки:* Синтаксические ошибки разбора (неизвестный флаг, отсутствие обязательных параметров) приводят к выводу справки/сообщения в `stderr` и завершению работы с кодом `2`. Нечисловые или неположительные идентификаторы в команде `done` вызывают ошибку синтаксиса (код `2`). В БД пишется корректная дата по умолчанию при отсутствии явного указания `--date` в команде `add`.
* **Задача 5.2: Форматирование вывода в `stdout`**
  * *Описание:* Настроить вывод результатов выполнения команд:
    * При успешном выполнении `todo add`: выводится только ID созданной задачи.
    * При успешном выполнении `todo done`: вывод полностью отсутствует (тишина).
    * При выполнении `todo list`: выводится список строк без заголовков столбцов и пустых строк. Поля разделяются символом табуляции `\t`: `<id>\t<статус>\t<дата>\t<название>`. Строгое представление статусов: `[ ]` для невыполненных, `[X]` для выполненных.
  * *Критерии приемки:* Формат вывода строго соответствует спецификации, не содержит декоративных элементов и псевдографики.
* **Задача 5.3: Централизованная обработка ошибок и кодов возврата (Exit Codes)**
  * *Описание:* Реализовать перехват всех системных и семантических исключений в точке входа приложения. Перехватывать ошибки отсутствия прав доступа, неверного формата даты, несуществующего ID задачи в `todo done`. Выводить лаконичное сообщение на русском языке в поток `stderr` (без отображения stack trace) и завершать работу с кодом `1`.
  * *Критерии приемки:* Исключены падения программы с необработанными трейсбеками Python. Любая штатная логическая или дисковая ошибка завершается с кодом `1`.
* **Задача 5.4: Реализация опционального отладочного логирования (`TODO_DEBUG=1`)**
  * *Описание:* Если в окружении установлена переменная `TODO_DEBUG=1`, приложение должно записывать техническую информацию, выполняемые SQL-запросы и stack trace возникающих ошибок в файл `todo.log`, располагаемый непосредственно в вычисленной рабочей директории приложения. По умолчанию логирование в файл отключено. Чтобы предотвратить неконтролируемое разрастание файла, использовать ротируемый обработчик логов с ограничением размера.
  * *Критерии приемки:* При `TODO_DEBUG=1` файл `todo.log` создается в рабочей директории и наполняется отладочной информацией. В штатном режиме (переменная не задана) лог-файл не создается и не изменяется.

#### Фаза 6: Покрытие тестами (Testing Suite)
* **Задача 6.1: Модульные тесты (Unit Tests)**
  * *Описание:* Написать тесты для парсера аргументов (включая проверку значения по умолчанию для даты при добавлении задачи), валидатора дат и правил фильтрации задач.
* **Задача 6.2: Интеграционные тесты (Integration Tests)**
  * *Описание:* Написать тесты для проверки инициализации БД (`clean_slate`), транзакционности записи, механизма создания и ротации бэкапов (включая проверку лексикографической ротации по временным меткам), а также прав доступа к создаваемым файлам.
* **Задача 6.3: Системные E2E-тесты (CLI Tests)**
  * *Описание:* Реализовать автоматизированный запуск утилиты в изолированном окружении, проверку кодов возврата процесса и сопоставление вывода в `stdout`/`stderr` с эталонными шаблонами.

## Risks & Sequencing Notes

### Ключевые риски и стратегии их минимизации

1. **Различия прав доступа в ОС (POSIX vs Windows):**
   * *Риск:* Попытка вызова UNIX-специфичных функций изменения прав доступа (например, `os.chmod` с правами `0600`) в среде Windows приведет к сбою выполнения программы.
   * *Минимизация:* В модуле инициализации окружения применить условное ветвление. Изменять права доступа на `0700` для папок и `0600` для файлов только в случае, если `os.name == 'posix'`. На операционных системах семейства Windows использовать стандартные права наследования папки `%APPDATA%` без вызова низкоуровневых ACL API.

2. **Коллизии при ротации бэкапов при высокочастотных тестах:**
   * *Риск:* Если тесты выполняются очень быстро (в рамках одной секунды), несколько бэкапов могут получить одинаковую временную метку `YYYYMMDDHHMMSS`, что вызовет перезапись файлов резервных копий или сбой в определении самого старого файла.
   * *Минимизация:* Использовать в имени файлов бэкапов временную метку UTC с обязательным указанием микросекунд: `todo.db.bak.YYYYMMDDHHMMSSffffff`. Это гарантирует абсолютную уникальность каждого бэкап-файла даже в быстрых автоматизированных тестах.

3. **Смещение часовых поясов при выборке задач:**
   * *Риск:* Если использовать встроенные функции SQLite вроде `CURRENT_DATE`, выборка задач "на сегодня" будет опираться на время UTC, из-за чего у пользователей в других часовых поясах задачи могут пропадать или появляться несвоевременно.
   * *Минимизация:* Категорически отказаться от использования `CURRENT_DATE` в SQL-запросах. Текущая локальная дата должна вычисляться силами Python в локальном часовом поясе системы пользователя и передаваться в параметризованный SQL-запрос как строка вида `YYYY-MM-DD`.

4. **Блокировка доступа к директории при неверных правах:**
   * *Риск:* Ошибка установки прав `0600` вместо `0700` для создаваемых директорий рабочей области сделает невозможным вход в директорию и чтение файлов внутри нее при повторных запусках.
   * *Минимизация:* Директории всегда создавать строго с правами `0700` (разрешающими выполнение/переход), а файлы данных и бэкапов — с правами `0600`. Это требование должно быть покрыто интеграционными тестами.

5. **Бесконечный рост лог-файла в режиме отладки:**
   * *Риск:* При активированном `TODO_DEBUG=1` файл `todo.log` может разрастись и занять дисковое пространство.
   * *Минимизация:* Ограничить объем записи логов или использовать ротируемый обработчик логов стандартной библиотеки Python (`logging.handlers.RotatingFileHandler`) с жестким лимитом размера файла (например, 5 МБ) и количеством резервных файлов.

### Рекомендуемая последовательность разработки (Sequencing)

Для минимизации переписывания кода рекомендуется придерживаться строго восходящей последовательности разработки (Bottom-Up):

```
┌────────────────────────────────────────────────────────┐
│ Фаза 5: CLI Интерфейс, Форматирование и Коды Возврата   │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│ Фаза 4: Бизнес-логика, Даты и Идемпотентность (Noop)   │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│ Фаза 3: Сервис Бэкапов (Резервное копирование)         │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│ Фаза 2: Слой Базы Данных (Repository, clean_slate)     │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│ Фаза 1: Инициализация Путей и Создание Папок (POSIX)   │
└────────────────────────────────────────────────────────┘
```

1. **Сначала реализовать Фазу 1:** Это заложит надежный фундамент для работы с файловой системой и гарантирует, что база данных всегда будет создаваться в правильном месте с корректными правами доступа.
2. **Затем Фазу 2:** Создать схему данных и репозиторий. Без стабильного слоя данных невозможно тестировать бизнес-логику.
3. **Далее Фазу 3:** Встроить автоматические бэкапы. Это важно сделать до реализации сервисного слоя, чтобы бизнес-логика могла прозрачно вызывать бэкап перед транзакциями записи.
4. **Затем Фазу 4:** Реализовать логику отбора задач и обработку статусов на уровне сервисов, опираясь на готовые методы репозитория.
5. **В последнюю очередь Фазу 5:** Написать парсер аргументов командной строки и связать его с сервисным слоем. Это позволит не отвлекаться на особенности разбора CLI при отладке логики приложения. Также на этом этапе реализуется отладочное логирование (`TODO_DEBUG=1`), которое поможет анализировать интеграцию компонентов.
6. **Фаза 6 (Тестирование):** Должна выполняться параллельно (TDD) или сразу после завершения соответствующих фаз реализации, начиная от модульных тестов компонентов и заканчивая системным E2E-тестированием готовой CLI-утилиты.
